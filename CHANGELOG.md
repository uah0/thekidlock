# Журнал изменений

## Актуальный IP Web UI после отключения домашнего Wi-Fi — 04.10.2026

- Кнопка «Настройки» всегда запрашивает актуальный IPv4 ESP32 по encrypted BLE; сохранённый `lock_wifi_ip` больше не открывается напрямую.
- Если ESP не сообщает IP в течение 5 секунд, приложение запускает существующий LocalOnlyHotspot и Wi-Fi provisioning.
- Runtime на Redmi Note 15 подтверждён при выключенном ESP автоподключении к домашнему Wi-Fi: телефон создал hotspot `172.18.51.2`, ESP отправила актуальный IP `172.18.51.177`, Web UI открылся; старый `192.168.1.54` не открывался.
- Android build 182 и debug/release unit tests прошли; Web UI ESP подтвердил firmware 10.0.314.

## Передача Web UI IP от ESP к телефону — 04.10.2026

- ESP автоматически передаёт собственный Web UI IPv4 через encrypted BLE; Android сохраняет адрес и открывает браузер по нажатию «Настройки» только после получения свежего IP. Если IP отсутствует, после 5 секунд запускаются прежние LocalOnlyHotspot и Wi-Fi provisioning.
- RSSI-порог открытия применяется только к обычному lock beacon; служебные BLE-маркеры `0x81`/`0x82` принимаются без этого порога.
- Android build 180 и debug/release unit tests собраны успешно; установка на Redmi Note 15 прошла с восстановлением ориентации `1/0`.
- ESP build 10.0.314 прошит OTA (`10.0.313 → 10.0.314`), версия после перезапуска подтверждена.
- Runtime подтверждает encrypted IP push, сохранение `192.168.1.54` и открытие Chrome с Web UI. Hotspot fallback создал сеть с IP телефона `172.18.51.2`; соединение в no-home-Wi-Fi сценарии после RSSI-исправления не запускалось.

## Калибровка по закрытой и открытой двери — 01.10.2026

- Мастер больше не просит вручную подставлять лист или отдельно измерять

- Raw одного листа вычисляется как `closed + (open - closed) / 6.14`;
  raw двух листов остаётся расчётной точкой для существующей шкалы ULP. Firmware
  валидирует допустимый диапазон до записи прежнего формата калибровки в NVS.
- Сборка 10.0.242 установлена на текущий замок; он вернулся в сеть в состоянии
  `LOCKED`, `fault_flags=0`. Страница мастера отвечает HTTP 200.

## Android: закрытие при выходе из Always Open — 28.09.2026

- При выключении Always Open Android отправляет `AUTO_OFF_CLOSE`, чтобы замок
  сразу получил запрос закрытия; переход в обычный AUTO подтверждается через

- Сброс Always Open выключает и сохраняет автооткрытие; явный выбор AUTO
  закрывает замок перед возобновлением автоматического открытия.
- Добавлен тест reducer-а для выключения Always Open обеими mode-кнопками.
- Проверено на телефоне: Always Open дал `OPEN_HOLD`, сброс дал `LOCKED`.
  Добавлена очистка native presence latch после закрытия; APK build 107 установлен.
- Полный прогон build 107 подтвердил AUTO (`OPEN`) → Always Open (`OPEN_HOLD`)
  → сброс (`LOCKED`) → AUTO (`OPEN`) → AUTO off (`LOCKED`); в конце замок
  оставался закрытым при телефоне рядом.

## RSSI-контроль и удаление «Долго открыт» — 28.09.2026

- `phone_rssi_threshold` больше не проверяется повторно при записи команды
  `OPEN`; там остаётся проверка encrypted/bonded. Порог применяется в RSSI
  мониторе зоны, который отключает соединение после `zone_exit_grace_ms`.
- Удалены настройка `long_open_s`, её обычные дедлайны и поле из ESP Web UI и
  BLE admin-схемы. Старые NVS-ключи удаляются при запуске/сохранении конфига.
- Сохранён отдельный фиксированный 10-секундный ручной тест открытия.
- Android admin UI также больше не показывает удалённую настройку; legacy BLE
  CSV сохраняет зарезервированное поле для совместимости старых клиентов.

## Android: непрерывное ожидание BLE-рекламы — 28.09.2026

## Настройка выдержки выхода из BLE-зоны — 27.09.2026

## BLE multi-slot — этап 2, таблица соединений — 26.09.2026

- Состояние RSSI, security и регистрации перенесено из singleton-полей в таблицу
  слотов. `OPEN` использует RSSI своего соединения; сигналы для lock-control
  агрегируются, а потеря одного secured-соединения не сбрасывает остальные.

## BLE multi-slot — этапы 3–4, владелец и реклама — 26.09.2026

- Слот 0 зарезервирован за владельцем, гостям доступны только слоты 1–5. При
  первом pairing owner-соединение переносится из временного guest slot в слот 0;
  повторное параллельное owner-соединение отклоняется.
- Реклама запускается, пока свободен хотя бы один слот, и останавливается, когда
  заняты все шесть. Accept-list остаётся общим и не менялся.

## BLE multi-slot — этап 5, admission grace для гостей — 26.09.2026

- Слабый гостевой слот освобождается после 1500 мс валидной медианы ниже общего
  порога открытия. Слот владельца исключён; старый 6000 мс BLE disconnect grace
  сохранён отдельно. При RSSI не ниже порога или открытой/удерживаемой двери новый
  отсчёт не запускается.

## BLE multi-slot — этап 6, диагностика слотов — 26.09.2026

- В существующий RSSI task добавлен периодический `ESP_LOGI` с индексом слота,
  owner flag, handle, последним RSSI и временем слабого гостевого сигнала.
- Финальная прошивка с проверенными типами аргументов логов: `10.0.200`.

## Отключение импульсной проверки зазора при постоянном открытии — 26.09.2026

- В ULP добавлен отдельный `ULP_CMD_HOLD_OPEN`. В этом режиме gate удерживается
  LOW, импульсное измерение зазора пропускается, `pulse_actual_us` публикуется
  как 0.
- Состояние восстанавливается из NVS после перезагрузки и возвращается к
  обычному измерению при выключении режима.
- При переходе из LOCKED в постоянное открытие сохраняется проверка снятия
  остаточного тока, но после неё импульсное измерение не выполняется.
- Обычный OPEN, таймеры, закрытие и финальная проверка закрытия не изменены.

## BLE больше не ждёт подключения Wi-Fi при загрузке

- Раньше `app_main()` вызывал `wifi_sta_start_and_wait()`, который блокировался
  (`portMAX_DELAY`) до получения IP по Wi-Fi, и только после этого стартовал
  `ble_phone_init()`. Если роутер после ребута отвечал медленно (сам ещё
  поднимается, DHCP не сразу отвечает, ретраи и т.п.), телефон физически не
  видел устройство по BLE всё это время — иногда около минуты и дольше.
- `wifi_sta_start_and_wait()` переименован в `wifi_sta_start()` и больше не
  блокируется: запускает Wi-Fi STA и сразу возвращается; подключение и
  переподключение продолжаются в фоне через уже существующий
  `wifi_event_handler` (лог о реальном подключении по-прежнему пишется).
- Порядок в `app_main()` изменён: `ble_phone_init()` теперь вызывается сразу
  после `lock_control_init()`/`buzzer_init()`, **до** старта Wi-Fi — телефон
  может открывать замок по BLE сразу после загрузки независимо от состояния
  Wi-Fi. `web_ui_start()` по-прежнему идёт после `wifi_sta_start()`, так как
  ему нужен инициализированный `esp_netif`/LWIP (это делает `wifi_sta_start()`),
  но не требует уже установленного соединения.

## Исправлен выбор порога RSSI при снятии блокировки

- Найдена реальная причина "мгновенного" снятия фиолетовой блокировки:
  `ble_phone.c` выбирал порог сравнения RSSI только по `lock_control_is_open()`.
  Пока замок заблокирован (`reopen_blocked`), он физически закрыт, поэтому
  код ошибочно брал строгий порог открытия (`phone_rssi_threshold`) вместо
  слабого порога удержания (`phone_rssi_hold_threshold`) — а именно слабый
  порог логически должен использоваться для решения "телефон достаточно
  ушёл, чтобы снять блокировку". Строгий порог менее отрицательный, поэтому
  срабатывал как "слабый сигнал" значительно чаще, создавая впечатление
  мгновенного сброса от одного сигнала.
- Добавлена `lock_control_is_blocked()` — потокобезопасный геттер текущего
  состояния `reopen_blocked` (раньше это было локальной переменной внутри
  задачи `lock_task` и не было видно снаружи модуля).
- `ble_phone.c` теперь использует слабый порог удержания, если замок либо
  открыт, либо заблокирован; строгий порог открытия — только когда замок
  закрыт и не заблокирован (обычное ожидание приближения телефона).

## Строгий счётчик снятия блокировки повторного открытия

- Счётчик слабого RSSI для снятия `reopen_blocked` сделан строго
  последовательным: любой один сильный (`RSSI_HIGH`) сбрасывает счётчик в 0;
  снятие блокировки требует ровно 3 подряд слабых отсчёта без перерыва.
- Убрано мгновенное снятие блокировки по событию BLE-дисконнекта. Раньше
  `LOCK_EVENT_DISCONNECTED` снимал блокировку по одному событию в обход
  правила "3 подряд" — а разрыв BLE-соединения не доказывает, что телефон
  физически ушёл (фоновый режим приложения, разрывы стека BLE и т.п. могут
  происходить, даже когда телефон лежит рядом с ридером). Теперь
  единственный путь снятия блокировки — строгий RSSI-счётчик.

  менялось в момент переключения.
- Исправлен порядок инициализации в `main.c`: `led_init()` теперь вызывается
  до `lock_control_init()`, чтобы стартовый вызов `led_set_state(LED_STATE_LOCKED)`

  «boot»-цветом до первого события open/close).

- Постоянное питание соленоида после импульса 300 мс и паузы 100 мс теперь разрешается только по отдельной горячей границе: 4% интервала холодной калибровки «контакт → один лист» от горячего эталона полного контакта.

- Финальная проверка полного контакта стала симметричной относительно горячего эталона. Односторонняя проверка ошибочно принимала любое уменьшение ADC за улучшение контакта; теперь допустим только диапазон ±1% интервала contact…paper1 (минимум ±1 RAW).
- После отказа с зазором ULP больше не требует отвода пластины в состояние FAR. Он бесконечно ждёт холодный `CONTACT`, затем повторяет полную проверку 300/100/2 мс; при сохраняющемся зазоре силовые импульсы не повторяются.

- Холодное подтверждение после отказа использует узкое симметричное окно ±1% вокруг калибровочного контакта, а не широкую рабочую границу CONTACT 17%.

- Удалено незаданное требование пяти последовательных CONTACT. При уже прижатой пластине CLOSE сразу выполняет штатную проверку; после отказа первый классифицированный CONTACT запускает повтор без обязательного открытия двери.
- Android-кнопки AUTO и ALWAYS_OPEN стали переключателями: повторное нажатие AUTO выключает автоматику через `AUTO_OFF_CLOSE`, повторное нажатие ALWAYS_OPEN возвращает `MODE_AUTO`. Цвет AUTO снова отражает фактическую активность сервиса телефона.
- Единая граница CONTACT уменьшена с 17% до 10% интервала между калибровками полного контакта и одного листа; холодная и горячая проверки используют одно значение.

## Hotspot IPv4 через защищённый PhoneBeacon — Android этап (02.10.2026)

- После `LocalOnlyHotspotCallback.onStarted()` Android пытается определить текущий IPv4 по поднятым AP интерфейсам (`ap*`, `softap*`, `swlan*`); если AP интерфейс не обнаружен — использует единственный однозначный `wlan*` IPv4. При неоднозначности/ошибке IP не передаётся, фиксируется logcat warning, SSID/пароль provisioning продолжаются.
- IP (4 bytes network-order; `00 00 00 00` = отсутствует) передаётся BleLockService в `PhoneBeacon`. В GATT добавлена encrypted-read характеристика `HOTSPOT_IP_UUID = 6f4f0014-9a7b-4c21-8d32-5e6f708192a3` к существующему сервису.
- `PhoneBeacon` проверяет `BOND_BONDED`; `PERMISSION_READ_ENCRYPTED` оставляет фактическую проверку encryption стандартному Android Bluetooth stack. IP очищается при `onStopped`, `onFailed` и остановке reservation.
- Android `build-android.ps1 -Action test`: PASS (debug/release compile и unit tests). Добавлены проверки выбора AP-интерфейса, неоднозначности WLAN-кандидатов и недопустимого IPv4.

## HOTSPOT_IP — завершение Android/ESP (02.10.2026)

- Android IPv4 lookup использует перечисление поднятых интерфейсов и адресов. В первую очередь рассматриваются интерфейсы с AP-названием `ap*`, `softap*`, `swlan*`; единственный `wlan*` кандидат допускается только если нет активной Wi-Fi station сети. Адреса loopback/link-local/multicast/unspecified/broadcast отбрасываются. Неоднозначность возвращает «нет данных» и сохраняет credential/DHCP fallback. Стандартный Android API не раскрывает стабильно имя SoftAP интерфейса, поэтому физическое подтверждение на целевой модели остаётся необходимым.
- GATT characteristic: `HOTSPOT_IP_UUID = 6f4f0014-9a7b-4c21-8d32-5e6f708192a3`, в существующем PhoneBeacon service; 4 bytes IPv4 network-order, `00 00 00 00` означает отсутствие IP.
- Android проверяет `device.bondState == BOND_BONDED`; characteristic имеет `PERMISSION_READ_ENCRYPTED`, так что enforcement шифрования остаётся системному Bluetooth stack. IP очищается по жизненному циклу reservation; session token не даёт позднему STOP старого hotspot очистить адрес новой сессии.
- ESP использует единственный исходящий GATT connection: `connect → encrypted/bonded proof BLE_LOCK_V1 → Wi-Fi credentials → HOTSPOT_IP`. IP читается только при provisioning marker `0x81`; обычный AUTO proof не делает дополнительного чтения и соединения.
- ESP проверяет unicast IPv4, хранит его только в RAM через `wifi_ota_set_runtime_phone_ip()` / `wifi_ota_get_runtime_phone_ip()`. На IP отсутствует/ошибке продолжается credential provisioning fallback. ESP DHCP/static-IP поведение не менялось; NVS не получает IP телефона.
- Android `build-android.ps1 -Action test`: PASS, build 153 (debug/release и unit tests). ESP `build-esp32.ps1`: PASS, firmware 10.0.275; OTA PASS, device-agent подтвердил `10.0.274 → 10.0.275`.
- Радио-тест характеристик на физическом телефоне и проверка фактического интерфейса hotspot не выполнялись. Resolver покрыт unit tests, но использует доступные интерфейсы Android и при ambiguity намеренно возвращает отсутствие адреса.

# 03.10.2026 — оставить PhoneBeacon GATT Server между Auto OFF/ON

- В Auto OFF Android больше не закрывает GATT Server в активном bound `BleLockService`: останавливает advertising и запрашивает отключение подключённых peer. Auto ON повторно запускает advertising через тот же GATT Server. Если disconnect ещё выполняется, advertising ждёт callback отключения.
- Пока Auto Open OFF, proof/name/owner GATT операции отклоняются. Характеристики Wi-Fi доступны только во время отдельного provisioning. При уничтожении `BleLockService` сервер штатно закрывается.
