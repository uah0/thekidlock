## Таймер Б выхода из жёлтого состояния — 23.07.2026

- В конфигурацию ESP32/NVS добавлен `timer_b_s`, по умолчанию 5 секунд, диапазон 0–3600 секунд.

## BLE больше не ждёт подключения Wi-Fi при загрузке

- Раньше `app_main()` вызывал `wifi_sta_start_and_wait()`, который блокировался
  (`portMAX_DELAY`) до получения IP по Wi-Fi, и только после этого стартовал
  `ble_phone_init()`. Если роутер после ребута отвечал медленно (сам ещё
  поднимается, DHCP не сразу отвечает, ретраи и т.п.), телефон физически не
  видел устройство по BLE всё это время — иногда около минуты и дольше.
- `wifi_sta_start_and_wait()` переименован в `wifi_sta_start()` и больше не
  блокируется: запускает Wi-Fi STA и сразу возвращается; подключение и
  переподключение продолжаются в фоне через уже существующий
  `wifi_event_handler` (лог о реальном подключении по-прежнему пишется).
- Порядок в `app_main()` изменён: `ble_phone_init()` теперь вызывается сразу
  после `lock_control_init()`/`buzzer_init()`, **до** старта Wi-Fi — телефон
  может открывать замок по BLE сразу после загрузки независимо от состояния
  Wi-Fi. `web_ui_start()` по-прежнему идёт после `wifi_sta_start()`, так как
  ему нужен инициализированный `esp_netif`/LWIP (это делает `wifi_sta_start()`),
  но не требует уже установленного соединения.

## Исправлен выбор порога RSSI при снятии блокировки

- Найдена реальная причина "мгновенного" снятия фиолетовой блокировки:
  `ble_phone.c` выбирал порог сравнения RSSI только по `lock_control_is_open()`.
  Пока замок заблокирован (`reopen_blocked`), он физически закрыт, поэтому
  код ошибочно брал строгий порог открытия (`phone_rssi_threshold`) вместо
  слабого порога удержания (`phone_rssi_hold_threshold`) — а именно слабый
  порог логически должен использоваться для решения "телефон достаточно
  ушёл, чтобы снять блокировку". Строгий порог менее отрицательный, поэтому
  срабатывал как "слабый сигнал" значительно чаще, создавая впечатление
  мгновенного сброса от одного сигнала.
- Добавлена `lock_control_is_blocked()` — потокобезопасный геттер текущего
  состояния `reopen_blocked` (раньше это было локальной переменной внутри
  задачи `lock_task` и не было видно снаружи модуля).
- `ble_phone.c` теперь использует слабый порог удержания, если замок либо
  открыт, либо заблокирован; строгий порог открытия — только когда замок
  закрыт и не заблокирован (обычное ожидание приближения телефона).

## Строгий счётчик снятия блокировки повторного открытия

- Счётчик слабого RSSI для снятия `reopen_blocked` сделан строго
  последовательным: любой один сильный (`RSSI_HIGH`) сбрасывает счётчик в 0;
  снятие блокировки требует ровно 3 подряд слабых отсчёта без перерыва.
- Убрано мгновенное снятие блокировки по событию BLE-дисконнекта. Раньше
  `LOCK_EVENT_DISCONNECTED` снимал блокировку по одному событию в обход
  правила "3 подряд" — а разрыв BLE-соединения не доказывает, что телефон
  физически ушёл (фоновый режим приложения, разрывы стека BLE и т.п. могут
  происходить, даже когда телефон лежит рядом с ридером). Теперь
  единственный путь снятия блокировки — строгий RSSI-счётчик.

## Реальный RSSI в настройках, цвет блокировки и GPIO замка в Web UI

- В таблицу «Настройки замка» добавлена верхняя строка «Текущий RSSI (сейчас)»,
  обновляется вместе с общим статусом (раз в 500 мс), над строками порогов
  RSSI, чтобы значение порогов было видно относительно живого сигнала.
- Цвет светодиода при заблокированном повторном открытии заменён с
  малинового на фиолетовый (`{140, 0, 230}`).
- Устранена ошибка: при снятии блокировки повторного открытия (по слабому
  RSSI или по disconnect) без нового события open/close светодиод не
  возвращался в красный (LOCKED) — теперь возвращается явно.
- `APP_LOCK_GPIO` стал настройкой по умолчанию, а не жёстко зашитым пином:
  добавлено поле `lock_gpio` в `app_config_t`, сохраняется в NVS под ключом
  `lock_gpio`, доступно через `GET/POST /api/config` и как поле-список (select)
  «GPIO замка» в Web UI, по аналогии с уже существующим GPIO бипера.
- `lock_control` получил `lock_control_set_gpio()` — безопасное переключение
  пина замка в рантайме (по аналогии с `buzzer_set_gpio()`): старый пин
  переводится в закрытое состояние и освобождается, новый настраивается и
  получает текущий логический уровень замка, чтобы физическое состояние не
  менялось в момент переключения.
- Исправлен порядок инициализации в `main.c`: `led_init()` теперь вызывается
  до `lock_control_init()`, чтобы стартовый вызов `led_set_state(LED_STATE_LOCKED)`
  внутри `lock_control_init()` реально применялся (иначе LED оставался
  «boot»-цветом до первого события open/close).
- BLE admin-протокол конфигурации (GATT-характеристика) не изменён и по-прежнему
  передаёт 6 полей; `lock_gpio` через него не редактируется (сохраняется
  текущее значение), редактирование — только через Web UI.

## Этап 5 — защищённая команда OPEN и управление bonds

- В Web UI добавлены список NimBLE bonds, удаление выбранного bond и удаление
  всех bonds. Автоматическое удаление по-прежнему запрещено.
- Добавлены `GET/DELETE /api/ble/bonds`.
- Исправлен сценарий, когда bond удалён только на телефоне: пользователь может
  удалить соответствующий ключ ESP32 и повторить регистрацию в 60-секундном
  окне.
- `LOCK_COMMAND=OPEN` принимается только при одновременно выполненных условиях:
  encrypted connection, bonded peer и RSSI не ниже -68 dBm.
- GATT callback не управляет GPIO: он помещает запрос в очередь `lock_control`.
- Автомат таймеров перенесён в `lock_control`: OPEN запускает таймер А и
  неперезапускаемый таймер «Долго открыт»; достаточный RSSI телефона обновляет
  таймер А каждые 500 мс.
- По истечении «Долго открыт» сохраняется блокировка повторного открытия; она
  снимается после трёх слабых RSSI-измерений или disconnect.
- Устаревшая задача мониторинга маяков больше не запускается и не перезаписывает
  LED/состояние phone-only автомата.
- Исправлено повторное открытие: принятая защищённая команда OPEN вооружает
  текущее соединение до disconnect. После снятия блокировки тремя слабыми
  RSSI-измерениями последующее приближение телефона снова открывает замок и
  запускает новый цикл таймеров.

## Этап 4 — режим регистрации телефона

- Добавлено закрытое по умолчанию 60-секундное окно регистрации.

- При наличии 10 bonds новый телефон отклоняется с записью в журнал; старые
  bonds автоматически не удаляются.

## Этап 3 — LE Secure Connections и Bonding

- Для всех трёх GATT-характеристик включено требование шифрования.
- NimBLE Security Manager настроен на Bonding и LE Secure Connections.
- Legacy Pairing отключён; используется LE Secure Connections.
- Используется модель `No Input / No Output` и стандартное LE Secure
  Connections Just Works без собственной криптографии.
- Включено стандартное сохранение bonding keys NimBLE во внутренней NVS.
- Максимум сохранённых bonds увеличен до 10, максимум соединений уменьшен до 1.
- Добавлено журналирование успешного шифрования, bonded-состояния и размера
  ключа.
- Повторный Pairing при существующем bond отклоняется без автоматического
  удаления ключей.
- Команда `OPEN` по-прежнему только журналируется и не открывает замок.
- После аппаратного теста отключён запуск старого бесконечного Observer scan:
  его одновременная работа с Advertising и входящим соединением приводила к
  panic внутри `ble_gap_update_next_exp`. Это соответствует приоритетному
  phone-only ТЗ; исходные файлы сканера будут удалены окончательно при
  завершении миграции Web UI и таймерного автомата.
- После диагностированного SMP timeout (`BLE_HS_ETIMEOUT=13`) ESP32 теперь
  явно запускает стандартную процедуру безопасности сразу после подключения,
  не полагаясь на автоматическую реакцию BLE-клиента на ATT security error.
- Добавлено журналирование требуемого NimBLE `PASSKEY_ACTION` для диагностики
  возможностей конкретного телефона.
- Исправлен конфликт Security Manager: `Secure Connections Only` отключён,
  поскольку этот режим несовместим с `No Input / No Output`, `MITM=0` и
  стандартным Just Works. Поддержка Legacy Pairing остаётся скомпилированной
  выключенной, поэтому согласование по-прежнему выполняется через LE Secure
  Connections без возможности отката на Legacy Pairing.
