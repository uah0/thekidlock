# Облачный журнал и управление замком — проектирование 04.10.2026

Исходное состояние сохранено коммитом `85d24dc`. Проверочная сборка ESP32 10.0.328 и OTA прошли. Локальный HTTP API по указанию пользователя не защищаем и не меняем.

## Архитектура

Добавляем отдельный компонент приложения `cloud_link`, работающий с существующими `thingspeak_config`, очередью `lock_control`, BLE Central и Web UI. Сетевые операции не выполняются в BLE callback или задаче управления замком. OTA, Wi-Fi, сканер, служебный маяк, алгоритмы открытия и таймеров сохраняются. По умолчанию облачные функции выключены.

Используем три закрытых канала ThingSpeak:

1. Журнал: ESP пишет через HTTPS bulk API, read/write API keys задаются в существующей панели. Read key нужен для проверки доставки после неоднозначного сетевого сбоя.
2. Команды: ESP подписывается через MQTT TLS, публикующий клиент имеет отдельный write API key этого канала. ESP не получает права публикации команд.
3. Результаты: ESP публикует и подписывается через MQTT TLS. Подписка позволяет проверить, что результат действительно появился в облаке, а не только попал в исходящий буфер QoS 0.

MQTT Device создаётся отдельно для каждого замка: Client ID, Username, Password; разрешения только subscribe команд и publish/subscribe результатов. Пароль учётной записи MathWorks не используется. Все адреса фиксированы: HTTPS `api.thingspeak.com:443`, MQTT `mqtt3.thingspeak.com:8883`; стандартный ESP-IDF CA bundle и проверка имени сервера обязательны. Перехода на HTTP/1883 или отключения проверки сертификатов нет.

## События и время

Записываем защищённое подключение зарегистрированного телефона, запрос операции, изменения режима и фактического состояния ULP, ошибки и результаты облачных команд. MAC замка — Wi-Fi STA MAC ESP; MAC телефона — сохранённый BLE identity, а не меняющийся advertising address. Таймер имеет источник `timer`, локальные API — `local`, облако — `cloud` с заданной меткой оператора (это метка, не отдельная проверенная учётная запись).

У операции очередь хранит источник/инициатора. Фактические изменения связываем с текущей операцией; автоматическое закрытие переключает источник на `timer`. Подключения AUTO могут происходить часто, поэтому это отдельные события с ограниченной очередью; пропуски учитываются счётчиком.

SNTP запускается только после сетевой инициализации. Время события захватывается на ESP с микросекундным представлением UTC и монотонным uptime. Это разрешение записи, а не обещание микросекундной точности SNTP. До синхронизации событие того же запуска можно привязать к первой UTC-опоре. События предыдущего запуска без UTC остаются явно `unsynced`; время не выдумываем. SNTP сам по себе не аутентифицирован; счётчик команд обеспечивает защиту повторов независимо от него.

В ThingSpeak все `created_at` должны быть уникальными с шагом не менее секунды. Поэтому `created_at` используем как индекс доставки, а **точное время события хранится в field5**. Это позволяет сохранить несколько операций в одну секунду без потери времени. Поля: 1 MAC замка; 2 инициатор; 3 событие; 4 источник; 5 UTC микросекунды или `unsynced`; 6 уникальный ID события; 7 результат/состояние с fault flags/hold; 8 boot/uptime. Идентификаторы стабильны при повторной передаче. Интервал bulk-запросов и MQTT-публикаций результатов не менее 15 секунд.

События поступают неблокирующе в RAM-очередь, затем в ограниченный журнал из 32 записей во внутренней NVS. Сохранение происходит в отдельной задаче; резкое отключение питания может потерять ещё не сохранённую RAM-запись. При заполнении новые события отклоняются, старые неподтверждённые не удаляются; счётчик потерь виден в Web UI. После успешного HTTPS ответа либо сверки стабильных ID с закрытым каналом записи удаляются. Изменение канала при непустой очереди запрещено. Нет внешней памяти и неограниченного роста журнала.

## Формат и безопасность команды

JSON сообщения стандартной подписки `channels/N/subscribe`: field1 целевой MAC; field2 положительный возрастающий десятичный ID (до 2^53−1); field3 `open`, `close`, `hold_on`, `hold_off`; field4 срок действия UTC seconds; field5 время выдачи UTC seconds; field6 метка оператора (до 17 ASCII символов). Срок не более 60 секунд, будущее время выдачи допускается максимум на 5 секунд. Несовпадающий замок, неизвестная операция, несинхронизированное время, неверный формат, истёкшая команда, повторный ID или отказ NVS исключают выполнение.

Последний принятый ID и результат сохраняются **до** постановки физической операции в существующую очередь. После перезапуска незавершённая команда получает результат `interrupted` и автоматически повторно не выполняется. В любой момент допускается одна ожидающая команда. Повтор того же ID возвращает последний результат. Закрытие при активном hold возвращает `hold_conflict`; сначала нужен явный `hold_off`.

Открытие использует существующее ручное открытие на 10 секунд; закрытие и hold используют существующие функции. Подтверждение `ok` выдаётся только после свежего фактического состояния ULP без fault/close_rejected/calibration_required. Ожидание ограничено 5 секундами; результат `fault`/`timeout` не объявляет операцию успешной. По MQTT результаты: field1 ID; field2 результат; field3 фактическое состояние; field4 MAC; field5 UTC; field6 fault flags. QoS 0, retain=false, clean session=true; повтор результата до получения собственного подтверждения подпиской. Потерянная команда не считается выполненной: клиент ждёт результат и при необходимости повторяет тот же ID до expiry, не создаёт новый ID автоматически.

## Реализация и проверка

1. Дополнить конфигурацию и Web UI, журнал, время, происхождение событий; собрать и сразу OTA, проверить состояние.
2. Добавить TLS MQTT, строгий разбор/защиту повторов/фактическое подтверждение; проверить граничные и негативные случаи, собрать и сразу OTA.
3. Предоставить клиент управления через HTTPS API ThingSpeak без новых библиотек, инструкцию настройки трёх закрытых каналов. Реальную проверку облака выполнить после настройки каналов пользователем; без ключей не объявлять соединение с ThingSpeak проверенным. Android/BLE приложение в этой задаче не меняется.

Хранение облачных секретов остаётся существующей внутренней NVS. Secure Boot, flash encryption и сжигание eFuse относятся к отдельной подготовке production: необратимые операции здесь не выполняем. Полный производственный уровень защиты зависит также от удаления локального API, как запланировано пользователем.

Официальные источники: [MQTT](https://www.mathworks.com/help/thingspeak/mqtt-basics.html), [подписки](https://www.mathworks.com/help/thingspeak/subscribetoachannelfeed.html), [bulk JSON](https://www.mathworks.com/help/thingspeak/bulkwritejsondata.html), [ESP-IDF MQTT](https://docs.espressif.com/projects/esp-idf/en/v5.4.4/esp32s3/api-reference/protocols/mqtt.html).

## Уточнения итоговой реализации
После проектирования добавлены сверка частично доставленных записей по всем восьми полям, переменная длина blob журнала и отдельное сохранение счётчика потерь не чаще минуты для уменьшения износа NVS. До передачи освобождаются TLS-ресурсы перед разбором HTTPS JSON; сверка ограничена 32 последними записями. Команда имеет deadline в очереди lock_control, физическое подтверждение требует совпадения принятого ID и свежего feedback. Для hold подтверждается сохранение NVS. Проверки выполняются реальными C-функциями на RISC-V стенде и startup selftest ESP, без тестовой активации выхода замка.
