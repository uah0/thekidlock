# План перехода Android-приложения к единому BLE-соединению

## Цель

Перевести Android-приложение на промышленную архитектуру с одним владельцем BLE-соединения, сохранив автоматическое открытие, pairing, admin-панель, Wi-Fi/OTA и существующий BLE-протокол ESP32.

Пользователь не должен удалять кэш или данные приложения для восстановления работы Bluetooth.

## Зафиксированные проблемы

- `BleLockService` и `MainActivity` создают независимые `BleRepository`.
- Каждый репозиторий может выполнять собственный scan и `connectGatt()`.
- GATT read/write-операции не объединены в единую очередь.
- Вход в admin-панель останавливает сервис асинхронно и запускает второй BLE-сеанс.
- Верхний переключатель смешивает намерение пользователя с фактическим состоянием сервиса; `onResume()` принудительно включает его.
- При Bluetooth OFF/ON старый GATT-объект и scanner должны быть полностью заменены программно.

## Целевая архитектура

```
MainActivity (только UI)
        │ Binder/API и события
        ▼
BleLockService (единственный BLE-владелец)
        │
        ▼
BleRepository / BLE dispatcher
        │ один BluetoothGatt и одна очередь ATT
        ▼
ESP32 BLE Lock
```

## Этапы

### 1. Baseline и аудит

- проверить текущую структуру и рабочее состояние Git;
- зафиксировать все вызовы `connectGatt`, scan, GATT read/write и close;
- проверить Android-сборку и установленный APK;
- ESP32 собирает пользователь по принятому рабочему процессу;
- обновить `AUDIT.md`.

### 2. Единый BLE-владелец

- оставить `BleRepository` только внутри `BleLockService`;
- добавить локальный Binder/API для Activity;
- передавать события состояния, данных и ошибок в Activity;
- удалить создание второго repository из Activity;
- запретить Activity прямой доступ к Bluetooth API.

### 3. Очередь GATT-операций

- сериализовать connect, discovery, MTU, read, write и RSSI;
- запускать следующую операцию только после callback предыдущей;
- отменять устаревшие операции при disconnect и смене режима;
- добавить таймауты и единый результат операции.

### 4. Диспетчер режимов

Использовать взаимоисключающие режимы:

```
IDLE → AUTO_OPEN → ADMIN → OTA → AUTO_OPEN
```

- при входе в ADMIN автоматическое открытие ставится на паузу;
- при выходе из ADMIN возвращается AUTO_OPEN;
- OTA-команда блокирует конкурирующие BLE-команды;
- повторный запрос перехода не создаёт второй сеанс.

### 5. Надёжный Bluetooth OFF/ON

При `STATE_OFF`:

- остановить scan и RSSI;
- отменить очередь;
- disconnect и close старого GATT;
- сохранить pairing, MAC и настройки;
- перейти в `BLUETOOTH_OFF`.

При `STATE_ON`:

- пересоздать scanner и BLE-клиент;
- выполнить новый scan;
- подключиться к bonded-замку без повторного pairing;
- заново выполнить discovery и MTU;
- проверить защищённый доступ;
- вернуть AUTO_OPEN.

Повторные события ON должны быть безопасны. Использовать backoff и таймаут восстановления. Не удалять кэш, данные или pairing приложения.

### 6. Достоверное состояние UI

- переключатель показывает только разрешение пользователя на управление;
- отдельный статус показывает фактическое состояние сервиса;
- убрать принудительное включение в `onResume()`;
- кнопка «Сервис» открывает панель только после полного admin handshake;
- промежуточные состояния не показывать как окончательную ошибку.

### 7. Восстановление и защита от сбоев

Обработать GATT 133, 8, 19, Bluetooth OFF/ON, reboot ESP32, закрытие Activity, перезапуск процесса и очистку приложения системой. Восстановление должно быть идемпотентным: один сбой — одна последовательность cleanup/reconnect.

### 8. Тестирование и документация

Проверить:

- автоматическое открытие;
- вход в admin с первого нажатия;
- выход из admin и возврат AUTO_OPEN;
- Bluetooth OFF/ON;
- reboot ESP32;
- GATT 133/8;
- pairing и повторное подключение;
- OTA и повторную OTA;
- остановку и восстановление foreground-сервиса;
- работу без удаления данных приложения.

После каждого этапа обновлять `CHANGELOG.md` и `TEST_REPORT.md`.

## Ограничения

- не менять алгоритм открытия замка;
- не менять pairing-окно 60 секунд;
- не менять BLE UUID без необходимости;
- не удалять Wi-Fi, Web UI, OTA, scanner и поддержку маяков;
- не реализовывать собственную криптографию.

- Добавлена очередь GATT read/write и сериализация RSSI относительно ATT.
- Реализованы режимы `IDLE` / `AUTO_OPEN` / `ADMIN` / `OTA` и возврат в автоматический
  режим с немедленным `OPEN` при готовом GATT.
- Реализовано восстановление после Bluetooth OFF/ON без удаления данных,
  pairing и кеша приложения.
- Исправлены дублирование Activity, запуск admin из IDLE, выключение автоматики,
  задержка OPEN после выхода из admin и краш FGS при отсутствии разрешений.
- APK собирается и устанавливается; ESP32-сборку выполняет пользователь.
- Таймаут активной GATT read/write-операции 10 секунд добавлен.
- RSSI-опрос включён в общую очередь GATT; дублирующие admin-poll операции
  теперь отбрасываются.
- MTU-handshake защищён от повторного продвижения после нескольких callback.
- OTA выделен в отдельный режим с блокировкой автоматического реконнекта;
  после disconnect предусмотрен контролируемый возврат.
- Callback всех основных GATT-событий проверяет принадлежность текущему
  `BluetoothGatt`; события старого сеанса игнорируются.
- После GATT-ошибки флаг предыдущего `OPEN` сбрасывается, поэтому новый
  защищённый сеанс повторяет открытие сразу, без ожидания departure timeout.
- Завершение очереди использует единый результат операции:
  `SUCCESS`, `FAILED`, `TIMEOUT` или `CANCELLED`.
- После повторных GATT-сбоев реконнект использует ограниченный backoff
  3/6/12/24/30 секунд; после `READY` задержка сбрасывается.
- Перед повторным поиском после `ERROR` старый BLE-репозиторий закрывается,
  а новый создаётся заново, чтобы зависший GATT-сеанс не блокировал scan.
- Продолжение MTU-handshake и первое чтение `LOCK_INFO` сериализованы через
  главный handler приложения.
- В `AUTO_OPEN` чтение информационной характеристики не блокирует переход в
  `READY`; защищённая команда `OPEN` остаётся обязательной проверкой сеанса.
- После отказа MTU-handshake перед первым ATT-read выдерживается 500 мс.
- При явном входе в сервис запускается отдельный свежий GATT-сеанс в режиме
  `ADMIN`, даже если автоматический сеанс уже был готов.
- Сервисная панель получила отдельные действия «Закрыть настройки» и
  «Перезагрузить ESP32»; закрытие не вызывает перезагрузку.
- Следующий рабочий этап: полное физическое тестирование OFF/ON, reboot,
  admin, GATT 8/133 и OTA.
