# Контекст продолжения проекта BLE Lock

Дата фиксации: 18.08.2026

## Что делать при открытии нового сеанса

Продолжить переход Android-приложения к декларативной панели настроек, не
переписывая архитектуру и не удаляя существующие функции. Сначала прочитать:

- `AGENTS.md`;
- `AUDIT.md`;
- `BANK_GRADE_BLE_MIGRATION_PLAN.md`;
- `DECLARATIVE_UI_SPEC.md`;
- `CHANGELOG.md`;
- `TEST_REPORT.md`.

Пользователь собирает ESP32 самостоятельно. Прошивку без отдельной просьбы не
прошивать. Не менять алгоритм открытия, таймеры A/B, pairing-окно 60 секунд,
Wi-Fi, OTA, Web UI, BLE-маяки и scanner. Не использовать собственную
криптографию или собственный протокол шифрования.

## Текущий статус

План единого BLE-владельца и перехода к надёжности банковского уровня сохранён
в `BANK_GRADE_BLE_MIGRATION_PLAN.md`. В Android уже реализованы один
`BleLockService`/`BleRepository`, очередь GATT, режимы `AUTO_OPEN`, `ADMIN`,
`OTA`, восстановление Bluetooth OFF/ON, backoff и защита от устаревших callback.
Activity работает через Binder/`BleClient`, второй BLE-владелец не создаётся.

Android-сборка `:app:assembleDebug` ранее завершилась успешно. ESP32-сборка у
пользователя также завершилась успешно после настройки PowerShell; последний
успешный бинарник был создан до добавления характеристики декларативной схемы.

## Что уже изменено для декларативного UI

1. Добавлен контракт `DECLARATIVE_UI_SPEC.md`.
2. В `main/ble_phone.c` добавлена защищённая read-характеристика схемы настроек:

   `6f4f000e-9a7b-4c21-8d32-5e6f708192a3`

   Она имеет encrypted/read-only доступ и дополнительно проверяет bonded,
   encrypted и владельца admin-панели.
3. ESP32 формирует JSON со схемой существующих параметров замка: RSSI,
   длительное открытие, таймеры A/B, уровень открытия и GPIO.
4. В Android `BleProtocol.kt` добавлен `ADMIN_SCHEMA_UUID`.
5. Android пока не читает эту характеристику и не строит динамический экран.
   Старый статический экран должен оставаться fallback.

## Важное состояние сборки

Скрипт `tools/esp-idf-env.ps1` настраивает:

- `IDF_PATH`;
- `IDF_TOOLS_PATH`;
- `IDF_PYTHON_ENV_PATH`;
- `CC`, `CXX`, `ASM` полными путями;
- CMake, Ninja и Xtensa/RISC-V toolchain.

В новом PowerShell:

```powershell
. "F:\ble-lock-project\tools\esp-idf-env.ps1"
cd F:\ble-lock-project
idf.py build
```

Если появляется ошибка генератора CMake, старую папку `build` можно переименовать
в `build-nmake-backup`, затем повторить сборку. Не удалять пользовательские
исходники и не трогать pairing/NVS.

## Незавершённый этап

Этап 3 плана: проверить сборку ESP32 после добавления характеристики `000E`.
После успешной сборки обновить `CHANGELOG.md` и `TEST_REPORT.md`, затем перейти
к Android-модели/парсеру JSON и whitelist renderer.

Порядок дальнейшей реализации:

1. Получить от пользователя успешный результат `idf.py build` после текущего
   изменения `main/ble_phone.c`.
2. В Android добавить модель схемы, строгую валидацию версии/размера/types/ui_type
   и чтение `ADMIN_SCHEMA_UUID` через существующий единый BLE-владелец.
3. Реализовать renderer только для whitelist: `slider`, `switch`, `select`,
   `text`, `info`, `button`.
4. Сохранить старую статическую панель как обязательный fallback.
5. Не добавлять фрагментацию, пока схема не перестаёт помещаться в согласованный
   BLE read; если потребуется — сначала согласовать формат chunk header и лимит.
6. После каждого этапа собрать Android/ESP32, обновить `CHANGELOG.md` и
   `TEST_REPORT.md`, не переходить дальше при ошибке сборки.

## Последний диагностический эпизод

Проверки Python с `cmake` без кавычек дали `NameError: name 'cmake' is not
defined`; это не проверка WinError 5. Попытка создать временный тестовый файл в
`C:\Users\User\.codex\tmp` была заблокирована политикой среды агента. Проектные
файлы из-за этой попытки не изменялись.

## Правило продолжения

Новый агент должен считать этот файл актуальной точкой продолжения, не возвращаться
к старому phone-only плану из предыдущей версии `NEXT_AGENT.md` и не начинать
повторно уже выполненную миграцию единого BLE-соединения.
