# Декларативный интерфейс настроек BLE Lock

## Назначение

Экран настроек Android должен строиться по описанию, полученному от ESP32 по
защищённому BLE-соединению. Прошивка остаётся источником истины для доступных
параметров, диапазонов и прав записи. Текущий статический экран сохраняется как
резервный вариант при отсутствии схемы, ошибке передачи или несовместимой версии.

## Границы первого варианта

В первую версию входят только уже существующие настройки и действия:

- порог RSSI телефона;
- порог удержания RSSI;
- длительность длительного открытия;
- таймер A;
- таймер B;
- уровень открытия замка;
- GPIO замка (только при наличии права записи);
- Wi-Fi/OTA настройки;
- перезагрузка ESP32 и закрытие панели.

Алгоритм открытия, pairing-окно 60 секунд, BLE-маяки, OTA и Web UI этим
контрактом не меняются.

## Формат схемы

ESP32 будет отдавать UTF-8 JSON с верхним объектом:

```json
{
  "schema": 1,
  "revision": 1,
  "title": "Настройки замка",
  "sections": [
    {
      "id": "lock",
      "title": "Замок",
      "items": [
        {
          "id": "long_open_ms",
          "title": "Длительное открытие, мс",
          "type": "integer",
          "ui_type": "slider",
          "value": 10000,
          "min": 0,
          "max": 60000,
          "step": 1000,
          "unit": "мс",
          "read_only": false
        }
      ]
    }
  ]
}
```

Обязательные поля элемента: `id`, `title`, `type`, `ui_type`, `value`,
`read_only`. Для `slider` обязательны `min`, `max`, `step`; для `select` —
массив `options` с устойчивыми значениями. Android принимает только известные
типы и игнорирует неизвестные элементы, не выполняя код из JSON.

## Разрешённые элементы

| `ui_type` | `type` | Назначение |
|---|---|---|
| `slider` | `integer` | Значение в диапазоне с шагом |
| `switch` | `boolean` | Включение/выключение |
| `select` | `string`/`integer` | Выбор из whitelist ESP32 |
| `text` | `string` | Текстовое поле с ограничением длины |
| `info` | любой | Только отображение |
| `button` | `action` | Только известные действия, сопоставленные по `id` |

Произвольные URL, HTML, классы Android и обработчики из схемы запрещены.

## Версионирование и отказоустойчивость

- `schema` — версия формата, которую умеет разбирать приложение;
- `revision` — версия конкретного набора настроек;
- неизвестная версия или повреждённый JSON переводит приложение на статический
  экран и записывает диагностическую причину;
- схема не сохраняется как единственный источник UI в локальных данных;
- после перезапуска приложение повторно получает схему у ESP32;
- значения применяются только после успешного ответа ESP32 на всю операцию.

## Передача по BLE

Схема и запись параметров должны использовать существующую encrypted/admin
сессию. Если JSON не помещается в один ATT-пакет, передача выполняется
последовательными фрагментами с заголовком `schema`, `revision`, `index`,
`count`, `length` и контрольной суммой CRC-32. На Android обязательны общий
таймаут, проверка длины и ограничение максимального размера схемы.

Первый прототип допускает передачу всей схемы одним read, если она помещается в
согласованный размер. Фрагментация добавляется до расширения схемы и не должна
появляться скрыто в Android без поддержки ESP32.

Текущая реализация фрагментации использует запись `SCHEMA:<index>` в
существующую admin-характеристику управления. Ответ `ADMIN_SCHEMA_UUID` имеет
вид `key=value;...\n<base64>`, где `index` начинается с нуля, `count` задаёт число
фрагментов, а `length` и `crc32` относятся ко всему исходному UTF-8 JSON.

Схема может описывать OTA-раздел идентификаторами `ota_wifi_ssid`,
`ota_wifi_password`, `ota_firmware_url`, а также действиями `ota_read`,
`ota_save` и `ota_start`. Секретные значения в самой схеме не передаются:
фактические поля заполняются отдельным чтением существующей OTA-характеристики.

## Запись настроек

Android сначала собирает изменённые поля, затем отправляет одну операцию
сохранения через существующую admin-характеристику. ESP32 валидирует каждый
параметр повторно и сохраняет конфигурацию только после успешной проверки всего
набора. При ошибке показывается исходное состояние, а не предполагаемый новый
результат.

## Совместимость

До завершения физического тестирования декларативный экран не заменяет
статический полностью. При любом из условий ниже используется текущий экран:

- схема недоступна;
- admin-сессия не завершила handshake;
- JSON не прошёл whitelist/валидацию;
- `schema` не поддерживается приложением;
- запись параметров не подтверждена ESP32.

Копирование компонентов RainMaker целиком не требуется. Если позднее будет
заимствован исходный код Apache-2.0, авторство и лицензия будут добавлены в
`THIRD_PARTY_NOTICES.md`.
