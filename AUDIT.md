## BLE regression rollback 10.0.431 — 09.10.2026

Это изменение откатывает конкретную post-407 функциональную группу: Peripheral/GATT GAP/GATT service ради отображаемого имени `BLELock`, связанные NimBLE изменения имени и дополнительное снятие suppression при успешном восстановлении LTK. Пользователь подтвердил, что после установки 431 проблема восстановления pairing после reboot исчезла. Это runtime-подтверждение группы-регрессии; точная роль каждого подизменения внутри группы пока не отделена отдельным A/B тестом.

Сборка сохраняет production security profile, таблицу разделов и существующий SMP guard из build 406. Не меняются bonding/NVS API, параметры SMP, MTU/security sequencing, BLE тайм-ауты или алгоритм управления замком. Для точечной локализации нужен отдельный A/B тест подизменений; массовый reset или очистка данных не допускаются.

Дата: 08.10.2026  
Проект: ESP32-S3, ESP-IDF 5.4.4; Android: `android_lock_beacon`.

## Текущее состояние до изменения

- Телефон создаёт Android `LocalOnlyHotspot` при открытии локальных настроек.
- SSID и пароль точки доступа передаются в ESP по уже существующему зашифрованному BLE-сопряжению. ESP принимает настройки только при зашифрованном BLE-соединении с сохранённым сопряжением; пароль Wi-Fi в журналы не выводится.
- ESP подключается к точке доступа как Wi-Fi-клиент. Для этой процедуры не требуется новое сопряжение Wi-Fi.
- Локальный `POST /api/ota` в `components/ai_agent/ai_agent_ota.c` принимает образ известной длины, записывает его в следующий OTA-раздел через `esp_ota_write()`, завершает `esp_ota_end()` и только после успешной проверки выбирает раздел для загрузки.
- `esp_ota_end()` проверяет формат и целостность образа, но текущая конфигурация не требует подписи. Локальная передача идёт по HTTP и ограничена активной сессией точки доступа телефона.
- В `main/wifi_ota.c` также есть отдельное автоматическое HTTPS OTA-загружение из фиксированного GitHub Releases URL с проверкой сертификатов. Android пока не скачивает и не передаёт релиз через локальную сеть.
- Разметка 4 МиБ содержит два OTA-раздела по 0x1E0000 байт; раздела `factory` нет. Раздела эмуляции eFuse нет.
- Аппаратный Secure Boot, Flash Encryption и Anti-rollback в активной конфигурации выключены. Для ESP32-S3 Secure Boot V2 использует RSA-PSS; ECDSA для этой модели не поддерживается.
- В репозитории есть только Android development workflow; ESP32 release workflow и механизм подписи релиза отсутствуют.

## Целевое поведение

1. Android загружает только фиксированный образ из фиксированного репозитория GitHub по HTTPS с системной проверкой сертификатов.
2. Android отправляет образ в существующий локальный OTA endpoint через текущую точку доступа телефона.
3. ESP пишет данные только в неактивный OTA-раздел и вызывает штатную проверку подписи через API ESP-IDF до выбора нового раздела. Неподписанный, изменённый, неподходящий или устаревший образ не запускается.
4. Релиз подписывается RSA-PSS в CI закрытым ключом из секрета GitHub Actions; закрытый ключ не попадает в репозиторий и артефакты.
5. Отдельные профили разработки и выпуска позволяют проверить программную проверку подписей без прожига eFuse. Аппаратный Secure Boot, Flash Encryption в Release-режиме и отключение интерфейсов загрузки применяются лишь на тестовой плате и производственных устройствах после полного теста восстановления.

## Ограничения и открытые проверки

- Установка Secure Boot, Flash Encryption в Release-режиме и запрет ROM Download/JTAG могут необратимо изменить eFuse и ограничить восстановление. Не выполнять такие операции на текущем рабочем замке в ходе программной миграции.
- OTA API должен сохранять порядок `получение → запись в неактивный раздел → проверка esp_ota_end → выбор раздела → перезагрузка`; не добавлять обходной маршрут, который выбирает раздел до проверки.
- Защита подписью обеспечивает подлинность и целостность образа даже при HTTP в изолированной точке доступа. HTTPS локального канала остаётся отдельным усилением конфиденциальности и требует закрепления доверенного сертификата; оно не заменяет подпись.
- Anti-rollback `secure_version` должен повышаться только при отзыве уязвимых поколений. Его нельзя приравнивать к обычному номеру сборки.
- Не отправлять образ больше размера OTA-раздела и не держать лишнюю копию полного образа в оперативной памяти.

## Диагностика незапуска новой подписанной OTA-сборки — 08.10.2026

- Текущая ESP опрошена по device-agent: `10.0.384`, boot id `0e9670c104ba44e3` до пробы, `LOCKED`, ULP calibration valid, `fault_flags=0`, `calibration_required=false`.
- После отправки валидного образа наблюдалась перезагрузка (boot id сменился на `a97c23d5895bc431`), однако первой доступной версия была снова `10.0.384`; 10.0.388 не появилась в `/api/agent/info` ни в одной точке 2-секундного наблюдения (`artifacts/ota-boot-observation-20261008.txt`).
- Журнал текущего запуска показывает `wifi_ota ... auto_update=0`, поэтому старый firmware не был повторно загружен автоматическим GitHub OTA. ULP и замок после возврата исправны.
- Ранее полный образ с модифицированным байтом payload был отклонён на `esp_ota_end()` как `ESP_ERR_OTA_VALIDATE_FAILED`, без смены версии и без перезагрузки. Значит проверка подписи OTA работает.
- Ограничение диагностики: HTTP API показывает состояние уже работающего приложения, но не выдаёт сообщения ROM/bootloader при выборе раздела. На компьютере не обнаружено ни COM-порта, ни присутствующего USB-устройства ESP/USB-UART; поэтому нельзя по сетевому логу отличить отклонение кандидата загрузчиком от очень раннего сбоя приложения с последующим возвратом к 10.0.384.
- Текущий код не изменялся в рамках этой диагностики. Для окончательного вывода нужен UART лог через USB-UART/serial консоль во время одного OTA перезапуска, включая сообщения выбора OTA-раздела, проверку Secure Boot и состояние rollback. Не прожигать eFuse и не загружать Release-профиль до получения этого лога.

## Результат OTA-теста и промежуточное исправление HTTPD стека — 08.10.2026

Телефонный debug-клиент скачал файл с локального сервера (`GET 200`, 1,445,888 байт), а ESP дошла до `Signature verified successfully!`. Затем работающая 10.0.384 падала в `vTaskSwitchContext` с `LoadProhibited` до подтверждения HTTP-ответа; device-agent передача завершилась таймаутом 120 с. Поскольку в старом образе HTTPD stack size был 6144 байта, в сборке 10.0.390 он увеличен до 12 КиБ как проверочная гипотеза на исчерпание стека во время `esp_ota_end` RSA-PSS. OTA-установка 390 на старую 384 снова упала в старом обработчике; поэтому 390 загружена по USB COM7. Сейчас подтверждены `firmware_version=10.0.390`, `state=LOCKED`, `fault_flags=0`, `stack_http_bytes=10016`. Причина паники пока не доказана, а новый OTA-приёмник ещё не проверен OTA-передачей.

## Подготовка совместимого OTA-релиза — 09.10.2026

- Базовая сборка signed-dev успешна: 10.0.392, 1445888 байт. RSA-PSS подпись проверена espsecure публичным ключом, извлечённым из существующего локального ключа. Закрытый ключ не публикуется.
- Таблица остаётся на 0x8000; nvs 0x9000/0x6000, otadata 0xF000/0x2000, ota_0 0x20000/0x1E0000, ota_1 0x200000/0x1E0000. OTA передаёт только приложение, не загрузчик и не таблицу.
- Для текущей линии программной проверки подписи допустим signed-dev с прежним ключом. Он не включает аппаратный Secure Boot или Flash Encryption и не заменяет аппаратную защиту. Для устройств с иными ключами/eFuse совместимость не подтверждена. Предыдущая проверка 10.0.390 на текущем замке зафиксирована выше.

# Этап BLE rollback 430 — 09.10.2026

Контрольная гипотеза: перестановка MTU/security между рабочей сборкой 406 и бинарником 426 могла влиять на ранний disconnect. Изменён только порядок: security инициируется на CONNECT, как в коде 406. Диагностика 426 не доказывает причинность; окончательный вывод требует одинаковой процедуры reboot/reconnect и runtime trace. Device Name, pairing guard, BLE security parameters, timeout, таблица разделов, NVS и eFuse не менялись. Build 430 подписан Secure Boot V2 и зашифрован для OTA.

Попытка установки остановлена до OTA: Android не смог удержать GATT после открытия Web UI (connect/disconnect до чтения Wi-Fi credentials, bondState=12). Firmware cache телефона заменён на зашифрованный 430 и проверен по SHA-256; исходный 426 сохранён локально для восстановления. Для продолжения требуется восстановить штатный GATT-сеанс; pairing/NVS/reset действия автоматически не предпринимались.
