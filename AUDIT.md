# Аудит проекта TheKidLock

## Кратковременный замер GPIO7 при постоянном HIGH MOSFET — 30.09.2026

- В штатном `LOCKED` цикле ULP оставляет GPIO9 HIGH, но считывает только
  батарейный ADC GPIO5; `sense_raw` GPIO7 в этом режиме оставался старым.
- Добавлена отдельная Agent-команда `ulp_gate_test`: только из `OPEN_HOLD`
  ULP удерживает GPIO9 HIGH до 5 секунд, каждые 40 мс считывает ADC1_CH6/GPIO7
  и публикует `sense_raw`. После лимита ULP сам выключает GPIO9 и возвращается
  в `OPEN_HOLD`; отдельная stop-команда выключает его немедленно.
- Команда не меняет классификацию пластины или алгоритм закрытия. Во время
  теста UI состояния ULP показывает отдельный FSM `GATE_TEST`, а закрытие и
  повторная калибровка не используются для принудительного включения затвора.
- Диагностический вариант сохраняет первое raw-чтение GPIO7 в `baseline_raw`,
  усредняет восемь последующих чтений в `sense_raw` с паузой 100 мкс, а
  `delta_raw` показывает их разницу. На build 237 во время FSM `GATE_TEST`
  первое чтение было 56–63, среднее последующих — 22–34 raw. Стабильный
  низкий результат после серии чтений не объясняется только недостаточным
  временем установления между выборками.

## Android: закрытие при выходе из Always Open — 28.09.2026

- При снятии Always Open главный экран посылал `MODE_AUTO`. ESP обработчик
  `LOCK_EVENT_SET_AUTO` восстанавливает measurement поверх прежнего OPEN запроса,
  поэтому это не давало немедленного закрытия.
- Android теперь выбирает существующую BLE-команду `AUTO_OFF_CLOSE` для выхода
  из Always Open. Она явно очищает режим удержания и запрашивает закрытие;
  обычные переходы `MODE_AUTO` не затронуты.
- При сбросе самой кнопки Always Open приложение ещё и сохраняет AUTO service
  выключенным, чтобы телефон рядом не открыл замок снова. Кнопка AUTO выполняет
  выход из hold с закрытием, затем отдельно возобновляет автооткрытие.
- Устройство подтвердило Always Open (`OPEN_HOLD`), затем `AUTO_OFF_CLOSE` и
  `LOCKED`. При следующем включении AUTO обнаружен старый native presence
  latch; код очищает его после подтверждённого закрытия. Build 107 собран и
  установлен. На build 107 завершён полный прогон AUTO (`OPEN`) → Always Open
  (`OPEN_HOLD`) → сброс (`LOCKED`) → AUTO (`OPEN`) → AUTO off (`LOCKED`);
  в конечном состоянии при RSSI `-38 dBm` замок оставался `LOCKED`,
  `hold_open=false`.

## Android: активное сканирование без timeout между попытками — 28.09.2026

- Baseline и итоговый `build-android.ps1` прошли. Старый callback scanner
  `LOW_LATENCY` завершал discovery через 15 секунд, а сервис затем мог ждать
  backoff до 30 секунд; это создавало интервалы без запроса сканирования.
- Таймаут пустого discovery снят. После исправления APK собран и установлен
  после восстановления ADB-соединения. Ориентация `0/0` после установки
  восстановлена и проверена.
- Проверка на Xiaomi показала, что app scan callbacks продолжаются более 15 с
  при включённом экране, но `BtGatt.ScanManager` затем приостанавливает scanner
  `com.blelock.app` в screen-off режиме (duration 8396 мс, `scanModeUsed=0`),
  хотя сервис остаётся foreground. Следовательно, бесконечная регистрация
  устраняет паузы приложения, но не может отменить screen-off throttling MIUI.

## Настраиваемая выдержка выхода из BLE-зоны — 27.09.2026

- До изменения ESP использовала `BLE_ZONE_EXIT_GRACE_MS=1500` внутри RSSI-задачи
  `ble_phone.c`: при сигнале ниже единого `phone_rssi_threshold` соединение
  разрывалось после непрерывной выдержки. В Web UI `/api/config` поля не было.
- Web UI получает и сохраняет конфигурацию через `config_get/config_post` в
  `web_ui.c`; активная BLE-задача уже регулярно получает `app_config_t`, поэтому
  новое значение может применяться без перезапуска BLE и без изменения GATT.
- Добавляется отдельное поле NVS `zone_exit_ms` (внешнее имя API/UI
  `zone_exit_grace_ms`), диапазон 0…10000 мс,
  default 1500 мс. Значение 0 означает разрыв при первой RSSI-проверке ниже
  порога. BLE admin CSV и его число полей остаются без изменений.
- Старые HTTP POST без нового query-параметра сохраняют текущее значение;
  штатный Web UI отправляет поле вместе с остальными настройками.

## Один RSSI-порог зоны в ESP32, без phone-side hysteresis — 27.09.2026

- Baseline перед изменениями прошёл: Android `build-android.ps1` — PASS;
  ESP-IDF `build-esp32.ps1 -Action build` — PASS.
- В прошивке сейчас четыре RSSI-параметра: `phone_rssi_threshold`,
  `phone_rssi_hold_threshold`, `ble_connect_rssi_threshold` и
  `ble_disconnect_rssi_threshold`. Они присутствуют в NVS config, HTTP
  `/api/config`, Web UI и BLE admin config/schema. Задача оставляет один
  ESP-порог — `phone_rssi_threshold` — как предел зоны открытия/ухода.
  PHY/contact thresholds, timers и BLE TX power к RSSI proximity thresholds
  не относятся и сохраняются.
- `ble_phone.c` отдельно фильтрует гостей слабее порога 1.5 секунды, а затем
  применяет ещё один BLE link connect/disconnect порог с 6-секундной задержкой.
  Новая схема применяет оставшийся zone threshold к любому соединению; устойчивый
  сигнал ниже него заканчивает соединение, а уход вызывает штатную агрегацию
  `lock_control_report_disconnected()`. Команда `OPEN` ниже порога немедленно
  завершает соединение и не вооружает отложенное открытие. Обычный `MODE_AUTO`
  тоже больше не открывает замок по одному RSSI без команды `OPEN`; независимая
  явно вызванная `ARM_OPEN` команда остается для существующего AI-адаптера.
- Android имеет два независимых понятия: filtered PendingIntent advert threshold
  (`rssiThreshold`) для более сильного порога подключения сохраняется; второй
  slider и активная GATT hysteresis (6 секунд ниже вычисленного порога)
  удаляются. ESP остаётся единственным владельцем disconnect/zone-exit решения.
- BLE admin config уже используется как CSV с фиксированным количеством полей;
  чтобы не менять wire framing, legacy позиция hold threshold сохраняется как
  совместимое поле-заполнитель, равное основному threshold. ESP больше не хранит,
  не применяет и не показывает это отдельное значение. BLE schema и Android
  admin UI показывают только один порог. HTTP config/Web UI тоже убирают
  устаревшие RSSI поля, оставляя остальные параметры.

## Отключение сканирования ухода и режима «долго открыт» — 27.09.2026

- Baseline до изменений: `build-android.ps1` — PASS (`assembleDebug`),
  `build-esp32.ps1 -Action build` — PASS (ESP-IDF 5.4.4).
- Android: единственный запуск `BleRepository.waitForDeparture()` находится
  в `BleLockService.onBleState(IDLE)` после отправки OPEN. Он включает отдельный
  callback-скан. Для выключения этой функции после чистого отключения замка
  приложение должно снять `openSentForPresence` и повторно зарегистрировать
  существующий filtered PendingIntent scan; его порог подключения служит
  повторным условием допуска и не допускает цикла активных сканов.
- ESP32: режим «долго открыт» реализован дедлайном `long_open_deadline_ms` в
  `lock_control.c`; его истечение закрывает замок и устанавливает
  `reopen_blocked`. Таймер А и отдельная 10-секундная команда тестового
  открытия раньше использовали один дедлайн. Чтобы тестовый OPEN сохранил срок,
  его проверка выделяется отдельно; только обычная проверка дедлайна режима
  «долго открыт» отключается compile-time флагом. Настройки и таймер А не меняются.

## Отключение импульсной проверки зазора в режиме «Постоянно открыт» — 26.09.2026

- `lock_control.c` сохраняет `hold_open` в NVS, но при загрузке преобразует его
  в обычную команду `ULP_CMD_OPEN`; при включении/выключении режима также
  передаётся только OPEN/CLOSE. ULP не различает постоянное открытие и обычное
  временно открытое состояние.
- Активный профиль ULP имеет период 40 мс. Для `ULP_CMD_UNLOCK`, когда замок не
  заперт, `run_iteration()` вызывает `measure_plate()`. Она поднимает GPIO9 на
  2 мс для считывания дельты — около 25 импульсных проверок в секунду.
- При постоянном открытии gate должен оставаться LOW, и ULP не должна выполнять
  импульсную проверку. Остальные режимы и критическая проверка снятия тока при
  физическом открытии должны сохраниться.
- Минимальное разделение: передавать отдельную `ULP_CMD_HOLD_OPEN`, включая
  восстановление режима из NVS; для неё ULP пропускает `measure_plate()`. При
  выключении постоянного открытия возвращается обычная `ULP_CMD_OPEN`. Переход
  из фактически LOCKED в HOLD_OPEN выполняет current-off safety check без
  последующего импульсного замера зазора.
- Baseline `build-esp32.ps1` — PASS. Сразу после сборки baseline-прошивка
  передана текущему замку через `device-agent.ps1 flash`; устройство вернулось,
  версия изменилась `10.0.188` → `10.0.189`. До изменений замок был в `OPEN_HOLD`.
- После реализации `build-esp32.ps1` — PASS; OTA завершён, замок вернулся в
  сохранённый `OPEN_HOLD` на `10.0.190`. Две ULP-выборки с интервалом 3 с дали
  `measurement_counter=1`, `pulse_actual_us=0`, FSM `OPEN_HOLD`, faults=0.

## Фоновое обнаружение замка в Android — 26.09.2026

- Android targetSdk=36, minSdk=26; `BleLockService` объявлен как
  `connectedDevice` foreground service, BootReceiver уже восстанавливает AUTO.
- Текущий AUTO вызывает `BleRepository.findAndConnect()`: отфильтрованный UUID
  callback scan работает в LOW_LATENCY 15 секунд, затем сервис применяет
  экспоненциальную задержку до 30 секунд. Это создаёт слепые окна при отсутствии
  замка.
- UUID `6f4f0001-9a7b-4c21-8d32-5e6f708192a3` присутствует в рекламе ESP32
  (`main/ble_phone.c`, `fields.uuids128`), поэтому фильтр по Service UUID
  подходит и не требует ослабления.
- Существующие pairing/authentication, `openNow()`, защита
  `openSentForPresence` и `waitForDeparture()` остаются в `BleRepository` /
  `BleLockService`; active scan в ADMIN и отдельный departure scan имеют иные
  назначения и должны быть проверены отдельно.
- В Android-модуле до этой задачи нет unit-тестов. Нужны тесты для чистой логики
  фильтрации результата и однократного захвата события; аппаратное поведение
  PendingIntent после process death проверяется отдельно на телефоне.
- Официальное руководство Android подтверждает PendingIntent scan как способ
  пробуждения процесса после завершения и рекомендует его вместо периодических
  сканов. Для target API 31+ запуск FGS из фонового события ограничен; поэтому
  сервис AUTO уже запущен как `connectedDevice` при включении режима, но в
  ожидании будет использовать только низкоэнергетический PendingIntent scan.

## Завершение выключения AUTO при открытой двери — 25.09.2026

- Приложение повторяло `AUTO_OFF_CLOSE` до статуса `LOCKED`; при открытой двери
  статус оставался `OPEN`, BLE переходил между `READY` и `OPEN_SENT`, а кнопки

  AUTO завершается. Физическое подтверждение закрытия фиксируется отдельно.

## Лишнее условие повторного закрытия и нетогглируемые кнопки — 24.09.2026

### ULP

- В нормальной ветке CLOSE `retry_contact_streak` безусловно сбрасывается в 0
  перед проверкой контакта, поэтому при уже прижатой пластине каждый цикл
  достигает только 1 из 5 и закрытие невозможно.
- Само требование пяти измерений было добавлено агентом и не входило в заданный
  пользователем автомат. Оно удаляется.
- При CONTACT ULP должен немедленно выполнить штатную последовательность
  300/100/2 мс. После отклонённой попытки новая попытка также разрешается при
  первом CONTACT. GAP_1 запускает притяжку, но по действующему требованию не
  может напрямую разрешить постоянное удержание.

### Android

- `toggleAutomaticMode()` содержит ранний выход при подтверждённом AUTO, а
  `toggleKeepOpenMode()` — при подтверждённом ALWAYS_OPEN. Повторное нажатие
  поэтому ничего не делает.
- AUTO должен повторным нажатием выключать телефонную автоматику через
  существующий `setAutomaticMode(false)` / `AUTO_OFF_CLOSE` и снимать цвет по
  фактическому broadcast сервиса.
- ALWAYS_OPEN должен повторным нажатием посылать `MODE_AUTO`. После ответа
  кнопка ALWAYS снимается; AUTO подсвечивается только если телефонная
  автоматика действительно активна.

### Итоговый аудит исправлений

- В ULP больше нет `retry_contact_streak` и дополнительных серий. В нормальном
  CLOSE состояния CONTACT и GAP_1 немедленно вызывают `close_after_plate()`;
  при защёлке отказа повтор разрешает первый CONTACT. Требование FAR отсутствует.
- `close_after_plate()` по-прежнему не разрешает удержание попытке, начавшейся
  с GAP_1; постоянный HIGH возможен только у повторной попытки от CONTACT и при
  горячей классификации CONTACT. Алгоритмы открытия и таймеров не изменены.
- Повторное нажатие активного AUTO больше не имеет раннего выхода: отключается
  настройка и вызывается штатный `setAutomaticMode(false)`.
- Повторное нажатие активного ALWAYS_OPEN вычисляет
  `requestedAlwaysOpen=false` и посылает `MODE_AUTO`.
- AUTO окрашивается только при `automaticModeActive`, подтверждённом broadcast
  сервиса, и при отсутствии `OPEN_HOLD`; ALWAYS окрашивается по подтверждённому
  `LOCK_STATUS=OPEN_HOLD`. Во время команды обе кнопки заблокированы.


## Единая 17%-граница повторного закрытия — 24.09.2026

- По решению пользователя состояние без зазора определяется единой холодной
  границей `contact + 17% * (paper1 - contact)`; для текущей калибровки это
  `203 + floor(138 * 17 / 100) = 226 RAW`.
- Требуются пять последовательных значений `delta_raw <= contact_max`.
- Попытка, начавшаяся с GAP_1, выполняет притяжку и диагностику, но не может
  непосредственно включить постоянное удержание. После неё ULP ждёт серию
  холодных CONTACT и только затем выполняет новую попытку.
- Горячая проверка повторной попытки классифицируется через существующую
  компенсацию и ту же 17%-границу. Это принимает реальный полный контакт
  392 RAW (скорректированный 192 RAW) при границе 226 RAW.

## Повторное ожидание полного контакта после отказа — 24.09.2026

- Текущий `close_reject_latched` снимается только после состояния `FAR`.
  Поэтому после обнаружения одного или двух листов ULP требует сначала открыть
  дверь и не может закрыться, если зазор устранён без отвода пластины далеко.
- После отказа силовой импульс нельзя автоматически повторять при GAP_1/GAP_2:
  это создало бы бесконечную пульсацию MOSFET на неизменном зазоре.
- Безопасный автомат сохраняет защёлку и звуковую индикацию при любом зазоре,
  продолжает короткие диагностические измерения и снимает защёлку только при
  `PLATE_CONTACT`. В тот же цикл запускается новая штатная проверка 300/100/2 мс.
- Если новая проверка снова не подтверждает горячий контакт, защёлка снова
  устанавливается. Число таких переходов не ограничивается.
- Аппаратная проверка первой реализации показала 14 повторных попыток за 13 с:
  при листе шум холодного ADC иногда на один отсчёт попадал в `CONTACT`.
  Поэтому повтор разрешается только после пяти последовательных `CONTACT`;
  любой GAP немедленно обнуляет серию. Это не удлиняет 100-мс паузу финальной
  проверки, а фильтрует состояние до начала силового импульса.
- Build 161 показал, что пять подряд значений внутри широкой 17%-границы всё же
  могут накопиться через лист; на 24-й попытке горячий шум дал 402 RAW и попал
  в окно 402…404. Поэтому повторное разрешение теперь требует пяти холодных
  значений в том же строгом симметричном допуске ±1% непосредственно вокруг
  `calibration_contact_raw`, а не просто класса `PLATE_CONTACT`.

## Ложное закрытие через один лист: несопоставимый горячий эталон — 24.09.2026

- На build 157 один лист стабильно измерен как 349–351 RAW, то есть точно
  соответствует сохранённой точке `paper1=350`.
- Реальная цепочка закрытия после 300 мс и 100 мс получила 339 RAW и ошибочно
  приняла это значение за контакт, поскольку мастер сохранил горячий эталон
  `405 RAW` и границу `410 RAW`.
- ULP-цикл отдельного горячего измерения совпадает с реальным по длительностям,
  но Web-мастер запускает его пять раз подряд и сохраняет медиану. Реальная
  попытка выполняет только один такой цикл. Накопленное состояние катушки и
  измерительного тракта делает сохранённую медиану несопоставимой с одиночной
  попыткой.
- Горячий эталон необходимо получать одним циклом после уже выполненной
  пятисекундной проверки стабильности полного контакта.
- Дополнительно подтверждено, что `lock_control` публикует логическое LOCKED
  сразу после передачи CLOSE, до подтверждения `LOCK_STATE_LOCKED` от ULP.
  Это не вызвало ложный HIGH, но создаёт неверные журналы и статус.
- Повторная калибровка одним циклом дала hot-contact=403 RAW, а реальные
  проверки через лист — 399 и 367 RAW. Одностороннее условие
  `verify <= hot_contact + tolerance` принимает любое уменьшение сигнала как
  улучшение контакта. Это неверно для переходного процесса после силового
  импульса. Безопасное условие должно проверять абсолютное отклонение от
  горячего эталона с обеих сторон.
- Для финального допуска выбран ±1% холодного интервала contact…paper1.
  При текущих 203/341 это ±1 RAW: значения 399 и 367 отклоняются относительно
  эталона 403. Неуверенное измерение всегда оставляет MOSFET выключенным.

## Ложный контакт с одним листом и гонка Android-режимов — 24.09.2026

- Аппаратная попытка с листом дала горячий `close_verify_delta_raw=403`.
  Горячий эталон контакта равен `391`, но текущая компенсация переносит
  на горячую проверку 17% холодного интерва `contact…paper1`: допуск около 24
  raw, то есть границу около `415`. Поэтому raw 403 ложно классифицируется
  как отсутствие зазора.
- Для финального решения о постоянном HIGH нужен отдельный более
  строгий горячий порог: `hot_contact + 4% * (paper1 - contact)`. На текущей
  калибровке это около `396`, поэтому raw 403 должен отклонять закрытие.
- Android-log зафиксировал гонку `MODE_ALWAYS → AUTO_OFF_CLOSE → MODE_ALWAYS`.
  Причина: кнопки трактуются как независимые toggle, а старый
  `lastWorkingModeAlwaysOpen` обновляется только после асинхронного чтения status.
- Кнопки должны стать взаимоисключающим выбором `AUTO/ALWAYS_OPEN`,
  блокировать повторную команду до `LOCK_STATUS` и окрашиваться по
  подтверждённому `OPEN_HOLD`, а не по состоянию Android-сервиса.

## Закрытие по одному листу и имя bond — 24.09.2026

### Автомат ULP

- Текущая цепочка `close_after_plate()` уже выполняет 300 мс
  с открытым GPIO9, затем `measure_plate()` закрывает GPIO9 на 100 мс
  и выполняет 2-мс диагностический импульс.
- Постоянный HIGH разрешается только при `verify_state == PLATE_CONTACT`;
  эта часть уже совпадает с заданным алгоритмом.
- Ошибка — попытка притяжки разрешена для `CONTACT`, `GAP_1` и `GAP_2`.
  Новое условие — только `CONTACT` или `GAP_1`.

### Калибровка

- Мастер сейчас требует четыре холодные точки: 1 лист, 2 листа,
  открыто и контакт, плюс горячий эталон контакта.
- Из мастера удаляется этап двух листов. Для совместимости с
  текущей шкалой зазоров служебная точка `paper2` вычисляется как
  `paper1 + (paper1 - contact)`. Калибровка валидна, если расчётная точка
  остаётся ниже точки открытой двери.

### Имя телефона

- ESP32 сохраняет имя только по записи Android в `PHONE_NAME_UUID`.
  Web UI корректно отдаёт NVS-имя, но показывает «имя не сохранено»,
  когда такой записи не было.
- После pairing ESP планирует reboot через 1 с, а Android пи обычном
  handshake автоматически имя не записывает. Нужно записывать имя
  после первого чтения `LOCK_STATUS` и дать этой операции время до reboot.

## Синхронизация рабочего режима Android/ESP32 и NVS — 24.09.2026

### ESP32

- `s_hold_open` и локальный `hold_open` хранят режим только в RAM;
  `lock_control_init()` безусловно сбрасывает его в `false` и посылает
  ULP команду `CLOSE`.
- По требованию режим `ALWAYS_OPEN` должен храниться в отдельном NVS-
  пространстве. `MODE_ALWAYS`, `MODE_AUTO`, `KEEP_OPEN` и
  `AUTO_OFF_CLOSE` должны обновлять один и тот же NVS-флаг.
- При старте ULP получает `OPEN`, если в NVS сохранён
  `ALWAYS_OPEN`; при отсутствии/ошибке ключа безопасный режим по
  умолчанию — `AUTO`/`CLOSE`.

### Android

- `BleLockService` публикует фактический флаг через `EXTRA_AUTOMATIC_MODE`,
  но `MainActivity` его игнорирует и перерисовывает кнопку по
  `settings.autoOpenEnabled`.
- Включение автоматики сразу посылает `OPEN`, но не `MODE_AUTO`;
  поэтому ESP может остаться в `OPEN_HOLD`.
- При выборе автоматики нужна цепочка `MODE_AUTO` → чтение
  `LOCK_STATUS` → обычная команда `OPEN`. Кнопка не должна показывать
  автоматику, если подтверждён `OPEN_HOLD`.

## Обновление GPIO5 при закрытом замке — 24.09.2026

- В ветке `LOCK_STATE_LOCKED` ULP не вызывает `measure_plate()`, поэтому
  `vbat_raw` не обновляется до следующего открытия/диагностики.
- Замер аккумулятора в `LOCKED` должен читать только ADC1_CH4 и не
  вызывать `gate_low()`, `gate_high()` или `measure_plate()`. Это сохраняет
  GPIO9 постоянно высоким и не создаёт паузу тока соленоида.
- Публикация `vbat_raw` должна оставаться под seqlock, чтобы главное ядро
  не получало разорванный снимок.

## Напряжение аккумулятора GPIO5 в Web UI — 24.09.2026

- ULP уже измеряет GPIO5 / ADC1_CH4 с `ADC_ATTEN_DB_12` и публикует
  сырой код `vbat_raw`; повторно захватывать ADC главным ядром не нужно.
- Исходная аппаратная документация в истории проекта фиксирует делитель
  150 кОм / 27 кОм. Напряжение аккумулятора равно напряжению на
  ADC, умноженному на `(150 + 27) / 27`.
- Для перевода raw в милливольты нужно использовать штатную eFuse-калибровку
  ESP-IDF (`adc_cali`, curve fitting), а не номинальную шкалу 0–4095.
- `/api/ulp` должен сохранить `vbat_raw` для диагностики и добавить
  `battery_mv`; Web UI показывает его в вольтах с двумя знаками.

## Динамическая граница «зазора нет» — 24.09.2026

- Прежний `CONTACT_MAX=10500` ставил границу ровно на 50% интервала между
  калибровками полного контакта и одного листа. При точках `212/355` это давало
  raw-границу около `284`, тогда как физический тест дал `236`.
- Граница задаётся единой константой 17% интервала. В нормированной шкале это
  `6000 + (15000-6000)*17/100 = 7530`; благодаря линейной интерполяции ULP она
  автоматически адаптируется к каждой новой паре contact/paper1.
- `/api/ulp` дополнительно публикует процент и рассчитанную raw-границу для
  контроля в Web UI. Остальные границы зазоров не изменяются.

## Пороги положения пластины в Web UI — 24.09.2026

- Мастер сохраняет пять raw-точек в NVS/ULP: полный контакт, один лист, два

## Исправление управления зарегистрированными телефонами — 24.09.2026

### Решение

- Web API уже разрешает удалять отдельный bond без аппаратного configuration
  mode. Для единого и понятного поведения такое же ограничение снимается с
  удаления всех bonds; кнопка больше не приводит к скрытому HTTP 500.
- Перед удалением определяется, совпадает ли identity удаляемого bond с
  активным BLE peer. Такая сессия немедленно помечается как неавторизованная и
  завершается стандартной командой GAP terminate. При удалении всех bonds
  завершается любое активное соединение.
- `ble_phone_get_bonds()` уже возвращает сохранённое имя. Web JSON дополняется
  полем `name`, причём значение экранируется как JSON-строка и контролируется
  граница выходного буфера. Буфер 4096 байт размещается в heap, чтобы массив
  bonds и полный JSON не переполняли стек HTTP-задачи. Web-таблица получает
  отдельную колонку имени.

### Границы изменения

- Открытие 60-секундного окна, pairing, owner и алгоритмы замка не меняются.
- API остаётся рассчитанным на доверенную LAN в соответствии с действующим
  тестовым режимом проекта.

## Аудит блока «Регистрация телефонов» — 24.09.2026

### Текущая архитектура

- Web UI использует `GET/POST /api/ble/registration` для 60-секундного окна и
  `GET/DELETE /api/ble/bonds` для списка и удаления bonds.
- Открытие окна отключает текущее BLE-соединение, снимает accept-list и даёт
  новому телефону единственный слот соединения. Известные bonded-телефоны на
  время окна намеренно отклоняются.
- Новый peer допускается только в открытом окне, должен завершить encrypted +
  bonded соединение и появиться в NimBLE store. После успеха окно закрывается,
  первый bond становится owner, затем выполняется программный reboot.
- Лимит хранилища согласован: `BLE_PHONE_MAX_BONDS`, `MAX_BONDED_PHONES` и
  `CONFIG_BT_NIMBLE_MAX_BONDS` равны 20. Аппаратный accept-list равен 15.

### Обнаруженные проблемы

- В `ble_phone_start_advertising()` проверка превышения 15 элементов выполняется
  до чтения фактического `bond_count`, когда он ещё равен нулю. Заявленный в
  комментарии fallback для bonds 16–20 недостижим: последующий
  `ble_phone_refresh_accept_list(true)` возвращает ошибку. При 16–20 bonds
  штатная реклама после закрытия окна может не запуститься.
- Удаление всех bonds разрешено только в аппаратном configuration mode, а
  удаление одного bond такого ограничения не имеет. Web UI не показывает это
  различие: кнопка «Удалить все» доступна всегда и получает HTTP 500 вне синего
  режима.
- Удаление активного bond не разрывает уже установленное encrypted-соединение;
  удалённый телефон может пользоваться текущей сессией до её завершения.
- В структуре bond хранится имя телефона, BLE admin его показывает, но Web API
  отдаёт только адрес и тип. Web-таблица поэтому не показывает доступное имя.
- В текущем тестовом режиме Web Agent/API не имеет аутентификации; открытие окна
  и удаление отдельного bond доступны любому участнику доверенной LAN. Это
  соответствует временному решению пользователя, но неприемлемо для внешнего
  доступа.

### Что работает корректно

- Окно имеет монотонный deadline, отображает оставшееся время и закрывается
  после первого успешного bond.
- Неизвестный телефон вне окна отклоняется до pairing, переполнение 20 bonds
  проверяется, повторный pairing существующего identity отклоняется.
- Команды замка проверяют одновременно encrypted и bonded состояние.
- Имена и owner удаляются вместе с соответствующим bond; удаление всех bonds
  очищает owner и имеет отдельную LED-индикацию.

Изменения логики регистрации в этом этапе не выполняются: пользователь запросил
аудит. Исправления перечисленных проблем следует делать отдельным этапом.

## Удаление аппаратных настроек и секунды «Долго открыт» — 24.09.2026

- GPIO9 и активная полярность уже аппаратно закреплены в ULP; поля
  `lock_gpio/lock_open_level` не управляют ULP и создают ложное впечатление
  изменяемой схемы.
- Для полного удаления необходимо убрать поля из `app_config`, NVS write/read,
  HTTP JSON/POST, Web HTML/JS, BLE admin payload/schema и Android static/dynamic
  панели, а также удалить неиспользуемый `lock_control_set_gpio()`.
- «Долго открыт» сейчас имеет три представления: миллисекунды в firmware/Web/BLE
  schema и минуты в legacy Android UI. Единый внешний контракт становится
  секундами (`long_open_s`, диапазон 1…3600); умножение на 1000 остаётся только
  в расчёте deadline автомата.
- Старое NVS `long_open_ms` однократно читается как fallback и округляется вверх
  до секунд. При следующем сохранении старые ключи таймера и удалённых аппаратных
  полей стираются.

## Ошибка сохранения «Долго открыт» — 23.09.2026

- Удалённый монитор зафиксировал корректный запрос `long=15100 A=700`, после
  которого `app_config_set_logic()` вернул `ESP_ERR_NVS_KEY_TOO_LONG`.
- Значение таймера проходит все ограничения; ошибка возникает раньше commit при
  записи ключей `ble_connect_rssi` и `ble_disconnect_rssi`.
- ESP-IDF NVS допускает имя ключа максимум 15 символов. Оба имени длиннее лимита,
  поэтому общий запрос сохранения падал независимо от изменённого поля.
- Ключи сокращаются до `ble_conn_rssi` и `ble_disc_rssi`. Старые длинные ключи
  физически не могли быть созданы NVS, поэтому миграция данных не требуется.

## Событийные ULP-логи — 23.09.2026

- Старое условие печатает три длинные строки при любом изменении
  `gate_high_counter/gate_low_counter`. Диагностические импульсы меняют эти
  счётчики постоянно даже без изменения состояния замка, создавая около 7–8
  КиБ/с и вытесняя 32-КиБ удалённый журнал за несколько секунд.
- В обычном режиме логируются только изменения команды/ack, состояния замка и
  FSM, классификации пластины, ошибок/событий, калибровки, попыток/отказов
  закрытия и наложений команд.
- Значения ADC, GPIO9 и все счётчики импульсов по-прежнему входят в снимок при
  таком событии, но сами по себе не запускают новую запись.
- Временный verbose-режим возвращает прежнее условие по фронтам GPIO9. Он
  управляется Agent API и намеренно сбрасывается после перезагрузки.

## Удалённый аналог UART monitor — 23.09.2026

- Существующий `event_log` хранит только 32 строки по 96 байт и получает лишь
  явные вызовы `event_log_add()`. Системные Wi-Fi, NimBLE и остальные `ESP_LOGx`
  в него не попадают; длинные строки обрезаются.
- Для полного прикладного журнала используется стандартный ESP-IDF hook
  `esp_log_set_vprintf()`. Обёртка сохраняет вывод в кольцевой буфер внутренней
  RAM и вызывает прежний sink, поэтому UART продолжает работать без изменения.
- Буфер 32 КиБ не использует Flash, NVS или внешнюю SPI RAM. После reset журнал
  очищается; при переполнении старейшие байты вытесняются.
- HTTP endpoint отдаёт `text/plain` порциями с абсолютным курсором и признаком
  потери старых данных.
- Перехват устанавливается в начале `app_main()`. ROM, bootloader и ранние строки
  до входа в приложение технически недоступны прикладному hook.

## Стабильный Wi-Fi после программного reset и OTA — 23.09.2026

- Аппаратная проверка build 121 показала: HTTP restart и OTA вызывают reset, но
  Web API не возвращается даже за 60–120 секунд; физический Reset после этого
  сразу восстанавливает подключение к той же сохранённой сети.
- `connect_wifi()` запускает STA один раз и ждёт IP 30 секунд. Обработчик
  `WIFI_EVENT_STA_DISCONNECTED` только очищает флаг, но не вызывает
  `esp_wifi_connect()`. После первой неудачи `web_task` завершается без повторов.
- Все программные пути (`Web restart`, завершение HTTP OTA и BLE reboot) вызывают
  `esp_restart()` без предварительного отключения STA.
- Добавляется флаг разрешённого автоматического переподключения. Он активен во
  время штатной работы Web UI; при непреднамеренном разрыве обработчик повторно
  вызывает `esp_wifi_connect()`.
- Перед намеренной сменой сети или reset флаг снимается, выполняются
  `esp_wifi_disconnect()` и `esp_wifi_stop()`. HTTP-сервер не останавливается из
  собственного обработчика OTA, чтобы исключить взаимную блокировку.

## Приоритет домашней Wi-Fi сети над точкой телефона — 23.09.2026

- При автоматическом подключении ESP32 запускает фоновую задачу и публикует
  состояние `CONNECTING_WEB` до получения IP домашней сети.
- Android при запросе страницы настроек считает любой статус без
  `WEB_READY;IP=` отсутствием сети, сразу создаёт LocalOnlyHotspot и передаёт его
  временные реквизиты по BLE.
- `wifi_ota_set_runtime_config()` безусловно останавливает текущее подключение и
  заменяет рабочие реквизиты временными. Поэтому точка телефона выигрывает гонку
  у уже запущенного подключения к домашней сети.
- Android должен продолжать опрос при `CONNECTING_WEB`, не создавая hotspot.
- ESP32 дополнительно должна отклонять временные BLE-реквизиты, если включено
  автоподключение, сохранены домашние реквизиты и попытка ещё не завершилась
  `ERROR_WIFI`. После реальной ошибки домашней сети аварийный hotspot разрешён.

## Сохранение автоподключения к домашней Wi-Fi сети — 23.09.2026

- HTTP-флаг `auto_connect` сам по себе записывается в NVS корректно, однако
  сохранение SSID и пароля без отдельного OTA URL отклоняется общей функцией
  `wifi_ota_set_config()`.
- Для обычного подключения к домашней сети OTA URL не требуется. Его обязательная
  проверка связывает две независимые возможности и не позволяет сохранить сетевые
  реквизиты при пустом поле URL.
- Поле URL должно принимать пустое значение либо корректный `https://` адрес.
  Запуск исходящего HTTPS OTA по-прежнему требует непустой URL.
- Кнопка сохранения Wi-Fi должна также записывать текущее состояние переключателя
  автоподключения, чтобы пользовательская операция была единой и воспроизводимой.

## Полный локальный тестовый доступ и OTA по Wi-Fi — 23.09.2026

- Пользователь явно переводит Agent API в режим обкатки без аутентификации и
  прикладных ограничений команд в доверенной локальной сети.
- Агенту предоставляются команды автомата, прямые команды ULP LOCK/UNLOCK,
  тестовые шаблоны бипера, перезапуск и существующий OTA endpoint.
- Проектный клиент должен загружать `build/ble_lock_stage1_s3.bin` через HTTP OTA,
  ждать перезагрузки и проверять новую версию без открытия COM-порта.
- Для первой Wi-Fi-прошивки клиент допускает явно заданный адрес устройства со
  старой прошивкой, где ещё отсутствует `/api/agent/info`, проверяя `/api/status`.
- Прямую запись GPIO9 из главного ядра не добавляем: GPIO9 принадлежит ULP, а два
  независимых владельца сделали бы диагностику недостоверной. Полный контроль
  силового выхода обеспечивается прямыми командами ULP и его автоматом.
- Режим намеренно рассчитан только на доверенную LAN. Перед внешним доступом
  потребуются аутентификация, права и ограничение опасных операций.

## Локальный интерфейс диагностики для Codex — 23.09.2026

- Существующий Web UI уже автоматически подключается к сохранённой Wi-Fi сети и
  публикует подробные `/api/status` и `/api/ulp`, поэтому новый транспорт или
  облачный сервер для локальной диагностики не требуется.
- Для воспроизводимой работы агента не хватает идентификации возможностей,
  HTTP-доступа к кольцевому журналу и единой точки высокоуровневых команд.
- Добавляется API версии 1: `/api/agent/info`, `/api/agent/events` и
  `/api/agent/command`. Разрешены только существующие команды автомата:
  `open`, `close`, `auto`, `always_open`; прямого управления GPIO нет.
- Проектный PowerShell-клиент объединяет status/ULP/events в полный снимок,
  поддерживает наблюдение и сохраняет последний адрес устройства локально.
- На первом этапе обнаружение проверяет только адреса из ARP-кэша компьютера;
  произвольного сканирования всей локальной сети клиент не выполняет.
- API использует существующую модель доверенной локальной сети Web UI. До доступа
  из других сетей необходимо добавить индивидуальную аутентификацию устройства.

## Звуковой признак наложения событий — 23.09.2026

- Переключение в ALWAYS_OPEN после неудачной проверки отправляет UNLOCK и снимает
  ULP-защёлку. Существующая задача бипера просто прекращает серию, поэтому по звуку
  невозможно отличить штатную отмену от наложения управляющих событий.
- Наложением считается новая команда ULP, когда предыдущая ещё не подтверждена,
  либо когда активна защёлка неудачного закрытия. Отдельный монотонный счётчик
  сохраняет факт наложения независимо от последующего состояния LOCK/UNLOCK.
- Задача бипера отслеживает этот счётчик. Аварийный шаблон имеет приоритет над
  обычным кодом зазора: тире 600 мс, затем три точки по 150 мс.
- Если наложение возникает во время обычной серии, серия прерывается и немедленно
  заменяется аварийным шаблоном. Следующее наложение создаёт новое звуковое событие.
- Переключения GPIO8 логируются с заданным и прочитанным уровнем, чтобы отделить
  ошибку программной последовательности от электрической неисправности бипера.

## Защёлка неудачного закрытия и строгий контакт — 23.09.2026

- Аппаратный лог build 111 показал: первая проверка с одним листом корректно дала
  `GAP_1` (`raw=564`, `adjusted=385`) и увеличила `reject`, но уже на следующем
  цикле ULP повторно включил катушку. Изменившийся после двух силовых циклов отклик
  (`raw=335`, `adjusted=156`) был принят за `CONTACT`, после чего GPIO9 остался HIGH.
- Бипер опрашивает состояние асинхронно и не обязан успеть за короткое окно между
  первым отказом и ошибочным `LOCKED`. Поэтому счётчик отказов без защёлки не
  обеспечивает сигнализацию.
- Исправление: любой результат `GAP_1` и больше после контрольного импульса
  защёлкивает отказ. Пока пластина не была достоверно удалена (`FAR`), новые
  300-мс попытки запрещены. Защёлка напрямую управляет звуковой сигнализацией.
- После `FAR` контроллер только перевооружается; притягивание возможно в одном из
  следующих циклов при новом приближении пластины. Команда UNLOCK также снимает
  защёлку.
- Граница строгого контакта переносится в середину между эталонами «контакт» и
  «один лист»: feature `10500` вместо `12000`. Это симметричная граница ближайшего
  эталона и уменьшает вероятность принятия части листового зазора за контакт.
- Пауза контрольной проверки остаётся ровно 100 мс. В состоянии `LOCKED` ULP не
  вызывает `measure_plate()`: GPIO9 удерживается HIGH без диагностических импульсов.

## Наблюдаемость классификации зазора — 23.09.2026

- Текущая UART-строка показывает `delta`, итоговый `feature` и числовые состояния,
  но не выводит сохранённые точки калибровки, горячее смещение и фактически
  классифицируемый после компенсации `delta`.
- Из-за этого по одному логу нельзя отличить неверную калибровку от ошибки
  компенсации или неверного порога `CONTACT/GAP_1`.
- Все нужные исходные значения уже находятся в общей памяти ULP; для диагностики
  не требуется менять алгоритм измерения или добавлять переменные в RTC memory.
- Решение: расширить атомарный диагностический снимок существующими пятью
  калибровочными точками, а на основном ядре вычислять и печатать горячее смещение,
  компенсированный `delta`, текстовые имена состояний и полный набор feature-порогов.
- Диагностические данные также публикуются через `/api/ulp`, чтобы UART и Web API
  показывали одну и ту же картину.

## Отдельный горячий эталон контрольного контакта — 23.09.2026

- В calibration mode добавлен запрашиваемый цикл, идентичный штатной проверке:
  300 мс питания, 100 мс разряда и диагностический импульс 2 мс.
- Мастер собирает пять таких значений при полном контакте, проверяет
  стабильность и сохраняет медиану `verify_contact_raw` вместе с четырьмя
  холодными точками. Старые записи без нового ключа считаются невалидными.
- При штатной проверке вычисляется сдвиг между горячим и холодным контактом.
  Он вычитается из `verify_delta`, после чего применяется четырёхточечная шкала.
  Это сохраняет строгий `CONTACT` и позволяет звуковому коду отражать реальный
  GAP, не расширяя границу контакта.
- Для контрольной классификации используется прямой классификатор без FAR-
  гистерезиса предыдущего холодного измерения.

## Почему полный контакт после притяжения определяется как GAP_1 — 23.09.2026

### Наблюдение на устройстве

- Загруженная build 103 подтверждена COM-журналом.
- До длительного включения физический контакт даёт `delta=268–296`,
  `feature=9952–11655` и классифицируется как `CONTACT`.
- После 300 мс непрерывного питания, отключения и 100-мс паузы тот же
  физический контакт стабильно даёт `verify_delta=390–393`,
  `feature=18478–18652` и классифицируется как `GAP_1`.
- Ошибок ADC нет (`faults=0`), calibration mode выключен, результат повторяем.
  Следовательно, проблема не является шумом, потерей NVS или неверным порядком
  четырёх точек.

### Причина

- Мастер записывает четыре эталона в обычном режиме коротких 2-мс импульсов.
- Контрольный замер выполняется после другого режима: 300 мс непрерывного тока.
  После него изменено состояние катушки, магнитопровода, повышающего
  преобразователя и измерительной цепи.
- Пауза 100 мс убрала грубый выброс (`delta` снизился с 1300–1437 до 390–393),
  но не вернула характеристику к холодному эталону контакта 268–296.
- `calibrated_feature()` не знает контекст измерения и пропускает горячий
  `verify_delta` через холодную шкалу `contact/paper1/paper2/open`. Поэтому
  физический полный контакт закономерно попадает в `GAP_1`.

### Дополнительные факторы

- GPIO5 измеряет аккумулятор, а не 12-В выход преобразователя. Прошивка не
  видит возможное восстановление/просадку 12-В шины после 300 мс нагрузки и не
  может нормализовать контрольный импульс по фактическому напряжению катушки.
- Увеличивать паузу без измерений нельзя: это может дать электрическое
  восстановление, но одновременно позволяет пластине механически отойти.
- Изменение границы `CONTACT_MAX` замаскирует расхождение и ухудшит различение
  реального одного листа; это не исправление причины.

### Необходимое исправление

- Калибровать контроль полного контакта в том же цикле, в котором он затем
  проверяется: 300 мс включения → отключение → выбранная пауза → 2-мс импульс.
- Хранить отдельный эталон `verify_contact_raw` и отдельный допуск для
  контрольного замера. Четыре холодные точки продолжить использовать только
  для ожидания и определения расстояния до первоначального притяжения.
- Мастер должен дополнительно автоматически выполнить несколько циклов
  притяжения при плотно прижатой двери, получить устойчивую медиану
  `verify_contact_raw` и сохранить её в NVS.

## Строгий контакт и звуковой код отказа — 23.09.2026

- По уточнённому требованию `GAP_1` после контрольного импульса не является
  успешным закрытием: постоянный HIGH разрешён только для `CONTACT`.
- GPIO8 уже выделен активному низким уровнем биперу и не используется ULP;
  звуковая индикация безопасно реализуется отдельной задачей основного CPU по
  диагностическому снимку ULP, без вмешательства в силовую FSM.
- После `close_reject_counter > 0` повторяется серия: 1…5 сигналов для
  `GAP_1`…`GAP_5`, 6 для `FAR/UNKNOWN`. Сигнал прекращается при `LOCKED`,
  `UNLOCK` или calibration mode.

## Критерий близости после отпускания магнита — 23.09.2026

- Build 103 подтвердил, что 100-мс пауза устраняет переходный процесс:
  `verify_delta` стабилен на 391–393 вместо 1300–1437.
- За время паузы пластина механически переходит из `CONTACT` в `GAP_1`, поэтому
  требование только `CONTACT` отклоняет каждую исправную попытку.
- Повторная проверка теперь принимает `CONTACT` или `GAP_1`, то есть близость
  не хуже одного листа. `GAP_2` остаётся допустим только для начала притяжения
  и не разрешает постоянное удержание после отпускания.

## Остаточный переходный процесс после притяжения — 23.09.2026

- Аппаратный лог build 102 подтвердил рабочую четырёхточечную шкалу до
  притяжения: `delta=320–435` классифицируется как `GAP_1/GAP_2`.
- После 300 мс включения даже при 10-мс off-guard повторный замер имеет
  `delta=1300–1437` и насыщает шкалу как `FAR`; каждая попытка отклоняется.
- К следующему циклу измерение возвращается в обычный диапазон, поэтому для
  повторной проверки выбран консервативный отдельный off-guard 100 мс.
- Порог, длительность импульса, четыре калибровочные точки и требование
  `CONTACT` для постоянного удержания не меняются.

## Восстановление четырёхточечной калибровки — 23.09.2026

- В старом PoC сохранены отдельные состояния `CONTACT`, `GAP_1`, `GAP_2` и
  инструкция собирать данные для контакта, одного и двух листов.
- Трёхточечная калибровка не имела эталона двух листов и интерполировала его
  на длинном участке до открытой двери.
- Новый контракт использует строгий порядок raw-значений: контакт < один лист
  < два листа < открытая дверь. Старые трёхточечные данные NVS намеренно не
  считаются валидными до повторного прохождения мастера.
- Первичное притяжение разрешается до `GAP_2`; после 300 мс питание снимается,
  выдерживается полный 10-мс off-guard и выполняется штатный 2-мс импульс.
  Постоянный HIGH разрешается только если повторный замер показывает `CONTACT`.

## Диагностика пульсации GPIO9 — 23.09.2026

- Существующий COM-журнал показывает только логическое решение основного CPU
  о закрытии и не доказывает переход ULP в `LOCKED`.
- Для различения диагностических импульсов, повторных попыток и постоянного
  удержания нужны программный уровень GPIO9 и счётчики фактических переходов
  LOW→HIGH/HIGH→LOW непосредственно в ULP.
- Диагностический снимок должен также содержать команду, calibration mode,
  `lock_state`, `fsm_state`, положение пластины, faults, ADC delta, число
  попыток/отказов и результат повторной проверки.
- Печать выполняется основным CPU только при изменении счётчиков переходов;
  алгоритм управления соленоидом и временные интервалы ULP не меняются.

## Преждевременные переходы голосового мастера — 23.09.2026

- Отсчёт 20 замеров запускался одновременно с длинной голосовой репликой.
  К её завершению пятисекундное окно уже было заполнено, поэтому этап
  мог переключиться до выполнения инструкции.
- Сбор данных должен быть приостановлен на всё время озвучивания и запущен
  только из `SpeechSynthesisUtterance.onend/onerror`. Повтор реплики обнуляет окно.
- Аудит удержания: успешная вторая проверка вызывает `gate_high()`, после
  чего в ветви `LOCK_STATE_LOCKED` ULP не переключает GPIO9. Программно это
  постоянный HIGH, а не PWM; слабое удержание требует замера GPIO9 и 12-В
  шины под реальной нагрузкой.

## Отдельный голосовой мастер калибровки — 23.09.2026

- Мастер вынесен из основного `index.html` в отдельный embedded-ресурс
  `web/calibration.html`, доступный по `/calibration` и открываемый кнопкой
  из настроек в отдельном окне.
- Сценарий: один лист бумаги и плотно прижатая дверь; открытая дверь
  без бумаги; плотно прижатая дверь без бумаги.
- Каждый этап завершается автоматически после 20 уникальных стабильных
  замеров с интервалом 250 мс, то есть примерно за 5 секунд непрерывной
  стабильности. При движении скользящее окно заполняется заново.
- Переходы дополнительно проверяют `contact < paper < open`; инструкции и
  ошибки озвучиваются штатным Web Speech API. Кнопка повтора остаётся доступной.
- Закрытие/отмена окна выключает ULP calibration mode; при успехе он
  выключается backend-ом после NVS commit.

## Восстановление калибровки магнитной системы — 22.09.2026

- В Git-истории найден эталонный мастер: полный контакт, открытая дверь,
  один лист бумаги. Ранний UI был только mockup без ESP32 backend.
- Теперь мастер рабочий: в режиме калибровки ULP игнорирует CLOSE,
  держит GPIO9 в LOW и выполняет только 2-мс измерительные импульсы.
- Web UI сохраняет медиану последних десяти `delta_raw` для трёх точек.
  Сервер принимает только порядок `contact < paper < open` и сохраняет точки в NVS.
- ULP кусочно-линейно преобразует `delta_raw` между тремя эталонами в
  прежнюю шкалу `feature`, поэтому восстановлены `CONTACT…FAR` и старые пороги.
- GPIO5 по-прежнему измеряется, но не формирует fault и не участвует в
  расчёте положения. Без валидной NVS-калибровки ULP не разрешает закрытие.

## Двухэтапное подтверждение закрытия ULP — 22.09.2026

- До изменения ULP ожидал допустимое положение пластины и включал
  магнит на 300 мс, но после этого не снимал питание и не выполнял
  новый замер. Поля `close_verify_*` копировали данные до притяжения.
- Требуемая последовательность: периодически ждать пластину; при допустимом
  зазоре притянуть 300 мс; отключить; после короткой паузы повторно
  измерить; и только после подтверждения включить магнит постоянно.
- В коде уже есть неиспользуемый `close_verify_mode` и пауза 500 мкс;
  они предназначены именно для повторного замера до отпускания пластины.
- При неуспешной повторной проверке MOSFET остаётся в LOW, а ULP
  возвращается к ожиданию. При ADC/fault аварийное состояние не должно
  подменяться обычным `CLOSE_REJECTED`.

## Временное исключение GPIO5 из решения о закрытии — 22.09.2026

- Новая схема подаёт на неизменённый делитель GPIO5 напряжение одной
  Li-ion ячейки 3,0–4,2 В вместо прежних 12 В; соленоид по-прежнему
  питается от стабилизированных 12 В после повышающего преобразователя.
- Текущее деление `delta_raw` на `vbat_raw` больше не отражает напряжение
  катушки и ложно сдвигает классификацию пластины.
- Для аппаратной проверки вводится явный временный флаг: GPIO5
  измеряется и публикуется, но не формирует fault и не участвует в
  решении о закрытии.
- Пока флаг включён, любой подтверждённый отклик GPIO7 с `delta_raw >= 40`
  временно считается `PLATE_CONTACT`. Это отключает защиту по зазору
  и допустимо только для краткого контролируемого теста.

## Новая разводка MOSFET и бипера — 22.09.2026

- До изменения GPIO8 жёстко закреплён за ULP RISC-V как выход
  затвора MOSFET: он задан в `APP_LOCK_GPIO`, `LOCK_GATE_GPIO` и
  трёх прямых вызовах RTC GPIO в ULP-программе.
- Новая аппаратная разводка требует GPIO9 для MOSFET и GPIO8 для

- Алгоритм ULP, таймеры замка и логика открытия не меняются;

- Звуковые сценарии в текущей архитектуре отсутствуют, поэтому GPIO8
  нужно инициализировать в неактивном `HIGH`, не возвращая

- Для исключения звука до инициализации GPIO на плате нужен
  внешний pull-up входа бипера; прошивка не может задать уровень
  во время reset/ROM boot.

## Issue #4: разделение постоянной и временной Wi-Fi-конфигурации — 22.08.2026

## Аудит кнопки «Сохранить Wi-Fi/OTA» — 22.08.2026

Проверены два независимых пользовательских маршрута с одинаковым названием.

### Web UI в Chrome

- Кнопка вызывает JavaScript `saveWifi()` и отправляет `POST /api/wifi` с
  `ssid`, `password` и `url`.
- `wifi_post()` формирует `SSID\npassword\nHTTPS_URL` и вызывает постоянное
  сохранение `wifi_ota_set_config()` в NVS.
- При HTTP 200 страница показывает «Сохранено»; запрос Chrome не появляется в
  BLE-логе Android-приложения.
- Неизменённые SSID/URL с пустым паролем возвращают `unchanged=true`, сохраняя
  прежний пароль.

Недостатки Web-маршрута:

- `wifi_post()` не логирует вход и успешный HTTP 200; по журналу телефона
  невозможно доказать нажатие кнопки.
- Query-буфер ограничен 420 байтами, хотя URL-кодирование допустимых значений
  может увеличить запрос сильнее и вызвать HTTP 400 до сохранения.
- SSID и URL вставляются в JSON без escaping; специальные символы могут
  сделать ответ `/api/wifi` невалидным.

### Android/BLE

- Кнопки вызывают `saveOtaConfig()` и передают `SSID\npassword\nHTTPS_URL`
  через `OTA_CONFIG_UUID`.
- ESP32 направляет запись в `wifi_ota_set_runtime_config()`, а не в
  `wifi_ota_set_config()`.
- Runtime-функция предназначена для временной LocalOnlyHotspot-сети, ожидает
  только `SSID\npassword`, не сохраняет NVS и запускает Web UI. Постоянное
  сохранение Android поэтому несовместимо с ESP32: payload отклоняется по
  длине либо URL становится частью неверного Wi-Fi-пароля.
- Callback Android для любой записи сообщает «Временные настройки точки
  доступа переданы», даже для кнопки постоянного сохранения. Проверки чтением
  сохранённой конфигурации нет.

### Вывод

Web-кнопка привязана к правильному backend постоянного сохранения, но результат
проверяется ответом страницы или serial-логом ESP32, не BLE-логом телефона.
Android-кнопка постоянного сохранения функционально неверна из-за объединения
постоянной и временной конфигурации в одной характеристике без различимого
формата. Исправление должно сохранить runtime hotspot-путь и явно разделить
два назначения.

## Issue #4 — режимы Android и автоматический вход в Web UI (22.08.2026)

### Runtime-аудит гонки hotspot/BLE (22.08.2026)

- На физическом телефоне подтверждён сценарий: hotspot успешно создаётся,
  после чего BLE-запись завершается локальной ошибкой «Сначала подключитесь к
  зарегистрированному замку».
- Причина: `MainActivity.onLockData()` вызывал `resumeAutomaticMode()` для
  каждого статуса, отличного от `OPEN_HOLD`. Во время Web UI это переводило
  единый `BleLockService` из `ADMIN` в `AUTO` непосредственно перед передачей
  runtime Wi-Fi credentials.
- `pendingHotspotWifi` очищался до подтверждения ATT-записи, поэтому гонка
  превращала временный разрыв в безвозвратную потерю payload.
- Исправление должно разрешать AUTO-resume только как завершение явного выбора
  пользователем режима `AUTO`, а credentials сохранять до успешного callback и
  повторять после восстановления `READY`.

### Уже существующие механизмы

- `BleLockService` остаётся единственным владельцем фонового BLE-сеанса, а
  `MainActivity` использует его через `BleClient`.
- ESP32 допускает команды замка только через encrypted/bonded BLE; доступ к
  административным характеристикам дополнительно сверяется с owner address.
- `CHR_LOCK_STATUS` уже возвращает `OPEN_HOLD`, `OPEN` или `LOCKED`, поэтому
  фактический взаимоисключающий режим можно восстановить после reconnect.
- `wifi_ota_set_runtime_config()` уже принимает временные `SSID/password`, не
  записывает их в NVS, подключает ESP32 как STA, запускает локальный Web UI и
  публикует `WEB_READY;IP=...` через защищённую BLE-характеристику статуса.
- Android уже использует `LocalOnlyHotspot`, передаёт runtime credentials по
  BLE, опрашивает статус ESP32 и открывает полученный локальный URL.

### Выявленные пробелы относительно Issue #4

- главное окно построено из switch и пары небольших ручных кнопок, а не из
  трёх крупных полноширинных кнопок режимов;
- `KEEP_OPEN` является toggle-командой: повтор или потерянный ответ способны
  рассинхронизировать Android и ESP32; нужна идемпотентная установка `AUTO` и
  `ALWAYS_OPEN`;
- Android `autoOpenEnabled` управляет foreground service локально, но отдельной
  команды установки рабочего режима ESP32 нет;
- сценарий hotspot управляется набором boolean-флагов и не имеет единого
  перечисления состояний, отображаемого на сервисной кнопке;
- отсутствуют измерение полного времени успешного цикла и сохранённая оценка
  начального countdown;
- текущий экран выводит пароль hotspot пользователю и пишет SSID в журнал;
  для полностью автоматического сценария это не требуется и увеличивает
  поверхность раскрытия credentials.

### Точки безопасной интеграции

- сохранить существующие UUID и добавить идемпотентные команды в
  `CHR_LOCK_COMMAND`, не создавая собственного шифрования или нового BLE
  протокола;
- расширить `lock_control` операцией явной установки hold-open, не меняя
  алгоритмы таймеров А/Б и открытия по RSSI;
- сохранить существующий runtime Wi-Fi/Web UI путь, обернув его на Android в
  явную state machine и countdown;
- использовать `CHR_LOCK_STATUS` как источник фактического режима после

## Быстрое открытие и индикация автомата замка — 22.07.2026

- Текущий Android-сервис отправляет `OPEN` после discovery и чтений
  `LOCK_INFO/LOCK_STATUS`. ESP32 отклоняет запись, если RSSI ещё не измерен или
  ниже порога; сервис после отказа начинает новый цикл подключения. Это может
  задержать открытие на секунды и пропустить момент пересечения порога.
- Существующий `lock_control` уже поддерживает `open_armed`: после принятой
  команды последующий `RSSI_HIGH` открывает замок. Требуется отдельное событие
  ARM, которое устанавливает этот флаг без преждевременного открытия.
- BLE-команда `OPEN` должна приниматься для encrypted + bonded телефона при
  любом текущем RSSI: при достаточном RSSI открывать сразу, иначе вооружать
  автомат. Проверка порога и физическое решение остаются на ESP32.
- Период ESP32 RSSI task равен 500 мс. Уменьшение до 100 мс сокращает
  программную задержку после пересечения порога, не меняя значения и семантику
  таймеров А/«Долго открыт».
- Для уже bonded-телефона фоновому Android-сервису не нужны UI-чтения INFO,
  STATUS и ADMIN_STATE перед OPEN. Control-only путь может перейти в READY
  сразу после service discovery; регистрационный Activity-путь сохраняется.
- LED уже получает состояния от `lock_control`, но blocked окрашен фиолетовым,
  а режим настройки перекрывает базовое состояние синим. Требуется жёлтый для
  `LOCKED_BLOCKED` и постоянный приоритет состояния замка; синий остаётся
  только для OTA.
- Целевая индикация: `LOCKED` — красный, `UNLOCKED` — зелёный,
  `LOCKED_BLOCKED` — жёлтый. Снятие блокировки возвращает красный.
- Алгоритмы таймера А, «Долго открыт», гистерезиса и трёх слабых RSSI для снятия
  защиты не изменяются.

## Имена телефонов, привязанные к bonds — 22.07.2026

- Текущая идентификация телефона выполняется стандартным NimBLE store по

  изменять не требуется.
- Стандартное bond-хранилище NimBLE не содержит пользовательского имени
  Android-телефона. Получение имени непосредственно из SMP bonding также не
  предусмотрено используемым стандартным GAP/SMP потоком.
- Для имени требуется отдельная метаданная во внутренней NVS. Ключ формируется
  из типа и identity MAC, поэтому имя не участвует в авторизации и не заменяет
  MAC-привязку.
- Android передаёт локальное Bluetooth-имя после того, как соединение стало
  encrypted + bonded. Новая GATT-характеристика доступна только для
  зашифрованной записи, а обработчик дополнительно проверяет bonded-состояние.
- ESP32 сохраняет первое непустое имя для MAC и не перезаписывает его при
  последующих соединениях. Таким образом фиксируется имя на момент первой
  регистрации обновлённым протоколом.
- Для уже существующих bonds обратная совместимость сохраняется: до первого
  подключения обновлённого приложения выводится отметка об отсутствии имени;
  затем имя заполняется без изменения самого bond.
- Удаление одного или всех bonds должно одновременно удалять соответствующие
  метаданные имён, чтобы старое имя не перешло новой регистрации того же MAC.
- Формат `ADMIN_BONDS` расширяется добавлением имени после сохранённых полей
  `address_type,address`. Команда удаления остаётся основанной только на MAC.
- Wi-Fi, Web UI, OTA, стандартная BLE-криптография, автомат открытия и таймеры

### Диагностика GATT status 8

- UART подтвердил успешное подключение, `encrypted=1 bonded=1 key=16` и приём
  имени телефона. Сразу после этого FreeRTOS обнаружил stack overflow задачи
  `nimble_host`, ESP32 перезагрузилась, а Android получил GATT status 8.
- Причина не связана с радиотайм-аутом, отсутствием сервиса или MAC-привязкой:
  соединение и SMP завершились успешно до падения.
- Стек штатной задачи NimBLE host был равен 4096 байтам. Операция с NVS внутри
  защищённого GATT callback превысила этот запас.
- Минимальное исправление — увеличить стек NimBLE host до 6144 байт во
  внутренней RAM. Алгоритм BLE, bonding, замка и таймеров не меняется.

## 2. Точка входа и порядок запуска

Точка входа находится в `main/main.c`, функция `app_main()`.

Порядок инициализации:

2. Журнал событий.
3. Загрузка прикладной конфигурации из NVS.
4. Буззер.

## 3. BLE Stack

- Используется Apache NimBLE из ESP-IDF, а не Bluedroid.
- Инициализация хоста: `nimble_port_init()` в `main/ble_scanner.c`.
- Задача хоста: `nimble_port_freertos_init(host_task)`.
- Текущая рабочая роль — Observer; выполняется пассивное непрерывное
  сканирование.
- В `sdkconfig` роли Peripheral и Broadcaster выключены.
- После этапа 3 Legacy Pairing отключён и включены LE Secure Connections;
  GATT-доступ требует шифрования. Режим Secure Connections Only не применяется,
  так как устройство `No Input / No Output` использует стандартный Just Works
  без MITM; отключённая поддержка Legacy исключает откат на Legacy Pairing.
- Включено стандартное постоянное хранилище NimBLE bonds во внутренней NVS.
- Конфигурация допускает одно соединение и до 10 bonds.
- В проекте должен остаться один экземпляр NimBLE host. GATT Server следует
  интегрировать в существующую инициализацию, не создавая второй BLE stack.

## 4. BLE Scanner и маяки

Файлы: `main/ble_scanner.c`, `main/ble_scanner.h`.

- Сканирование запускается `start_scan()` после callback `on_sync()`.
- Используется пассивный scan без фильтра дубликатов.
- Из advertising data извлекается Short/Complete Local Name.
- Поддерживается до 32 недавно видимых BLE-устройств и до пяти настроенных
  имён маяков.
- Маяк сопоставляется только по имени, MAC-адрес для выбора не используется.
- Для каждого маяка отдельно хранятся RSSI, время последнего пакета,
  `requests_open`, блокировка повторного открытия и дедлайны таймеров.
- Таблицы и состояние защищены FreeRTOS mutex.

## 5. Существующий автомат открытия

Автомат полностью расположен в `main/ble_scanner.c` и сейчас тесно связан со
сканером.

Переход к запросу открытия происходит в `gap_event()` при достаточном RSSI:

- устанавливается `requests_open` конкретного маяка;
- фиксируется дедлайн «Долго открыт»;
- обновляется время достаточного RSSI для таймера А;
- вызывается `apply_aggregate_state()`.

`apply_aggregate_state()` объединяет запросы всех маяков по правилу OR:
открытие имеет приоритет. Результат сохраняется как логическое состояние
`BLE_LOCK_STATE_UNLOCKED/LOCKED`, записывается в журнал и передаётся RGB LED.

Критическое расхождение: в предоставленных исходниках не найден модуль или
вызов GPIO физического замка. Единственные вызовы обычного GPIO находятся в
`main/buzzer.c` и управляют буззером. Поэтому текущий «автомат открытия» меняет
программное состояние и LED, но по доступному коду не управляет исполнительным
GPIO замка. Номер GPIO замка также отсутствует в конфигурации.

## 6. Таймер А и таймер Б

Оба таймера обслуживаются задачей `monitor_task()` каждые 100 мс.

- Таймер А: `timer_a_ms`. Перезапускается каждым пакетом маяка с достаточным
  RSSI. По истечении снимает `requests_open`.
- Таймер Б в коде не называется `timer_b`. Его функциональному описанию
  соответствует `long_open_ms` / `long_open_deadline_ms` («Долго открыт»).
  Он не продлевается; по истечении закрывает состояние и блокирует повторное
  открытие от этого маяка.
- Блокировка снимается после трёх слабых пакетов или исчезновения маяка более
  чем на 15 секунд.

Алгоритмы этих таймеров на этапах добавления телефона изменять нельзя.

## 9. Целевая архитектура по TASK_BLE_PHONE_ONLY_v2

В целевой версии используется один NimBLE host только для телефона. Роли
Observer/Central и логика поиска маяков удаляются. Включаются роли
Peripheral/Broadcaster, GATT Server, стандартные SMP Pairing/Bonding и
постоянное NimBLE NVS-хранилище bonds.

Планируемое разделение ответственности:

- `lock_control` — единственная точка управления физическим замком на GPIO 5;
  запросы BLE и тестовая команда Web проходят через этот интерфейс; здесь же
  сохраняется существующая семантика таймера А и таймера «Долго открыт»;
- `ble_phone` — единственный владелец NimBLE host, GATT service, advertising,
  GAP/SMP событий, 60-секундного окна регистрации, проверки encryption,
  bonded-состояния и RSSI;
- `app_config` — порог RSSI телефона со значением по умолчанию -68 dBm;
- `web_ui` — состояние регистрации, открытие 60-секундного окна, список bonds,
  удаление одного/всех bonds, порог RSSI, активный уровень открытия GPIO 5 и
  тест замка;
- стандартный NimBLE store — сохранение максимум 10 bonds во внутренней NVS.

Одновременно разрешено только одно BLE-соединение. При наличии 10 bonds новый
pairing отклоняется без автоматического удаления сохранённых записей.

Автомат открытия переносится из сканера без изменения принципа работы:

1. Разрешённая команда OPEN при достаточном RSSI снимает питание с GPIO 5,
   запускает таймер А и однократно запускает таймер «Долго открыт».
2. Каждое последующее подтверждение достаточного BLE RSSI до истечения таймера
   А сбрасывает таймер А и начинает его отсчёт заново.
3. Если подтверждений достаточного RSSI нет до истечения таймера А, питание
   электромагнита восстанавливается и замок закрывается.
4. Таймер «Долго открыт» не продлевается. Если он истёк, пока замок открыт,
   замок принудительно закрывается независимо от обновлений таймера А.
5. GATT callback не управляет GPIO напрямую: он передаёт событие в
   `lock_control`, а контроль времени выполняется отдельным безопасным
   контекстом FreeRTOS/ESP timer.

## 11. Риски

1. Замок является fail-safe электромагнитом: в запертом состоянии на него
   постоянно подаётся ток, для открытия питание снимается. Активный логический
   уровень «открыто» должен настраиваться через Web UI и сохраняться в NVS;
   противоположный уровень означает «закрыто». До загрузки настройки и при
   перезапуске существует риск краткого импульса неправильной полярности,
   поэтому начальная установка GPIO 3 должна быть выполнена как можно раньше.
2. Автомат таймеров А/«Долго открыт» должен быть перенесён из BLE Scanner в
   `lock_control` без изменения порядка проверок: в текущем коде таймер А имеет
   приоритет проверки перед таймером «Долго открыт» в одной итерации.
3. Текущие defaults явно запрещают Peripheral/Broadcaster; их необходимо
   согласованно изменить во всех конфигурационных файлах.
4. Для сохранения bonding потребуется стандартный NimBLE NVS store. Нужно
   исключить конфликт с прикладным namespace и проверить переживание reboot.
5. Выбор режима Pairing (Just Works или passkey) влияет на MITM-защиту и
   совместимость телефонов. Задача требует LE Secure Connections, но не задаёт
   возможности ввода/вывода passkey.
6. Проверка bonded должна учитывать resolvable private addresses телефона, а
   не сравнивать только текущий MAC.
7. RSSI соединения нужно получать стандартным GAP/HCI API непосредственно
   перед OPEN; RSSI advertising после подключения недостаточен.
8. Callback GATT нельзя блокировать и нельзя из него напрямую менять GPIO;
   запрос должен передаваться в автомат безопасно относительно FreeRTOS mutex.
9. Встроенный HTML и обработчики находятся в одном минифицированном C-файле;
    расширение повышает риск переполнения буферов JSON и лимита URI handlers.
10. Увеличение bonds с 3 до 10 расходует внутреннюю RAM/NVS; внешняя RAM
    запрещена. Число соединений при этом должно быть уменьшено с 3 до 1.
11. NimBLE API может не хранить человекочитаемое имя вместе с bond; Web UI
    должен честно показывать доступный identity address/type.
12. Гонка окончания 60-секундного окна и уже начавшегося Pairing должна иметь
    однозначное безопасное поведение.
13. Аппаратные критерии — Pairing, Bonding после reboot, RSSI и импульс GPIO 5 —
    нельзя полностью подтвердить одной компиляцией.

- OTA остаётся частью существующего Web UI.
- BLE GATT, bonding, автоматическое открытие и алгоритмы таймеров А и

### Разрешение противоречия в плане

В ранней части `AP_MODE_PLAN.md` записано сохранение выбранного режима через
перезапуск, но подтверждённое решение ниже требует после каждого reboot или
пропадания питания запускать нормальный режим. При реализации приоритет имеет
последнее подтверждённое решение: настройки сохраняются в NVS, сам временный
режим настройки — нет.

# Дополнение: источник RSSI в приложении (22.07.2026)

- ESP32 уже публикует измеренный ею RSSI активного телефона в защищённой административной характеристике `ADMIN_STATE` (`rssi=<dBm>` или `rssi=NA`).
- Характеристика доступна только забонденному зашифрованному соединению и только в режиме настроек ESP32.
- Для отображения ESP-side RSSI новый GATT-сервис и изменение алгоритма замка не требуются; приложение может читать существующий `ADMIN_STATE` периодически.
- Android scan RSSI и `BluetoothGatt.readRemoteRssi()` измеряются телефоном и не должны использоваться для требуемой индикации.
- Первое значение ESP-side RSSI уже поступает в ответе на проверочное чтение `ADMIN_STATE`. Повторное немедленное чтение после подтверждения сервисного режима создаёт конкуренцию с `PHONE_NAME` и последующим чтением `ADMIN_BONDS`, поскольку Android GATT выполняет операции последовательно.
- Периодический опрос RSSI не должен использовать ошибку запуска чтения как фатальную: во время записи `ADMIN_CONFIG` репозиторий закономерно находится в `DISCOVERING`. Фоновое чтение в этот момент следует пропустить, сохранив сервисный режим и основную GATT-операцию.
- Успешный callback записи `ADMIN_CONFIG` означает, что ESP32 приняла значение: обработчик ESP сохраняет NVS и применяет конфигурацию до возврата успешного ATT-ответа. Дополнительное чтение из самого write callback не требуется и на части Android BLE-стеков не запускается, оставляя клиент в `DISCOVERING`.
# Дополнение: потеря BLE-соединения как слабый сигнал (22.07.2026)

- `LOCK_EVENT_RSSI_LOW` снимает защиту от повторного открытия после трёх последовательных слабых измерений и переводит LED закрытого замка из жёлтого в красный.
- До изменения `LOCK_EVENT_DISCONNECTED` только снимал вооружение открытия и намеренно не освобождал защиту; без соединения новые RSSI-измерения невозможны, поэтому защита могла остаться включённой неограниченно долго.
- При потере соединения открытый замок уже перестаёт получать `RSSI_HIGH`, поэтому существующий таймер А продолжает работать и закрывает замок без изменения алгоритма таймера.
- Требуемая интеграция ограничивается немедленным снятием защиты при disconnect; алгоритмы открытия и таймеров не меняются.

## Блокирующие риски

### CRITICAL-01 (латентный) — Web UI не имеет аутентификации и авторизации

Важно: **сейчас Web UI не используется в рабочем сценарии**. В `main/main.c`
нет вызовов `web_ui_start()` или `web_ui_stop()`, поэтому HTTP-сервер не
запускается. `main/web_ui.c` остаётся собранным, но неактивным резервным кодом.

Если этот интерфейс будет включён без доработки, он зарегистрирует без проверки
сессии, токена или пароля endpoints:

- `POST /api/lock/test` — открытие замка;
- `POST /api/config` — изменение логики и GPIO;
- `POST /api/ble/registration` — разрешение pairing;
- `DELETE /api/ble/bonds` — удаление ключей;
- `POST /api/ota` — запись произвольной прошивки.

Тогда защита фактически будет основана только на физическом включении режима
AP кнопкой GPIO0. Любой пользователь, получивший доступ к этой Wi-Fi сети,
получит полный административный контроль. Для банковского уровня это
неприемлемо. В текущем firmware этот риск неэксплуатируем через Web UI,
поскольку сервер не запущен.

### CRITICAL-02 — Secure Boot и Flash Encryption отключены

В текущем `sdkconfig`:

- `# CONFIG_SECURE_BOOT is not set`;
- `# CONFIG_FLASH_ENCRYPTION_ENABLED is not set`.

Следствия: физический атакующий может подменить прошивку, прочитать содержимое
flash/NVS и извлечь сохранённые Wi-Fi credentials, pairing-данные и настройки.
Один только `esp_ota_end()` не является доказательством доверенности образа.

## Высокие риски

### HIGH-01 — OTA доверяет любому HTTPS URL

`main/wifi_ota.c` проверяет URL только на префикс `https://` и использует общий
CA bundle. Сертификат сервера проверяется, но нет pinning доверенного домена,
проверки ожидаемого владельца сертификата или отдельной подписи релизного
артефакта. Компрометация DNS/аккаунта/релиза может привести к установке
вредоносного, но формально валидного HTTPS-образа.

### HIGH-02 — Wi-Fi пароль хранится в NVS открытым текстом

`main/wifi_ota.c` сохраняет SSID и пароль через `nvs_set_str()` без шифрования.
При отключённом Flash Encryption это практически доступные credentials. Даже
после включения шифрования требуется политика удаления/замены пароля и запрет
его вывода в диагностические дампы.

### HIGH-03 — Web OTA не ограничивает размер и тип образа

`ota_post()` принимает тело запроса напрямую в OTA partition. Не видно проверки
магического заголовка образа, ожидаемой модели чипа, версии, размера относительно
partition и отдельной подписи приложения. При отсутствии Secure Boot это
позволяет записывать неподконтрольный код.

### HIGH-04 — Нет production-процесса релизов Android

В `app/build.gradle.kts`:

- `versionCode = 1` остаётся постоянным;
- `versionName = "0.1.0"` остаётся постоянным;
- release `isMinifyEnabled = false`;
- конфигурация release-подписи и проверяемая цепочка артефактов в проекте не
  зафиксированы;
- CI, SAST, dependency scanning, SBOM и обязательные release gates не найдены.

Строка времени сборки полезна для диагностики, но не заменяет уникальную
версию, подпись и воспроизводимый релиз.

### HIGH-05 — Неполное доказательство восстановления BLE

Архитектура улучшена: один владелец BLE, Binder, очередь GATT, timeout,
backoff, режимы `AUTO_OPEN/ADMIN/OTA`, stale-callback guard. Однако текущие
logcat показывают реальные незавершённые сценарии:

- `LOCK_INFO -> TIMEOUT`;
- `ADMIN_STATE` с `status=133`;
- приложение остаётся в состоянии `READY`, но сервисная панель не открывается.

Это означает, что отказоустойчивость пока не подтверждена фактическими
тестами для GATT 8/19/133, reboot ESP32, Bluetooth OFF/ON и stale bond.

## Средние риски

### MEDIUM-01 — Открытая Web UI поверхность даже при физическом переключателе

Режим AP отключается вне configuration mode, что снижает риск. Но нет
rate-limit, CSRF-защиты, журнала субъекта запроса, подтверждения опасных
операций на сервере и отдельного read-only режима. Для банковского уровня
нужны server-side authorization checks на каждом endpoint.

### MEDIUM-02 — Android настройки не используют защищённое хранилище

`LockSettings` использует `SharedPreferences`. Сейчас там нет BLE bond keys и
нет Wi-Fi пароля, что хорошо, но это не универсальная гарантия на будущее.
Любые будущие credentials должны храниться в Android Keystore/Encrypted
storage, а не добавляться в обычные preferences.

### MEDIUM-03 — Статическая команда OPEN

Команда `OPEN` — фиксированные четыре байта. Защита опирается на системное BLE
шифрование, bonding, owner identity и RSSI-проверку ESP32. Это приемлемо в
рамках текущего ограничения «не создавать собственный протокол», но не даёт
защиты от использования уже скомпрометированного bonded-телефона и не даёт
криптографической защиты от replay внутри доверенного BLE-сеанса.

### MEDIUM-04 — Нет автоматизированной регрессии

В проекте не обнаружены unit-, integration-, instrumentation- или hardware-in-
the-loop тесты. `TEST_REPORT.md` в основном содержит ручные проверки и факт
сборки. Для банковского уровня нужны повторяемые тесты переходов состояний,
fault injection, OTA rollback и длительная работа foreground service.

### MEDIUM-05 — Диагностические логи потенциально раскрывают инфраструктуру

Логи содержат URL OTA, SSID и состояние подключения. Пароль явно не логируется,
что правильно, но production-сборка должна иметь контролируемый уровень логов,
redaction и запрет передачи диагностического журнала в UI без авторизации.

## Что уже сделано хорошо

- единственный BLE-владелец внутри `BleLockService`;
- Activity не создаёт отдельный GATT-клиент;
- сериализация ATT/GATT операций и таймаут активной операции;
- проверка актуальности `BluetoothGatt` в callback;
- ограниченный backoff реконнекта;
- отдельные режимы автоматического управления, admin и OTA;
- `android:allowBackup="false"`;
- service и внутренний restart receiver не экспортированы;
- защищённые BLE characteristics используют `READ_ENC/WRITE_ENC`;
- ESP32 проверяет `encrypted`, `bonded`, owner identity и RSSI для admin/OPEN;
- OTA через ESP32 использует HTTPS и CA bundle;
- OTA partition scheme использует две app-партиции (`ota_0`, `ota_1`);
- pairing лимитирован 20 bonds и окно регистрации ограничено 60 секундами.

## Приоритетный план до production

1. Включить Secure Boot v2 и Flash Encryption в production-конфигурации,
   организовать безопасное provision-производство ключей и recovery-процедуру.
2. Закрыть Web UI server-side аутентификацией/авторизацией; опасные endpointы
   должны требовать отдельного подтверждения и иметь audit log.
3. Сделать OTA доверенным: подписанные образы, проверка версии/rollback,
   фиксированный доверенный endpoint либо pinning; закрыть Web OTA тем же
   контролем доступа.
4. Ввести release pipeline Android: уникальный versionCode, release signing,
   minify/R8, SBOM, dependency/SAST scanning, проверяемые артефакты и
   двухэтапное одобрение релиза.
5. Добавить автоматические тесты BLE state machine и аппаратную матрицу:
   GATT 8/19/133, MTU failure, stale bond, reboot, Bluetooth OFF/ON, screen
   off, process kill, MIUI cleanup, OTA failure и rollback.
6. Исправить текущий admin-handshake `status=133`: различать временный GATT
   сбой и отказ авторизации, закрывать зависший сеанс и не показывать
   «обычный режим» как окончательный результат до завершения recovery policy.
7. После выполнения пунктов провести независимый security review и
   penetration-тестирование на физическом устройстве.

# Разделение автоматики телефона и режима ESP32 — 22.08.2026

- «Автоматический режим» является локальной настройкой Android и управляет только
  фоновым сервисом автоматического открытия.
- Эта кнопка доступна без текущего BLE-соединения и сама может инициировать поиск ESP32.
- `OPEN_HOLD` больше не изменяет `autoOpenEnabled` и не управляет цветом кнопки
  автоматического режима.
- «Замок постоянно открыт» изменяет только подтверждаемое состояние ESP32 и доступен
  исключительно при BLE-состоянии `READY`.

# Имена и обнаружение нескольких BLE-замков — 22.08.2026

- Видимое имя ESP32 имеет строгий формат `BLE Lock` или `BLE Lock <имя>`;
  серийный номер чипа не используется.
- Пользовательская часть хранится в NVS, задаётся из WebUI и ограничена 20 байтами,
  чтобы полное UTF-8 имя помещалось в BLE scan response.
- UUID сервиса остаётся в основном advertising-пакете, полное имя передаётся в
  scan response; это сохраняет фильтрацию по UUID и позволяет длинное имя.
- Android дополнительно проверяет имя после UUID-фильтрации. В автоматическом
  режиме принимаются только устройства `BOND_BONDED`, поэтому системный список
  bonds является списком замков, которые разрешено автоматически открывать.
- Полный сценарий WebUI выявил недопустимые ключи NVS длиннее 15 символов:
  `ble_connect_rssi` и `ble_disconnect_rssi`. Они заменены на `ble_conn_rssi`
  и `ble_disc_rssi`; старые значения фактически не могли быть записаны.
- Для совместимости с обычными экранами Bluetooth базовый префикс `BLE Lock`
  помещён также в основной advertising-пакет. Полное пользовательское имя остаётся
  в scan response, а UUID сервиса — в основном пакете.
- Android Logcat подтвердил переходный GATT `133` на первом защищённом чтении после
  неуспешного MTU negotiation (`status=6`), хотя ESP уже сообщает encrypted/bonded.
  Начальные чтения INFO/STATUS теперь имеют до трёх повторов в том же GATT-сеансе.

- Граница восстановления подтверждена файлом `история чата для восстановления.txt`: запрос начинается со строки 1034, контрольная ESP32-сборка до изменения имела номер 59.

## Гонка восстановления security и MTU

- На первом соединении после перезапуска ESP Android иногда получает `onMtuChanged(mtu=23, status=6)`: восстановление шифрования известного bond ещё не завершено.
- Переход сразу к защищённому `LOCK_INFO` приводит к `GATT 133`. Исправление ограниченно повторяет MTU в том же GATT-соединении и сохраняет прежний fallback после двух неудач.
- Физический тест выявил вариант, когда повторный `requestMtu()` возвращает `true`, но callback не приходит. Для него установлен watchdog 1500 мс с закрытием зависшей сессии; существующий сервисный reconnect запускается через 1000 мс.

## Восстановление BLE-рекламы ESP32 после пропущенного disconnect

- Физический тест второго телефона показал supervision timeout на Android, после которого ESP32 более минуты не появлялась в сканировании.
- `rssi_task` обрабатывала только успешные `ble_gap_conn_find()` и `ble_gap_conn_rssi()`; ошибки оставляли глобальный handle занятым без ограничения времени.
- При отсутствии соединения задача также не запускала остановленную рекламу, поскольку прежняя проверка выполнялась только для уже активной рекламы.
- Исправление не меняет алгоритм замка: оно удаляет handle только когда NimBLE подтверждает отсутствие соединения, запрашивает штатный terminate при длительной ошибке RSSI и восстанавливает рекламу при её неожиданной остановке.

## Системная геолокация для BLE на Android 6–11

- Приложение уже запрашивало `ACCESS_FINE_LOCATION` до Android 12, но не проверяло, включена ли системная служба геолокации; при выключенной службе пользователь видел только ошибки BLE-сканирования.
- Проверка ограничена API 23–30. На Android 12 и новее диалог не показывается, поскольку там используются разрешения группы «Устройства поблизости».
- Диалог объясняет, что местоположение приложением не используется и не сохраняется, и открывает штатный экран геолокации Android.

## Задержка после выключения Bluetooth телефона

- Logcat показал два разных сценария: обычный GATT-разрыв восстанавливается до `READY` примерно за 3 секунды, а выключение радиомодуля телефона оставляло ESP32 ждать supervision timeout старого канала более 15 секунд.
- Пока старый канал считался подключённым, единственный connection slot ESP32 был занят и реклама отсутствовала; Android завершал полный 15-секундный scan timeout.
- ESP32 теперь запрашивает стандартный BLE supervision timeout 3 секунды при каждом подключении. Это параметр штатного BLE link layer, а не собственный механизм протокола.
- На Android 11 также зафиксированы зависшие `connectGatt()` без callback до системного 30-секундного тайм-аута. Добавлен локальный watchdog 8 секунд, закрывающий только текущий зависший GATT-клиент; повтор запускает существующая логика сервиса.
- Физическая проверка после прошивки ESP локализовала оставшиеся 7,9 секунды в `requestMtu()` до первого защищённого чтения Android 11. На API 23–30 короткие служебные кадры теперь сначала устанавливают шифрованную сессию и состояние `READY`; MTU 256 запрашивается после этого для административных данных.
- Повторный тест показал, что запуск первой сессии сразу после `STATE_ON` может перенести зависание с MTU на первое зашифрованное чтение. После включения Bluetooth сервис ждёт 3 секунды — одновременно стабилизируется GATT Android и истекает supervision старого канала ESP; аварийный timeout `LOCK_INFO` сокращён с 10 до 3 секунд.
- На Redmi Android 11 первая сессия после `STATE_ON` стабильно выполняет discovery, но не восстанавливает bond encryption; вторая сессия достигает `READY` примерно за 1,35–1,6 с. Только для API 23–30 после перезапуска адаптера первая сессия теперь используется как короткий GATT warm-up и закрывается сразу после discovery; повтор начинается через 200 мс без ожидания зависшего чтения.
- Первый warm-up тест выявил, что немедленный `close()` после `disconnect()` не даёт Android передать ESP штатный link-layer разрыв: повторный scan ждал рекламу 7,4 с. Теперь репозиторий ждёт callback `STATE_DISCONNECTED` перед `close()`; аварийный предел ожидания callback — 1,5 с.
- После подтверждённого разрыва повторный Android scan всё равно задержал выдачу ESP на 4,94 с. Поскольку устройство уже идентифицировано и bonded, рабочая сессия теперь использует прямой `connectGatt()` к тому же `BluetoothDevice` через 200 мс, без повторного scan.
- Контроль прямого подключения показал, что Redmi Android 11 восстанавливает security-состояние не дополнительной GATT-сессией, а только после временной паузы: защищённое чтение на 6,9-й секунде после `STATE_ON` ещё зависает. Экспериментальный warm-up отключён; рабочее восстановление начинается один раз через 8 секунд после `STATE_ON`.
- На первом телефоне Android 16 обнаружен тот же принцип порядка операций: MTU до восстановления шифрования стабильно возвращал `status=6`, а retry оставался без callback. Перенос MTU после `READY` распространён на все версии Android.

## Командное продление автоматического открытия

- Ранее `LOCK_EVENT_RSSI_HIGH` обновлял `last_sufficient_ms` при каждом сильном RSSI, поэтому выключение автоматического режима телефона не позволяло таймеру А закрыть замок, пока BLE оставался подключён.
- Теперь RSSI остаётся обязательной проверкой близости, но продление таймера А выполняет только защищённая команда `OPEN`. Android в автоматическом режиме повторяет её каждые 2 секунды.
- Для уже открытого замка повторный `OPEN` проверяется по порогу удержания, для закрытого — по строгому порогу открытия. Режим постоянного открытия не изменён.

## Выход из жёлтого состояния без команд OPEN — 22.08.2026

- После введения командной аренды жёлтая блокировка продолжала учитывать только
  RSSI: сильный сигнал отменял таймер Б, даже когда Android уже прекратил команды
  `OPEN` после выключения автоматического режима.
- Каждая принятая защищённая команда `OPEN` теперь обновляет отметку активности и
  в жёлтом состоянии. Если команды отсутствуют дольше таймера А, запускается
  существующий таймер Б; сильный RSSI такой отсчёт не отменяет.
- Возобновление команд до завершения таймера Б сохраняет прежнее поведение, а по
  истечении таймера без команд блокировка снимается и LED становится красным.

## Диагностика фоновой команды OPEN — 22.08.2026

- Для проверки поведения с заблокированным экраном временно отключено только
  двухсекундное продление команды `OPEN` со стороны Android.
- Первая команда после достижения `READY` сохранена, поэтому поиск, защищённое
  подключение и первоначальная попытка открытия продолжают работать.
- Изменение оформлено отдельным диагностическим флагом и не затрагивает ESP32.

## Возврат автоматики при блокировке экрана — 23.08.2026

- Физическая диагностика показала, что Android сохраняет foreground-service и
  BLE/GATT в Doze, однако видимый экран ранее переводил общую сессию в `ADMIN`.
- При блокировке вызываются `onPause()`/`onStop()`, но не обязательно `onDestroy()`,
  где раньше находился единственный общий возврат к фоновой автоматике.
- `MainActivity.onStop()` теперь вызывает `resumeAutomaticMode()` при включённой
  локальной автоматике; если Binder уже недоступен, запускается foreground-service.
- Android 16 может сохранять Activity без `onStop()` после гашения экрана, поэтому
  foreground-service также непосредственно обрабатывает `ACTION_SCREEN_OFF` и
  возвращает активную сессию `ADMIN` в `AUTO_OPEN`.
- Диагностическое отключение повторных `OPEN` отменено: командная аренда каждые
  2 секунды восстановлена после исключения её как причины проблемы.
- При Bluetooth OFF отметка отправленного `OPEN` теперь сбрасывается до закрытия
  GATT. Асинхронный callback старой сессии больше не запускает `WAITING_DEPARTURE`
  и не конкурирует с новым репозиторием после Bluetooth ON.

## Временное отключение командной аренды — 23.08.2026

- По требованию пользователя до отдельного указания удалена периодическая отправка
  `OPEN`: Android передаёт команду один раз после достижения `READY`.
- ESP32 больше не рассматривает `OPEN` как периодически обновляемую аренду. После
  первого разрешения автоматики открытое состояние продлевается достаточным RSSI,

Исходная ESP32-сборка build 175 успешна и загружена по OTA вместо 174.

- До задачи AUTO discovery шёл через `PassiveBleScan.register()` с filtered

## Android AUTO: системный запрос, защищённая готовность и OPEN

## Проверка роли RSSI-ползунка перед изменением

- До изменения Android baseline `build-android.ps1` прошёл (assembleDebug).
- Фактические read-only значения на 28.09.2026: ESP firmware 10.0.224 имеет `phone_rssi_threshold=-50 dBm` и `zone_exit_grace_ms=500 ms`; Android SharedPreferences содержит `rssi_threshold=-55 dBm`, `security_settle_delay_ms=700 ms`.
- Текущий живой замер не надо смешивать по направлениям: `/api/status` показывает RSSI телефона, принятый ESP (`-36 dBm`), а Android `readRemoteRssi()` показывает RSSI ESP, принятый телефоном (последние значения `-53..-55 dBm`). В этом прогоне обе стороны выше своих порогов, но запас по Android-порогу мал.
- Прошивка разрывает соединение, если её фильтрованный RSSI телефона остаётся ниже `-50 dBm` дольше 500 мс. Android ждёт 700 мс после MTU/service discovery перед первой защищённой операцией. Это потенциальное окно гонки только при слабом ESP-side RSSI; сейчас ESP принимает сигнал около `-36 dBm`, поэтому такая причина в текущем соединении не проявляется.
- До правки bonded AUTO использовал `connectGatt(autoConnect=true)`, а ползунок не влиял на этот путь. Общий scan callback отбрасывал слабые объявления до GATT; это не соответствовало желаемой роли настройки.
- Событие `onSignalRssi` смешивает данные рекламного сканирования и GATT `readRemoteRssi()`, поэтому его нельзя использовать как доказательство RSSI уже установленной GATT-сессии. Для порога OPEN нужен отдельный callback именно из GATT RSSI-операции.
- Решение для этапа: принимать подходящую рекламу независимо от RSSI; после защищённого GATT READY запускать немедленный GATT RSSI-запрос; отправлять AUTO OPEN только при `rssi >= LockSettings.rssiThreshold`. Порог ниже не разрывает GATT и не влияет на алгоритм ESP; порог продолжает применяться только к решению телефона об отправке OPEN. ESP-порог и выдержка не изменяются.

## 2026-09-28 — сигнал при выключенном экране

Журналы телефона показали, что BLE advertisement callback продолжает выполняться при выключенном экране; сканирование не остановлено. Для короткого сигнала добавлен timed PARTIAL_WAKE_LOCK на 1,09 секунды: CPU остаётся активным до завершения ToneGenerator, экран не включается, блокировка освобождается при cleanup. Автоматическое native GATT подключение является подтверждением обнаружения замка через BLE рекламу, поэтому теперь первый GATT_CONNECTED native auto-connect запускает тот же сигнал, с защитой от повторов до подтверждённого ухода. Краткий partial wake lock применяется для всех путей запуска сигнала.

Итоговый тест на реальном телефоне: при `mWakefulness=Dozing` native auto-connect вызвал `ToneGenerator.startTone()`, вернувший `true`; partial wake lock был получен и снят через ~0,33 секунды.
## 2026-09-29 — диагностика отсутствия BLE-сигнала
