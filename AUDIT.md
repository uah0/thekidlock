# Аудит текущего проекта — 10.10.2026

## Переподключение MQTT и кэш конфигурации — 13.10.2026

Baseline `build-esp32.ps1` успешно собрал signed-dev 10.0.585 до изменений на
ESP-IDF 5.4.4; проверены RSA-подпись и encrypted OTA round-trip. В `command_task()`
конфигурация MQTT перечитывалась из NVS каждый цикл (каждые 100 мс), очередь
сообщений опрашивалась без ожидания и задача затем делала `vTaskDelay(100 мс)`.
MQTT client использовал keepalive 60 секунд и внутренний reconnect timeout 30
секунд.

Keepalive снижен до 25 секунд, reconnect timeout — до 3000 мс. `command_task()`
теперь ждёт первую запись до 100 мс в `xQueueReceive()`, затем обрабатывает
накопленную очередь; пустой периодический опрос и `vTaskDelay()` удалены.
`mqtt_config_get()` читает NVS при первом запросе после сброса кэша, последующие
запросы копируют значение из RAM. `mqtt_config_save()` инвалидирует кэш только
после успешного NVS commit; поколение кэша защищает от устаревшего параллельного
чтения. Сборка signed-dev 10.0.586 установлена OTA на `192.168.1.54`;
Device Agent подтвердил переход 10.0.584 → 10.0.586. После перезапуска замок
вернулся в состояние LOCKED без ошибок, затем журнал подтвердил подключение к
`iot.coreflux.cloud` и готовую MQTT-подписку. Runtime-проверка сохранения нового
адреса брокера отдельно не выполнялась. MQTT wire protocol, темы и команды не менялись.

## Чтение снимка ULP и проверка владельца HOLD — 13.10.2026

Baseline `build-esp32.ps1` прошёл на ESP-IDF 5.4.4 до изменений (signed-dev,
build 582). `ulp_controller_read_diagnostics()` использует seqlock вокруг общей
структуры ULP, но делает четыре немедленные попытки; если ULP обновляет снимок,
все попытки могут попасть в окно нечётного/изменившегося sequence. FreeRTOS tick
в текущей конфигурации 100 Hz, поэтому повтор с `vTaskDelay(1)` и общим deadline
около 50 мс даёт ULP время закончить запись, не меняя код ULP.

`lock_control` уже обновляет `lock_feedback_t` примерно в каждом цикле; он
содержит нужные для интернет-открытия признаки fault/calibration и время последнего
валидного чтения. Ранее `sampled_at_us` переписывался даже после неудачного
снимка. Этап 1 сохраняет timestamp только валидного чтения, использует кэш не
старше 300 мс для интернет-команды, а при устаревшем кэше запрашивает свежую
диагностику; если снимок получить не удалось, открытие отклоняется. Реализация
собрана и установлена OTA: 10.0.578 → 10.0.583. Device Agent подтвердил новую
версию; после перезапуска замок сообщил LOCKED, без ошибок.

В `central_service_request_cb()` HOLD ранее обходил owner-check из-за явного
исключения `request[1] != PHONE_SERVICE_HOLD`, хотя ниже уже предусмотрен ответ
`send_result(1)` для не-владельца. Этап 2 удаляет только это исключение; разбор
пакета, шифрованное BLE-соединение, HOME_WIFI и выполнение HOLD остаются прежними.
Алгоритмы ULP, автоматики открытия и таймеров A/B не меняются. Signed-dev 10.0.584
собрана и установлена OTA: 10.0.583 → 10.0.584. Device Agent подтвердил новую
версию; после перезапуска замок сообщил LOCKED, без ошибок. Запрет HOLD для
не-владельца проверен по обработчику и сборке; отдельный физический телефон
не-владелец для runtime-проверки не подключался.

## Единый защищённый USB-образ с чистой NVS — 13.10.2026

Пользователь уточнил, что параметры тестовой прошивки сохранять не требуется.
Поэтому схема со снимком каждого чипа заменена универсальным образом:
ESP-IDF `nvs_flash_init()` сам генерирует NVS-ключи в пустом `nvs_keys` partition,
который шифруется Flash Encryption. Отдельный профиль `factory-usb` использует
Flash Encryption Release, Secure Boot V2 и отключение ROM Download при первом
запуске. Образ 10.0.581 содержит пустые NVS и `nvs_keys`; физический первый запуск
не выполнен, eFuse не менялись. До него требуется отдельное явное разрешение на
необратимую финализацию конкретного ESP по этому `AGENTS.md`.

Опубликованное OTA signed-dev 10.0.578 предназначено для промежуточной проверки
после начального USB 10.0.574. Второй USB 10.0.581 собирается отдельно локальным
скриптом `usb-final/build.ps1`; он не зависит от сохранённого снимка и очищает все
состояния первой прошивки. После финального USB пользователь регистрирует телефон,
проводит калибровку и задаёт настройки заново.

## MQTT-дашборд состояния замка — 11.10.2026

Аудит после успешных исходных Android release и ESP32 release сборок. ESP уже
публикует `locks/<mac>/result` с HMAC по LTK владельца только при интернет-команде;
Android подписывается на этот топик только во время выполнения команды. Отдельного
потока состояния нет. В ULP доступны состояние замка, состояние пластины и raw батареи;
Web UI рассчитывает `battery_mv` из raw через ADC calibration. Модель двери в MQTT
сейчас имеет только `closed/open/unknown`, а UI показывает только данные исполнения
интернет-команды.

Для дашборда нужен retained `locks/<mac>/state`, обновляемый во время MQTT-сессии
замка и проверяемый приложением HMAC владельца. Состояние замка строится по
`LOCK_STATE_LOCKED/UNLOCKED`; дверь — по `PLATE_CONTACT`, зазорам `PLATE_GAP_*` и
`PLATE_FAR`; напряжение берётся тем же ADC-преобразованием, что Web UI. Публичный
анонимный брокер не обеспечивает приватность топика: подпись защитит данные от
подмены приложением, но не скроет состояние от читателя MQTT.

Изменение 11.10.2026: вынести дашборд в самостоятельную карточку непосредственно
над карточкой автооткрытия. Видимость зависит от подтверждённой роли владельца и
ответа замка о настроенной сохранённой домашней сети с активным автоподключением
(либо MQTT, которому разрешено подключение к домашней сети). Приложение ранее не
получало второй признак; существующий ответ BLE передаёт только булев статус через
зашифрованный GATT, без SSID/пароля. При входе на экран признак сбрасывается до ответа.
ESP публикует retained `state` с частотой 2 Гц; Android принимает MQTT push и не
выполняет периодический опрос брокера.

## Почему Wi-Fi подключается при выключенном автоподключении — 11.10.2026

В Web UI переключатель `wauto` сохраняет `auto_connect` в NVS через
`/api/wifi/auto`; `/api/wifi` читает это же значение. В `wifi_ota.c`
`home_auto_connect()` возвращает `s_auto_connect || s_mqtt_required`.
`s_mqtt_required` загружается из NVS-настройки `mqtt.enabled` и обновляется
задачей интернет-команд. Поэтому `main.c` при запуске и задача MQTT могут
подключить домашнюю сеть при `auto_connect=false`. Текущий Web UI всегда
сохраняет MQTT как `enabled=true` и не показывает его выключатель.

В рамках диагностики сетевую логику не менять: жёсткое применение
`auto_connect=false` отключило бы при запуске интернет-открытие. Содержимое
NVS текущего устройства напрямую не прочитано: `/api/wifi` и `/api/mqtt`
недоступны по Agent API. Доступность замка через домашнюю сеть и кодовое
условие согласуются с наблюдением пользователя.

## Диагностика периодического белого LED — 13.10.2026

На устройстве 10.0.566 HTTP status в повторных проверках показывал `STARTING` при одновременных `ULP lock_state=LOCKED`, `fault_flags=0` и актуальных ULP измерениях. Журнал событий также часто чередовал `ULP факт: LOCKED` и `ULP факт: STARTING`. В `lock_control.c` `refresh_feedback()` выставляет `valid=false`, если `ulp_controller_read_diagnostics()` не удаётся более 1 секунды; отображение LED переводит невалидную обратную связь в `LED_STATE_BOOT`, чей цвет белый. Это объясняет наблюдаемый переход красный/белый без отдельного мигающего LED-таймера.

Последнее изменение для тока катушки добавило в `main/ulp/main.c` дополнительные 8 ADC выборок и переключение канала в `measure_battery_locked()`. Функция выполняется на каждом ULP цикле при запертом замке, пока `sequence` нечётный. Чтение `ulp_controller_read_diagnostics()` делает только четыре немедленные попытки seqlock и возвращает false, если все попали в нечётную/меняющуюся публикацию. Это вероятный триггер начавшегося после изменения голодания чтения; точный вклад длительности дополнительного ADC окна требует отдельного измерения. Web UI только форматирует API значение тока и GPIO LED не меняет.

### Дополнительные симптомы: always-open и MQTT open — 13.10.2026

При live-проверке режим `hold_open=true`, `requested_open=true`, но Agent status сообщил `state=STARTING`, `ulp=null`, `ulp_error=snapshot unavailable`. Журнал последовательно показывал `ULP факт: OPEN_HOLD`, затем `STARTING`; постоянный белый в режиме always-open соответствует той же невалидной обратной связи (ожидаемый валидный UNLOCKED был бы зелёным). MQTT/UI endpoint на Agent API не доступен, поэтому активное соединение с брокером этой проверкой не измерялось.

Путь ошибки удалённого открытия найден в `cloud_commands.c`: после получения и криптографической проверки MQTT-команды `lock_control.c` выполняет свежий `ulp_controller_read_diagnostics()`. Если snapshot недоступен, команда сразу переводится в фазу error без подачи команды ULP. Поэтому рабочий брокер может доставить команду, но замок отклонит её на локальной проверке ULP; это согласуется с белым LED и `snapshot unavailable`. Для окончательного подтверждения отдельного запроса MQTT-команды не отправляли, так как он физически отпирает замок.

### Read-only проверка текущей сессии — 13.10.2026

После нового запуска устройство 10.0.566 стабильно держит `OPEN_HOLD`: шесть status-снимков за 11 секунд показывали `state=OPEN_HOLD`, `hold_open=true`, ULP «Открыт», `fault_flags=0`; ULP measurement_counter=1 как ожидается для `Постоянно открыт: без измерения`. Значит ранее зафиксированный ULP snapshot starvation не проявляется в текущем открытом режиме. В старте MQTT к `mqtt.tyckr.io` подключился и подтвердил подписки; socket errno 113 на 39-й секунде сменился успешным reconnect и повторной подпиской на 41–42 секундах. BLE-поле `host` временно сохраняется на wire для старых версий приложения и первичной конфигурации.
- Вне Android WebView синхронизировать адрес с приложением невозможно; при отсутствии bridge Web UI должен показывать ошибку, а не подтверждать полную синхронизацию. Алгоритм открытия, топики и ESP MQTT-переподключение не меняются.
- Реализация завершена: Android хранит выбранный адрес в отдельном локальном ключе и накладывает его при чтении MQTT-профиля. BLE-пакет по-прежнему содержит `host` для старых приложений и первичной настройки, но при повторной синхронизации того же `target`/`phone` Android сохраняет свой действующий адрес. - Нижняя информация приложения смещается на 12 dp вниз в безопасную область над системной панелью; нижняя граница `SwipeRefreshLayout` сдвигается на ту же величину, чтобы увеличить доступную область пульта и не перекрывать футер.
- Проверка промежуточного распределения по зазору от низа содержимого выявила положительную обратную связь при переполнении `ScrollView`; финальный расчёт использует фиксированный бюджет viewport, поэтому увеличение плиток не меняет расчёт доступного пространства. Release 1.0.439 установлен и визуально проверен на штатном экране 1080×2392 и портретном размере 360×800 dp.

## Вертикальное центрирование текста плиток — аудит 14.10.2026

- Проверка снимков release 1.0.441 показала, что у обычных кнопок текст оставался у верхнего края, хотя иконка и интернет-плитка были по центру. `Gravity.CENTER` не исправлял размещение текста кнопок с compound-иконкой.
- Для кнопок пульта задаётся верхняя гравитация текста и горизонтальное центрирование; дополнительная высота каждой плитки поровну добавляется к верхнему и нижнему внутреннему отступу. Поэтому текст вместе с иконкой остаётся по центру плитки при любом рассчитанном размере. Интернет-плитка продолжает центрировать многострочную подпись в `onDraw()`.
- BLE/MQTT действия, подписи и размеры шрифта не меняются; логика затрагивает только размещение плиток главного пульта.
- Проверено на release 1.0.442: на штатном экране 1080×2392 и тестовом портретном размере 360×800 dp текст видимо центрирован во всех плитках; все плитки и подвал видны без прокрутки.

## Горизонтальное центрирование интернет-кнопки — аудит 14.10.2026

- Исходная Android debug-сборка 1.0.444 успешно прошла проектным скриптом до изменений. `InternetOpenProgressButton` строит подпись и адрес брокера через `StaticLayout`, но оставлял стандартное выравнивание `ALIGN_NORMAL`; строки начинались у левого края текстовой области.
- Для текста задано `ALIGN_CENTER`; область начинается после иконки с отступом 16 dp и заканчивается за 24 dp до правого края. Таким образом подпись центрируется между иконкой и правым краем, как попросил пользователь. Изменения касаются только отрисовки и измерения интернет-плитки; обработка MQTT и состояния кнопки не затронуты.
- Release 1.0.446 установлен и визуально проверен на физическом экране 1080×2392 и тестовом размере 360×800 dp; все кнопки и подвал остаются видимыми.
