# Аудит проекта BLE Lock

## Issue #4: разделение постоянной и временной Wi-Fi-конфигурации — 22.08.2026

- UUID `OTA_CONFIG` сохранён для совместимости с установленными клиентами и
  существующим runtime hotspot-сценарием.
- Двухпольная запись `SSID\npassword` по-прежнему означает временную сеть и не
  затрагивает NVS.
- Постоянная запись получила явный префикс `PERSIST\n`, после которого идут
  `SSID\npassword\nHTTPS_URL`; ESP32 направляет только такой payload в
  `wifi_ota_set_config()`.
- ATT success постоянной записи возвращается только после результата записи
  NVS. В Android постоянная и временная операции теперь имеют разные сообщения
  об успехе и ошибке.
- Секретные значения не добавлены в журналы ESP32 или Android.

## Аудит кнопки «Сохранить Wi-Fi/OTA» — 22.08.2026

Проверены два независимых пользовательских маршрута с одинаковым названием.

### Web UI в Chrome

- Кнопка вызывает JavaScript `saveWifi()` и отправляет `POST /api/wifi` с
  `ssid`, `password` и `url`.
- `wifi_post()` формирует `SSID\npassword\nHTTPS_URL` и вызывает постоянное
  сохранение `wifi_ota_set_config()` в NVS.
- При HTTP 200 страница показывает «Сохранено»; запрос Chrome не появляется в
  BLE-логе Android-приложения.
- Неизменённые SSID/URL с пустым паролем возвращают `unchanged=true`, сохраняя
  прежний пароль.

Недостатки Web-маршрута:

- `wifi_post()` не логирует вход и успешный HTTP 200; по журналу телефона
  невозможно доказать нажатие кнопки.
- Query-буфер ограничен 420 байтами, хотя URL-кодирование допустимых значений
  может увеличить запрос сильнее и вызвать HTTP 400 до сохранения.
- SSID и URL вставляются в JSON без escaping; специальные символы могут
  сделать ответ `/api/wifi` невалидным.

### Android/BLE

- Кнопки вызывают `saveOtaConfig()` и передают `SSID\npassword\nHTTPS_URL`
  через `OTA_CONFIG_UUID`.
- ESP32 направляет запись в `wifi_ota_set_runtime_config()`, а не в
  `wifi_ota_set_config()`.
- Runtime-функция предназначена для временной LocalOnlyHotspot-сети, ожидает
  только `SSID\npassword`, не сохраняет NVS и запускает Web UI. Постоянное
  сохранение Android поэтому несовместимо с ESP32: payload отклоняется по
  длине либо URL становится частью неверного Wi-Fi-пароля.
- Callback Android для любой записи сообщает «Временные настройки точки
  доступа переданы», даже для кнопки постоянного сохранения. Проверки чтением
  сохранённой конфигурации нет.

### Вывод

Web-кнопка привязана к правильному backend постоянного сохранения, но результат
проверяется ответом страницы или serial-логом ESP32, не BLE-логом телефона.
Android-кнопка постоянного сохранения функционально неверна из-за объединения
постоянной и временной конфигурации в одной характеристике без различимого
формата. Исправление должно сохранить runtime hotspot-путь и явно разделить
два назначения.

## Issue #4 — режимы Android и автоматический вход в Web UI (22.08.2026)

### Runtime-аудит гонки hotspot/BLE (22.08.2026)

- На физическом телефоне подтверждён сценарий: hotspot успешно создаётся,
  после чего BLE-запись завершается локальной ошибкой «Сначала подключитесь к
  зарегистрированному замку».
- Причина: `MainActivity.onLockData()` вызывал `resumeAutomaticMode()` для
  каждого статуса, отличного от `OPEN_HOLD`. Во время Web UI это переводило
  единый `BleLockService` из `ADMIN` в `AUTO` непосредственно перед передачей
  runtime Wi-Fi credentials.
- `pendingHotspotWifi` очищался до подтверждения ATT-записи, поэтому гонка
  превращала временный разрыв в безвозвратную потерю payload.
- Исправление должно разрешать AUTO-resume только как завершение явного выбора
  пользователем режима `AUTO`, а credentials сохранять до успешного callback и
  повторять после восстановления `READY`.

### Уже существующие механизмы

- `BleLockService` остаётся единственным владельцем фонового BLE-сеанса, а
  `MainActivity` использует его через `BleClient`.
- ESP32 допускает команды замка только через encrypted/bonded BLE; доступ к
  административным характеристикам дополнительно сверяется с owner address.
- `CHR_LOCK_STATUS` уже возвращает `OPEN_HOLD`, `OPEN` или `LOCKED`, поэтому
  фактический взаимоисключающий режим можно восстановить после reconnect.
- `wifi_ota_set_runtime_config()` уже принимает временные `SSID/password`, не
  записывает их в NVS, подключает ESP32 как STA, запускает локальный Web UI и
  публикует `WEB_READY;IP=...` через защищённую BLE-характеристику статуса.
- Android уже использует `LocalOnlyHotspot`, передаёт runtime credentials по
  BLE, опрашивает статус ESP32 и открывает полученный локальный URL.

### Выявленные пробелы относительно Issue #4

- главное окно построено из switch и пары небольших ручных кнопок, а не из
  трёх крупных полноширинных кнопок режимов;
- `KEEP_OPEN` является toggle-командой: повтор или потерянный ответ способны
  рассинхронизировать Android и ESP32; нужна идемпотентная установка `AUTO` и
  `ALWAYS_OPEN`;
- Android `autoOpenEnabled` управляет foreground service локально, но отдельной
  команды установки рабочего режима ESP32 нет;
- сценарий hotspot управляется набором boolean-флагов и не имеет единого
  перечисления состояний, отображаемого на сервисной кнопке;
- отсутствуют измерение полного времени успешного цикла и сохранённая оценка
  начального countdown;
- текущий экран выводит пароль hotspot пользователю и пишет SSID в журнал;
  для полностью автоматического сценария это не требуется и увеличивает
  поверхность раскрытия credentials.

### Точки безопасной интеграции

- сохранить существующие UUID и добавить идемпотентные команды в
  `CHR_LOCK_COMMAND`, не создавая собственного шифрования или нового BLE
  протокола;
- расширить `lock_control` операцией явной установки hold-open, не меняя
  алгоритмы таймеров А/Б и открытия по RSSI;
- сохранить существующий runtime Wi-Fi/Web UI путь, обернув его на Android в
  явную state machine и countdown;
- использовать `CHR_LOCK_STATUS` как источник фактического режима после
  reconnect и показывать третью кнопку только после admin-ответа ESP32.

## Архитектура BLE Android — 17.08.2026

- В приложении одновременно существуют два экземпляра `BleRepository`: один
  внутри `BleLockService` для автоматического открытия, второй внутри
  `MainActivity` для сервисной панели.
- При входе в сервисную панель Activity останавливает службу асинхронно и
  почти сразу запускает собственный scan/GATT. Это допускает пересечение
  `closeGatt()`, сканирования и системного bonding.
- В `BleRepository` операции чтения/записи GATT вызываются напрямую из разных
  обработчиков и не образуют единую очередь ATT-операций.
- По logcat подтверждена гонка: Activity успевала показать ошибку чтения
  состояния до завершения MTU/GATT-последовательности, после чего тот же вход
  завершался успешно.
- Текущий небольшой фикс блокирует административный опрос до состояния READY
  и повторяет проверку доступа после готовности GATT. Это убирает конкретную
  преждевременную ошибку, но не устраняет архитектурную причину.
- Целевая схема: один BLE-владелец в foreground service, одна очередь GATT и
  явные взаимоисключающие режимы `AUTO_OPEN`, `ADMIN`, `OTA`. Activity должна
  быть только UI-клиентом владельца и не создавать собственный GATT.
- После перехода в `ADMIN` автоматическое открытие приостанавливается только
  через диспетчер, затем выполняется полное освобождение прежней GATT-сессии и
  новый последовательный admin-сеанс. При закрытии панели диспетчер возвращает
  `AUTO_OPEN`.

## Индикация полного сброса bonds — 22.07.2026

- Полное удаление bonds вызывается из трёх путей: BLE `DELETE_ALL`, Web UI и
  длинное нажатие GPIO0. BLE admin уже ограничен режимом настройки, Web UI
  существует только в этом режиме, но длинное нажатие сейчас доступно всегда.
- Ограничение следует установить внутри `ble_phone_delete_all_bonds()`, чтобы
  единое правило действовало для всех текущих и будущих вызывающих сторон.
- После успешного полного удаления LED должен трижды переключиться белый/
  выключен и восстановить текущий отображаемый режим. Поскольку удаление может
  выполняться в NimBLE host callback, задержки нельзя выполнять синхронно.
- Мигание реализуется отдельной одноразовой FreeRTOS-задачей; изменения базового
  состояния замка во время мигания сохраняются и применяются после окончания.
- Так как полный сброс разрешён только в режиме настройки, итоговый цвет после
  трёх миганий — синий.
- Удаление одного bond не запускает специальную индикацию.

## Быстрое открытие и индикация автомата замка — 22.07.2026

- Текущий Android-сервис отправляет `OPEN` после discovery и чтений
  `LOCK_INFO/LOCK_STATUS`. ESP32 отклоняет запись, если RSSI ещё не измерен или
  ниже порога; сервис после отказа начинает новый цикл подключения. Это может
  задержать открытие на секунды и пропустить момент пересечения порога.
- Существующий `lock_control` уже поддерживает `open_armed`: после принятой
  команды последующий `RSSI_HIGH` открывает замок. Требуется отдельное событие
  ARM, которое устанавливает этот флаг без преждевременного открытия.
- BLE-команда `OPEN` должна приниматься для encrypted + bonded телефона при
  любом текущем RSSI: при достаточном RSSI открывать сразу, иначе вооружать
  автомат. Проверка порога и физическое решение остаются на ESP32.
- Период ESP32 RSSI task равен 500 мс. Уменьшение до 100 мс сокращает
  программную задержку после пересечения порога, не меняя значения и семантику
  таймеров А/«Долго открыт».
- Для уже bonded-телефона фоновому Android-сервису не нужны UI-чтения INFO,
  STATUS и ADMIN_STATE перед OPEN. Control-only путь может перейти в READY
  сразу после service discovery; регистрационный Activity-путь сохраняется.
- LED уже получает состояния от `lock_control`, но blocked окрашен фиолетовым,
  а режим настройки перекрывает базовое состояние синим. Требуется жёлтый для
  `LOCKED_BLOCKED` и постоянный приоритет состояния замка; синий остаётся
  только для OTA.
- Целевая индикация: `LOCKED` — красный, `UNLOCKED` — зелёный,
  `LOCKED_BLOCKED` — жёлтый. Снятие блокировки возвращает красный.
- Алгоритмы таймера А, «Долго открыт», гистерезиса и трёх слабых RSSI для снятия
  защиты не изменяются.

## Имена телефонов, привязанные к bonds — 22.07.2026

- Текущая идентификация телефона выполняется стандартным NimBLE store по
  identity MAC и типу BLE-адреса. Этот механизм и алгоритм допуска телефона
  изменять не требуется.
- Стандартное bond-хранилище NimBLE не содержит пользовательского имени
  Android-телефона. Получение имени непосредственно из SMP bonding также не
  предусмотрено используемым стандартным GAP/SMP потоком.
- Для имени требуется отдельная метаданная во внутренней NVS. Ключ формируется
  из типа и identity MAC, поэтому имя не участвует в авторизации и не заменяет
  MAC-привязку.
- Android передаёт локальное Bluetooth-имя после того, как соединение стало
  encrypted + bonded. Новая GATT-характеристика доступна только для
  зашифрованной записи, а обработчик дополнительно проверяет bonded-состояние.
- ESP32 сохраняет первое непустое имя для MAC и не перезаписывает его при
  последующих соединениях. Таким образом фиксируется имя на момент первой
  регистрации обновлённым протоколом.
- Для уже существующих bonds обратная совместимость сохраняется: до первого
  подключения обновлённого приложения выводится отметка об отсутствии имени;
  затем имя заполняется без изменения самого bond.
- Удаление одного или всех bonds должно одновременно удалять соответствующие
  метаданные имён, чтобы старое имя не перешло новой регистрации того же MAC.
- Формат `ADMIN_BONDS` расширяется добавлением имени после сохранённых полей
  `address_type,address`. Команда удаления остаётся основанной только на MAC.
- Wi-Fi, Web UI, OTA, стандартная BLE-криптография, автомат открытия и таймеры
  А/«Долго открыт» данным этапом не затрагиваются.

### Диагностика GATT status 8

- UART подтвердил успешное подключение, `encrypted=1 bonded=1 key=16` и приём
  имени телефона. Сразу после этого FreeRTOS обнаружил stack overflow задачи
  `nimble_host`, ESP32 перезагрузилась, а Android получил GATT status 8.
- Причина не связана с радиотайм-аутом, отсутствием сервиса или MAC-привязкой:
  соединение и SMP завершились успешно до падения.
- Стек штатной задачи NimBLE host был равен 4096 байтам. Операция с NVS внутри
  защищённого GATT callback превысила этот запас.
- Минимальное исправление — увеличить стек NimBLE host до 6144 байт во
  внутренней RAM. Алгоритм BLE, bonding, замка и таймеров не меняется.

6. Wi-Fi STA и ожидание подключения.
7. HTTP/Web-интерфейс.
8. BLE Scanner и задача контроля таймеров.

Следствие: BLE сейчас не запускается, пока Wi-Fi не получил IP-адрес.

## 3. BLE Stack

- Используется Apache NimBLE из ESP-IDF, а не Bluedroid.
- Инициализация хоста: `nimble_port_init()` в `main/ble_scanner.c`.
- Задача хоста: `nimble_port_freertos_init(host_task)`.
- Текущая рабочая роль — Observer; выполняется пассивное непрерывное
  сканирование.
- В `sdkconfig` роли Peripheral и Broadcaster выключены.
- После этапа 3 Legacy Pairing отключён и включены LE Secure Connections;
  GATT-доступ требует шифрования. Режим Secure Connections Only не применяется,
  так как устройство `No Input / No Output` использует стандартный Just Works
  без MITM; отключённая поддержка Legacy исключает откат на Legacy Pairing.
- Включено стандартное постоянное хранилище NimBLE bonds во внутренней NVS.
- Конфигурация допускает одно соединение и до 10 bonds.
- В проекте должен остаться один экземпляр NimBLE host. GATT Server следует
  интегрировать в существующую инициализацию, не создавая второй BLE stack.

## 4. BLE Scanner и маяки

Файлы: `main/ble_scanner.c`, `main/ble_scanner.h`.

- Сканирование запускается `start_scan()` после callback `on_sync()`.
- Используется пассивный scan без фильтра дубликатов.
- Из advertising data извлекается Short/Complete Local Name.
- Поддерживается до 32 недавно видимых BLE-устройств и до пяти настроенных
  имён маяков.
- Маяк сопоставляется только по имени, MAC-адрес для выбора не используется.
- Для каждого маяка отдельно хранятся RSSI, время последнего пакета,
  `requests_open`, блокировка повторного открытия и дедлайны таймеров.
- Таблицы и состояние защищены FreeRTOS mutex.

## 5. Существующий автомат открытия

Автомат полностью расположен в `main/ble_scanner.c` и сейчас тесно связан со
сканером.

Переход к запросу открытия происходит в `gap_event()` при достаточном RSSI:

- устанавливается `requests_open` конкретного маяка;
- фиксируется дедлайн «Долго открыт»;
- обновляется время достаточного RSSI для таймера А;
- вызывается `apply_aggregate_state()`.

`apply_aggregate_state()` объединяет запросы всех маяков по правилу OR:
открытие имеет приоритет. Результат сохраняется как логическое состояние
`BLE_LOCK_STATE_UNLOCKED/LOCKED`, записывается в журнал и передаётся RGB LED.

Критическое расхождение: в предоставленных исходниках не найден модуль или
вызов GPIO физического замка. Единственные вызовы обычного GPIO находятся в
`main/buzzer.c` и управляют буззером. Поэтому текущий «автомат открытия» меняет
программное состояние и LED, но по доступному коду не управляет исполнительным
GPIO замка. Номер GPIO замка также отсутствует в конфигурации.

## 6. Таймер А и таймер Б

Оба таймера обслуживаются задачей `monitor_task()` каждые 100 мс.

- Таймер А: `timer_a_ms`. Перезапускается каждым пакетом маяка с достаточным
  RSSI. По истечении снимает `requests_open`.
- Таймер Б в коде не называется `timer_b`. Его функциональному описанию
  соответствует `long_open_ms` / `long_open_deadline_ms` («Долго открыт»).
  Он не продлевается; по истечении закрывает состояние и блокирует повторное
  открытие от этого маяка.
- Блокировка снимается после трёх слабых пакетов или исчезновения маяка более
  чем на 15 секунд.

Алгоритмы этих таймеров на этапах добавления телефона изменять нельзя.

## 7. Wi-Fi, Web-интерфейс и OTA

Файлы: `main/main.c`, `main/web_ui.c`, `main/web_ui.h`.

- Wi-Fi работает в режиме STA, реквизиты заданы compile-time константами в
  `main/app_config.h`.
- HTTP server предоставляет главную HTML-страницу и JSON API состояния,
  конфигурации, устройств, маяков и событий.
- HTML встроен строкой `INDEX_HTML` в `main/web_ui.c`. Файл `main/index.html`
  CMake-сборкой не встраивается и фактически не используется.
- OTA реализован HTTP endpoint `/api/ota` через стандартные API ESP-IDF:
  `esp_ota_begin/write/end` и `esp_ota_set_boot_partition`.
- Таблица разделов содержит NVS, OTA data и два OTA app-раздела по 0x1E0000.

## 8. Хранение настроек

Файлы: `main/app_config.c`, `main/app_config.h`.

- Прикладные настройки хранятся в NVS namespace `blelock`.
- Сохраняются имена пяти маяков, пороги RSSI, длительности таймеров и GPIO
  буззера.
- Значения по умолчанию задаются в `app_config.h`.
- Записи подтверждаются `nvs_commit()`.
- Bonds NimBLE сохраняются стандартным NimBLE store во внутренней NVS.

## 9. Целевая архитектура по TASK_BLE_PHONE_ONLY_v2

В целевой версии используется один NimBLE host только для телефона. Роли
Observer/Central и логика поиска маяков удаляются. Включаются роли
Peripheral/Broadcaster, GATT Server, стандартные SMP Pairing/Bonding и
постоянное NimBLE NVS-хранилище bonds.

Планируемое разделение ответственности:

- `lock_control` — единственная точка управления физическим замком на GPIO 5;
  запросы BLE и тестовая команда Web проходят через этот интерфейс; здесь же
  сохраняется существующая семантика таймера А и таймера «Долго открыт»;
- `ble_phone` — единственный владелец NimBLE host, GATT service, advertising,
  GAP/SMP событий, 60-секундного окна регистрации, проверки encryption,
  bonded-состояния и RSSI;
- `app_config` — порог RSSI телефона со значением по умолчанию -68 dBm;
- `web_ui` — состояние регистрации, открытие 60-секундного окна, список bonds,
  удаление одного/всех bonds, порог RSSI, активный уровень открытия GPIO 5 и
  тест замка;
- стандартный NimBLE store — сохранение максимум 10 bonds во внутренней NVS.

Одновременно разрешено только одно BLE-соединение. При наличии 10 bonds новый
pairing отклоняется без автоматического удаления сохранённых записей.

Автомат открытия переносится из сканера без изменения принципа работы:

1. Разрешённая команда OPEN при достаточном RSSI снимает питание с GPIO 5,
   запускает таймер А и однократно запускает таймер «Долго открыт».
2. Каждое последующее подтверждение достаточного BLE RSSI до истечения таймера
   А сбрасывает таймер А и начинает его отсчёт заново.
3. Если подтверждений достаточного RSSI нет до истечения таймера А, питание
   электромагнита восстанавливается и замок закрывается.
4. Таймер «Долго открыт» не продлевается. Если он истёк, пока замок открыт,
   замок принудительно закрывается независимо от обновлений таймера А.
5. GATT callback не управляет GPIO напрямую: он передаёт событие в
   `lock_control`, а контроль времени выполняется отдельным безопасным
   контекстом FreeRTOS/ESP timer.

## 11. Риски

1. Замок является fail-safe электромагнитом: в запертом состоянии на него
   постоянно подаётся ток, для открытия питание снимается. Активный логический
   уровень «открыто» должен настраиваться через Web UI и сохраняться в NVS;
   противоположный уровень означает «закрыто». До загрузки настройки и при
   перезапуске существует риск краткого импульса неправильной полярности,
   поэтому начальная установка GPIO 3 должна быть выполнена как можно раньше.
2. Автомат таймеров А/«Долго открыт» должен быть перенесён из BLE Scanner в
   `lock_control` без изменения порядка проверок: в текущем коде таймер А имеет
   приоритет проверки перед таймером «Долго открыт» в одной итерации.
3. Текущие defaults явно запрещают Peripheral/Broadcaster; их необходимо
   согласованно изменить во всех конфигурационных файлах.
4. Для сохранения bonding потребуется стандартный NimBLE NVS store. Нужно
   исключить конфликт с прикладным namespace и проверить переживание reboot.
5. Выбор режима Pairing (Just Works или passkey) влияет на MITM-защиту и
   совместимость телефонов. Задача требует LE Secure Connections, но не задаёт
   возможности ввода/вывода passkey.
6. Проверка bonded должна учитывать resolvable private addresses телефона, а
   не сравнивать только текущий MAC.
7. RSSI соединения нужно получать стандартным GAP/HCI API непосредственно
   перед OPEN; RSSI advertising после подключения недостаточен.
8. Callback GATT нельзя блокировать и нельзя из него напрямую менять GPIO;
   запрос должен передаваться в автомат безопасно относительно FreeRTOS mutex.
9. Встроенный HTML и обработчики находятся в одном минифицированном C-файле;
    расширение повышает риск переполнения буферов JSON и лимита URI handlers.
10. Увеличение bonds с 3 до 10 расходует внутреннюю RAM/NVS; внешняя RAM
    запрещена. Число соединений при этом должно быть уменьшено с 3 до 1.
11. NimBLE API может не хранить человекочитаемое имя вместе с bond; Web UI
    должен честно показывать доступный identity address/type.
12. Гонка окончания 60-секундного окна и уже начавшегося Pairing должна иметь
    однозначное безопасное поведение.
13. Аппаратные критерии — Pairing, Bonding после reboot, RSSI и импульс GPIO 5 —
    нельзя полностью подтвердить одной компиляцией.

## 14. Аудит отдельной AP-ветки перед реализацией

Дата: 21.07.2026

### Исходная сборка

- Проект проверяется из отдельного каталога `AP` для ESP32-S3 и ESP-IDF 5.4.1.
- `idf.py build` не дошёл до CMake/Ninja из-за ограничения среды выполнения:
  Python не смог создать subprocess pipe (`PermissionError: [WinError 5]`).
- Прямой запуск CMake определил Xtensa C/C++/ASM-компиляторы, после чего
  завис на дочернем процессе Ninja. Повтор с отключённым сетевым менеджером
  компонентов дал тот же результат.
- Ошибок исходного кода компилятор на этой проверке не сообщил, однако полная
  успешная сборка в текущей среде не подтверждена. До её подтверждения
  функциональный код AP-ветки изменять нельзя.

### Текущее состояние заготовки

- `main/ap_mode.c` опрашивает GPIO0 каждые 20 мс, различает короткое нажатие и
  удержание не менее 3 секунд и вызывает callback. Модуль пока не вызывается
  из `app_main()`.
- `main/app_config.h` содержит SSID `lock`, GPIO0 и поле
  `configuration_mode`, но `app_config.c` это поле не инициализирует явно, не
  читает из NVS и не сохраняет.
- `LED_STATE_CONFIGURATION` объявлен, но `led.c` не сопоставляет ему цвет;
  фактически будет выбран цвет загрузки.
- Текущий `main.c` всегда запускает Wi-Fi STA с SSID `Cisco`, Web UI и BLE.
  Режим SoftAP, остановка Wi-Fi/Web UI и переключение режимов отсутствуют.
- `web_ui.c` предоставляет только `web_ui_start()`; безопасного
  `web_ui_stop()` пока нет.
- BLE-модуль предоставляет запуск, но не предоставляет остановку. Для
  подтверждённого поведения останавливать BLE в режиме настройки не требуется:
  регистрацию можно открыть существующим `ble_phone_allow_registration()`.

### Сохраняемые подсистемы и инварианты

- OTA остаётся частью существующего Web UI.
- BLE GATT, bonding, автоматическое открытие и алгоритмы таймеров А и
  «Долго открыт» изменять не требуется.
- Используется внутренняя NVS и штатные возможности Wi-Fi/BLE ESP-IDF;
  внешняя SPI RAM и собственная криптография не нужны.
- В нормальном режиме Wi-Fi и Web UI должны быть выключены, BLE должен
  продолжать работать.
- В режиме настройки требуется защищённый WPA2-PSK SoftAP `lock`, Web UI, синяя
  индикация и разрешение регистрации телефона.
- Длинное нажатие GPIO0 должно удалять bonds через существующий
  `ble_phone_delete_all_bonds()` и не должно переключать режим.

### Разрешение противоречия в плане

В ранней части `AP_MODE_PLAN.md` записано сохранение выбранного режима через
перезапуск, но подтверждённое решение ниже требует после каждого reboot или
пропадания питания запускать нормальный режим. При реализации приоритет имеет
последнее подтверждённое решение: настройки сохраняются в NVS, сам временный
режим настройки — нет.

### Безопасная последовательность реализации

1. Сначала получить успешную исходную сборку.
2. Добавить цвет конфигурации и проверить сборку.
3. Добавить управляемые start/stop для SoftAP и Web UI, не затрагивая OTA.
4. Подключить GPIO0 и переключение режимов через отдельный управляющий контекст,
   не выполняя тяжёлые Wi-Fi/BLE операции в обработчике GPIO.
5. После каждого этапа обновлять `CHANGELOG.md` и `TEST_REPORT.md` и выполнять
   полную сборку до начала следующего этапа.
## 15. Корневая причина отсутствующего SoftAP beacon

Дата: 22.07.2026

- Проблема воспроизведена отдельным минимальным проектом ESP-IDF 5.4.1 без
  BLE, Web UI и компонентов замка.
- UART подтверждает `AP_START`, WPA2, видимый SSID, канал 1 и DHCP, но два
  телефона и независимый адаптер компьютера не обнаруживают beacon.
- Та же плата с ESP-Easy передаёт WPA2 SoftAP с сигналом 96%, поэтому
  аппаратный RF-тракт работоспособен.
- Открытый issue Espressif `IDFGH-12498 / #13508` описывает тот же дефект:
  официальный SoftAP работает на ESP32, но не обнаруживается на ESP32-S3.
- В установленной среде доступен только ESP-IDF 5.4.1; для ветки 5.4 Espressif
  публикует более новые bugfix-релизы, включая 5.4.4.
- Исправлять проблему изменением архитектуры замка или собственной реализацией
  Wi-Fi/BLE протокола не следует. Требуется проверить исправленный официальный
  Wi-Fi stack Espressif.

Функции Web UI сопоставлены с существующими подсистемами. Настройки уже

# Дополнение: источник RSSI в приложении (22.07.2026)

- ESP32 уже публикует измеренный ею RSSI активного телефона в защищённой административной характеристике `ADMIN_STATE` (`rssi=<dBm>` или `rssi=NA`).
- Характеристика доступна только забонденному зашифрованному соединению и только в режиме настроек ESP32.
- Для отображения ESP-side RSSI новый GATT-сервис и изменение алгоритма замка не требуются; приложение может читать существующий `ADMIN_STATE` периодически.
- Android scan RSSI и `BluetoothGatt.readRemoteRssi()` измеряются телефоном и не должны использоваться для требуемой индикации.
- Первое значение ESP-side RSSI уже поступает в ответе на проверочное чтение `ADMIN_STATE`. Повторное немедленное чтение после подтверждения сервисного режима создаёт конкуренцию с `PHONE_NAME` и последующим чтением `ADMIN_BONDS`, поскольку Android GATT выполняет операции последовательно.
- Периодический опрос RSSI не должен использовать ошибку запуска чтения как фатальную: во время записи `ADMIN_CONFIG` репозиторий закономерно находится в `DISCOVERING`. Фоновое чтение в этот момент следует пропустить, сохранив сервисный режим и основную GATT-операцию.
- Успешный callback записи `ADMIN_CONFIG` означает, что ESP32 приняла значение: обработчик ESP сохраняет NVS и применяет конфигурацию до возврата успешного ATT-ответа. Дополнительное чтение из самого write callback не требуется и на части Android BLE-стеков не запускается, оставляя клиент в `DISCOVERING`.
# Дополнение: потеря BLE-соединения как слабый сигнал (22.07.2026)

- `LOCK_EVENT_RSSI_LOW` снимает защиту от повторного открытия после трёх последовательных слабых измерений и переводит LED закрытого замка из жёлтого в красный.
- До изменения `LOCK_EVENT_DISCONNECTED` только снимал вооружение открытия и намеренно не освобождал защиту; без соединения новые RSSI-измерения невозможны, поэтому защита могла остаться включённой неограниченно долго.
- При потере соединения открытый замок уже перестаёт получать `RSSI_HIGH`, поэтому существующий таймер А продолжает работать и закрывает замок без изменения алгоритма таймера.
- Требуемая интеграция ограничивается немедленным снятием защиты при disconnect; алгоритмы открытия и таймеров не меняются.

- Для надёжного распознавания 10 секунд требуется не только delayed Runnable, но и проверка фактической длительности между `ACTION_DOWN` и `ACTION_UP`.
- Живой ADB-тест показал зависание после service discovery при `bondState=BOND_NONE`: зашифрованное чтение `LOCK_INFO` не вызвало системный pairing и не вернуло callback. Для незабонденного устройства нужен один явный инициатор `BluetoothDevice.createBond()`; чтение следует выполнять только после broadcast `BOND_BONDED`, чтобы не создавать две параллельные SMP-процедуры.
- Первый ADB-тест после остановки фоновой службы не нашёл рекламу за 15 секунд, следующий тест нашёл ESP32 сразу. Пауза перед ручным сканированием должна дать службе закрыть GATT и ESP32 возобновить advertising.
- Системный Bluetooth dump телефона определяет ESP32 как LE (`DeviceType=2`, `TransportType=2`). Публичный SDK текущей сборки не предоставляет перегрузку `createBond(transport)`, поэтому транспорт нельзя задавать этим способом.
- На проверяемом телефоне `createBond()` после уже установленного GATT-соединения остаётся в `BOND_NONE`. Безопасная последовательность — после scan сначала bond, дождаться `ACTION_BOND_STATE_CHANGED/BOND_BONDED`, затем вызывать `connectGatt`; существующий receiver позволяет продолжить процесс без опроса.

- При отсутствии записи владельца первое успешное чтение `ADMIN_STATE` в режиме настройки сохраняет identity в отдельном NVS namespace `ble_owner`.
- При наличии владельца весь административный диапазон и запись имени разрешаются только совпадающему identity. Обычные lock-команды остаются доступны всем валидным bonds.
- Полный сброс bonds и удаление конкретного bond владельца должны очищать запись владельца, иначе восстановление доступа станет невозможным.

# Аудит надёжности и безопасности уровня банковского приложения — 18.08.2026

## Итог

Текущее состояние нельзя считать соответствующим банковскому уровню
надёжности или готовым к эксплуатации как защищённая система доступа.

Оценка: **условно пригодно для контролируемого прототипа, не готово для
production**.

Сборка Android перед аудитом прошла успешно (`:app:assembleDebug`). Аудит
выполнен статическим анализом исходников, конфигурации ESP-IDF и имеющихся
logcat; полноценное penetration-тестирование и длительная аппаратная
регрессия не выполнялись.

## Блокирующие риски

### CRITICAL-01 (латентный) — Web UI не имеет аутентификации и авторизации

Важно: **сейчас Web UI не используется в рабочем сценарии**. В `main/main.c`
нет вызовов `web_ui_start()` или `web_ui_stop()`, поэтому HTTP-сервер не
запускается. `main/web_ui.c` остаётся собранным, но неактивным резервным кодом.

Если этот интерфейс будет включён без доработки, он зарегистрирует без проверки
сессии, токена или пароля endpoints:

- `POST /api/lock/test` — открытие замка;
- `POST /api/config` — изменение логики и GPIO;
- `POST /api/ble/registration` — разрешение pairing;
- `DELETE /api/ble/bonds` — удаление ключей;
- `POST /api/ota` — запись произвольной прошивки.

Тогда защита фактически будет основана только на физическом включении режима
AP кнопкой GPIO0. Любой пользователь, получивший доступ к этой Wi-Fi сети,
получит полный административный контроль. Для банковского уровня это
неприемлемо. В текущем firmware этот риск неэксплуатируем через Web UI,
поскольку сервер не запущен.

### CRITICAL-02 — Secure Boot и Flash Encryption отключены

В текущем `sdkconfig`:

- `# CONFIG_SECURE_BOOT is not set`;
- `# CONFIG_FLASH_ENCRYPTION_ENABLED is not set`.

Следствия: физический атакующий может подменить прошивку, прочитать содержимое
flash/NVS и извлечь сохранённые Wi-Fi credentials, pairing-данные и настройки.
Один только `esp_ota_end()` не является доказательством доверенности образа.

## Высокие риски

### HIGH-01 — OTA доверяет любому HTTPS URL

`main/wifi_ota.c` проверяет URL только на префикс `https://` и использует общий
CA bundle. Сертификат сервера проверяется, но нет pinning доверенного домена,
проверки ожидаемого владельца сертификата или отдельной подписи релизного
артефакта. Компрометация DNS/аккаунта/релиза может привести к установке
вредоносного, но формально валидного HTTPS-образа.

### HIGH-02 — Wi-Fi пароль хранится в NVS открытым текстом

`main/wifi_ota.c` сохраняет SSID и пароль через `nvs_set_str()` без шифрования.
При отключённом Flash Encryption это практически доступные credentials. Даже
после включения шифрования требуется политика удаления/замены пароля и запрет
его вывода в диагностические дампы.

### HIGH-03 — Web OTA не ограничивает размер и тип образа

`ota_post()` принимает тело запроса напрямую в OTA partition. Не видно проверки
магического заголовка образа, ожидаемой модели чипа, версии, размера относительно
partition и отдельной подписи приложения. При отсутствии Secure Boot это
позволяет записывать неподконтрольный код.

### HIGH-04 — Нет production-процесса релизов Android

В `app/build.gradle.kts`:

- `versionCode = 1` остаётся постоянным;
- `versionName = "0.1.0"` остаётся постоянным;
- release `isMinifyEnabled = false`;
- конфигурация release-подписи и проверяемая цепочка артефактов в проекте не
  зафиксированы;
- CI, SAST, dependency scanning, SBOM и обязательные release gates не найдены.

Строка времени сборки полезна для диагностики, но не заменяет уникальную
версию, подпись и воспроизводимый релиз.

### HIGH-05 — Неполное доказательство восстановления BLE

Архитектура улучшена: один владелец BLE, Binder, очередь GATT, timeout,
backoff, режимы `AUTO_OPEN/ADMIN/OTA`, stale-callback guard. Однако текущие
logcat показывают реальные незавершённые сценарии:

- `LOCK_INFO -> TIMEOUT`;
- `ADMIN_STATE` с `status=133`;
- приложение остаётся в состоянии `READY`, но сервисная панель не открывается.

Это означает, что отказоустойчивость пока не подтверждена фактическими
тестами для GATT 8/19/133, reboot ESP32, Bluetooth OFF/ON и stale bond.

## Средние риски

### MEDIUM-01 — Открытая Web UI поверхность даже при физическом переключателе

Режим AP отключается вне configuration mode, что снижает риск. Но нет
rate-limit, CSRF-защиты, журнала субъекта запроса, подтверждения опасных
операций на сервере и отдельного read-only режима. Для банковского уровня
нужны server-side authorization checks на каждом endpoint.

### MEDIUM-02 — Android настройки не используют защищённое хранилище

`LockSettings` использует `SharedPreferences`. Сейчас там нет BLE bond keys и
нет Wi-Fi пароля, что хорошо, но это не универсальная гарантия на будущее.
Любые будущие credentials должны храниться в Android Keystore/Encrypted
storage, а не добавляться в обычные preferences.

### MEDIUM-03 — Статическая команда OPEN

Команда `OPEN` — фиксированные четыре байта. Защита опирается на системное BLE
шифрование, bonding, owner identity и RSSI-проверку ESP32. Это приемлемо в
рамках текущего ограничения «не создавать собственный протокол», но не даёт
защиты от использования уже скомпрометированного bonded-телефона и не даёт
криптографической защиты от replay внутри доверенного BLE-сеанса.

### MEDIUM-04 — Нет автоматизированной регрессии

В проекте не обнаружены unit-, integration-, instrumentation- или hardware-in-
the-loop тесты. `TEST_REPORT.md` в основном содержит ручные проверки и факт
сборки. Для банковского уровня нужны повторяемые тесты переходов состояний,
fault injection, OTA rollback и длительная работа foreground service.

### MEDIUM-05 — Диагностические логи потенциально раскрывают инфраструктуру

Логи содержат URL OTA, SSID и состояние подключения. Пароль явно не логируется,
что правильно, но production-сборка должна иметь контролируемый уровень логов,
redaction и запрет передачи диагностического журнала в UI без авторизации.

## Что уже сделано хорошо

- единственный BLE-владелец внутри `BleLockService`;
- Activity не создаёт отдельный GATT-клиент;
- сериализация ATT/GATT операций и таймаут активной операции;
- проверка актуальности `BluetoothGatt` в callback;
- ограниченный backoff реконнекта;
- отдельные режимы автоматического управления, admin и OTA;
- `android:allowBackup="false"`;
- service и внутренний restart receiver не экспортированы;
- защищённые BLE characteristics используют `READ_ENC/WRITE_ENC`;
- ESP32 проверяет `encrypted`, `bonded`, owner identity и RSSI для admin/OPEN;
- OTA через ESP32 использует HTTPS и CA bundle;
- OTA partition scheme использует две app-партиции (`ota_0`, `ota_1`);
- pairing лимитирован 20 bonds и окно регистрации ограничено 60 секундами.

## Приоритетный план до production

1. Включить Secure Boot v2 и Flash Encryption в production-конфигурации,
   организовать безопасное provision-производство ключей и recovery-процедуру.
2. Закрыть Web UI server-side аутентификацией/авторизацией; опасные endpointы
   должны требовать отдельного подтверждения и иметь audit log.
3. Сделать OTA доверенным: подписанные образы, проверка версии/rollback,
   фиксированный доверенный endpoint либо pinning; закрыть Web OTA тем же
   контролем доступа.
4. Ввести release pipeline Android: уникальный versionCode, release signing,
   minify/R8, SBOM, dependency/SAST scanning, проверяемые артефакты и
   двухэтапное одобрение релиза.
5. Добавить автоматические тесты BLE state machine и аппаратную матрицу:
   GATT 8/19/133, MTU failure, stale bond, reboot, Bluetooth OFF/ON, screen
   off, process kill, MIUI cleanup, OTA failure и rollback.
6. Исправить текущий admin-handshake `status=133`: различать временный GATT
   сбой и отказ авторизации, закрывать зависший сеанс и не показывать
   «обычный режим» как окончательный результат до завершения recovery policy.
7. После выполнения пунктов провести независимый security review и
   penetration-тестирование на физическом устройстве.
