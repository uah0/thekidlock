# AUDIT

## 09.10.2026 — повторное сопряжение после включения ESP

До изменений успешно собраны ESP signed-dev 405 и Android 247. ESP 405 установлен через зашифрованный OTA, версия проверена. Телефон подключён ADB 192.168.1.65:35329.
Логи подтверждают одностороннее состояние пары: ESP PEER_SEC LTK=1 SC=1; Android BOND_NONE, затем CONSENT и BOND_BONDING, разрыв через 10 секунд. В IDF 5.4.4 ble_sm_process_result автоматически запускает pairing при PINKEY_MISSING (BLE_RESTART_PAIR=1), обходя окно регистрации проекта; ble_sm_sec_req_rx также может начать pairing. Исправление: проверять разрешение проекта перед любым central pairing и перед автоматическим restart, сохранять ошибку восстановления для GAP callback при запрете. В разрешённом окне восстановление пары учитывается как новое SMP с ожиданием подтверждения и выдержкой существующих 5 секунд после bonding. Вне окна запрещённый peer подавляется для AUTO и service до явного открытия регистрации. Автоматически ключи и owner не удалять. Не менять криптографию, разметку, eFuse, алгоритм открытия и таймеры замка. Причина отсутствия ключа Android пока не установлена; исчезновение диалогов само по себе не доказывает восстановление работы.

Проверка 406 на устройстве подтвердила точную причину запуска цикла: восстановление LTK получает PINKEY_MISSING (HCI 0x06 / GAP 518), штатный NimBLE автоматически начинал новый SMP. Новый guard сохраняет ошибку для ENC_CHANGE, не отправляет Pairing Request вне окна и не удаляет ключ. После явной регистрации сохранённый ключ успешно восстанавливается, включая программный перезапуск ESP и запрос Web UI. Почему прежний Android-ключ отсутствовал, по доступным журналам определить нельзя.
