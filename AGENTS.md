# ESP32 BLE Lock Project

## Общие требования

Проект разрабатывается для:

- ESP32-S3
- ESP-IDF 5.4.4
- Android-приложение находится в `android_lock_beacon`

Работать необходимо только с существующим проектом.

Не переписывать архитектуру без необходимости.

Основной принцип:

Максимально использовать существующий код.

Новые возможности должны интегрироваться в существующий проект, а не заменять его.

---

## Локальное окружение и сборка

Использовать проектные скрипты из корня репозитория.

ESP32:

```powershell
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File .\build-esp32.ps1
```

Android:

```powershell
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File .\build-android.ps1
```

Не считать отсутствие глобальных `idf.py`, `JAVA_HOME`, `ANDROID_HOME` или `ANDROID_USER_HOME` ошибкой окружения, если соответствующий проектный скрипт успешно собирает проект.

ESP-IDF управляется через EIM. Рабочая версия проекта: `v5.4.4`.

Android использует JBR из Android Studio и Android SDK из `%LOCALAPPDATA%\Android\Sdk`.

Изменяемое состояние Gradle/Android должно храниться внутри репозитория:

- `.gradle-codex`
- `.android`

Не использовать старые машинозависимые пути, включая:

- `C:\jdk17`
- `C:\Users\User`
- `C:\Espressif\frameworks\esp-idf-v5.4.4`
- `C:\.android`
- старые пути проекта на дисках `D:` или `F:`

Каталог `build` ESP-IDF содержит машинозависимый CMake cache. После переноса проекта между каталогами или дисками его разрешено удалить и пересоздать сборкой.

# Перед началом любых изменений

Обязательно:

1. Собрать затрагиваемую часть проекта без изменений проектным скриптом.
2. Убедиться, что она успешно компилируется.
3. Выполнить аудит относящейся к задаче архитектуры.
4. Создать или актуализировать `AUDIT.md`, если задача предполагает изменение кода.

Если задача относится только к Android, ESP32-сборка не обязательна.
Если задача относится только к ESP32, Android-сборка не обязательна.

До завершения обязательной проверки затрагиваемой части код не изменять.

# Обязательные ограничения

Запрещается:

- удалять OTA;
- удалять Wi-Fi;
- удалять Web-интерфейс;
- удалять существующий BLE Scanner;
- удалять поддержку существующих BLE-маяков;
- менять алгоритм открытия замка;
- менять алгоритм таймеров А и Б без отдельного обоснования;
- использовать внешнюю SPI память;
- реализовывать собственную криптографию;
- реализовывать собственный протокол шифрования.

Использовать только стандартные возможности BLE.

# После каждого этапа

После каждого законченного этапа необходимо:

- собрать затронутую часть проекта соответствующим проектным скриптом;
- перечислить изменённые файлы;
- актуализировать `CHANGELOG.md`;
- актуализировать `TEST_REPORT.md`;
- дождаться успешной сборки перед следующим этапом.

При ошибке сборки дальнейшие изменения запрещены до устранения ошибки сборки.

# Стиль разработки

Предпочитать небольшие изменения.

Не выполнять массовый рефакторинг.

Не менять форматирование файлов без необходимости.

Изменять только те файлы, которые действительно относятся к задаче.

Не изменять существующие незакоммиченные пользовательские изменения, если они не относятся к текущей задаче.

# Android

Android-проект: `android_lock_beacon`.

Для локальной debug-сборки использовать:

```powershell
pwsh.exe -NoProfile -ExecutionPolicy Bypass -File .\build-android.ps1
```

Не требовать отдельной глобальной установки JDK, если JBR Android Studio доступен и проектный скрипт работает.

Не создавать и не требовать Android Emulator или AVD: тестирование выполняется на физическом Android-устройстве.

Для установки debug APK допускается ADB по Wi-Fi.

Перед каждой установкой APK через ADB обязательно прочитать и сохранить системные
значения Android `accelerometer_rotation` и `user_rotation`. После установки APK
восстановить оба исходных значения и проверить их повторным чтением. Установка или
запуск приложения не должны включать автоповорот либо изменять выбранную пользователем
ориентацию экрана.

Не менять signing configuration, `applicationId`, `versionCode` или release-настройки без явной необходимости задачи.

## Необратимая защита флеша — 09.10.2026

Необратимые изменения eFuse, включение аппаратного Secure Boot и Flash Encryption
в Release-режиме, блокировка JTAG, ROM Download и других физических интерфейсов
доступа к флешу допускаются только после отдельного явного разрешения пользователя
на конкретную операцию. Успешные сборки, тесты OTA, указание «приступай» и общее
разрешение на прошивку не являются разрешением на такие действия.

До получения этого разрешения сохранять возможность восстановления текущего
замка, не прожигать eFuse и не загружать профили/загрузчики, которые изменяют eFuse
при первом запуске. Это ограничение имеет приоритет над правилом автоматической
прошивки после сборки. Проверки зашифрованного OTA выполнять без необратимых
изменений аппаратной защиты.

## Прошивка после сборки

По указанию пользователя от 24.09.2026 после каждой успешной сборки целевой
ESP32-прошивки сразу загружать её на текущий замок и проверять возврат устройства
и firmware_version. Дополнительное подтверждение не требуется. Предпочитать
существующий device-agent.ps1/OTA. При недоступности устройства сообщить об этом;
не считать одну успешную сборку успешной прошивкой. Изолированные тестовые примеры
других устройств (например relay example) на замок не загружать.

Отложенные требования пользователя выполнены в ESP build 340:
