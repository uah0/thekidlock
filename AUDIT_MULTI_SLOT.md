## Текущее BLE-состояние в `main/ble_phone.c`

Один `portMUX_TYPE s_connection_lock` защищает singleton-состояние в строках
85–106. Перечисленные ниже поля описывают единственное соединение:

| Поле | Текущие использования и значение |
|---|---|

Используется в `ble_phone_get_status` (182), `disconnect_deleted_peer` (262, 273), включении и выключении окна регистрации (404, 423, 433), `BLE_GAP_EVENT_CONNECT/DISCONNECT` (986, 1055), watchdog/RSSI цикле (1165, 1213, 1230, 1249, 1273). ## Места, предполагающие одно подключение

- `ble_phone_get_status` (178–187) выдаёт один `connected/encrypted/bonded/rssi`.
  Его читает `CHR_ADMIN_STATE` (gatt_access около 727–744) и использует
  `start_advertising_on_host` (1362–1366) как запрет рекламы при любом активном
  handle. При нескольких слотах status должен стать совместимым агрегированным
  summary, а решение о рекламе — проверять наличие свободного слота напрямую.
- `disconnect_deleted_peer` (258–281) берёт только `s_conn_handle`; удаление bond
  конкретного peer и удаление всех bonds не могут разорвать все соответствующие
  параллельные сессии. `ble_phone_delete_bond/delete_all_bonds` вызывают этот helper
  (347–390).
- `ble_phone_allow_registration` и `ble_phone_set_registration_mode` (392–440)
  читают один handle и разрывают его, чтобы освободить единственный слот для
  pairing. При multi-slot нужно пройти по занятым слотам, сохранив текущее
  поведение регистрации (освобождение существующих связей перед окном pairing).
- `connection_is_admin(conn_handle)` (483–494) уже корректно использует handle,
  descriptor peer identity, encrypted/bonded и сравнение с сохранённым owner.
  Поиск администратора по глобальному текущему handle не нужен; функция может
  остаться без изменения.
- `gatt_access` (496 и далее) в большинстве защищённых операций проверяет именно
  `conn_handle` через descriptor/`connection_is_admin`. Особый случай — команда
  `OPEN` (около 575–605): проверяет encrypted/bonded вызывающего, но использует
  глобальный `s_last_rssi/s_rssi_valid`. После миграции RSSI необходимо получать
  из слота именно вызывающего handle; иначе сильный сигнал одного телефона может
  разрешить `OPEN` другому.
- `BLE_GAP_EVENT_CONNECT` (977–1050) перезаписывает singleton handle, очищает одну
  медиану и записывает общие peer/bond flags. `ble_gap_conn_find` уже используется
  далее в `peer_has_bond`; распределение слотов должно брать `peer_id_addr` из
  descriptor нового handle. `BLE_GAP_EVENT_DISCONNECT` (1052–1065) безусловно
  очищает все singleton поля. С несколькими соединениями он должен очищать только
  совпавший слот и перезапускать advertising лишь согласно наличию свободных слотов.
- `BLE_GAP_EVENT_ENC_CHANGE` (1066–1140) работает с общими encryption/bond и
  registration-candidate flags. При multi-slot каждый переход безопасности и
  результат pairing должен обновлять только слот события. Сохранение первого
  bonded peer назначает его owner (1097–1119): если owner до pairing не существовал,
  новый owner первоначально классифицирован как гость; после успешного `owner_save`
  его слот нужно повысить/переместить в индекс 0, который до назначения owner
  зарезервирован и свободен.
- В `rssi_task` (1153–1335) singleton handle и локальные timers
  `tracked_conn_handle`, `weak_ble_rssi_since_ms`, `link_probe_failure_since_ms`,
  `link_terminate_retry_ms` принадлежат одному линку (1155–1159). При цикле по
  слотам все три таймера слабого линка/probe должны тоже быть per-slot, иначе
  результат одного телефона будет сбрасывать grace другого. Проверка registration
  candidate, stale-handle очистка, median, terminate и RSSI reporting сейчас
  адресуют только `s_conn_handle` (1165–1331).
- Watchdog advertising и обновление accept-list внутри `rssi_task` выполняются
  только при `conn_handle == NONE` (около 1170–1200). Для multi-slot условием
  продолжения рекламы должно стать наличие хотя бы одного свободного слота;
  проверка/обновление bond accept-list не должна прекращаться только потому, что
  один из слотов занят.
- `start_advertising_on_host` (1362–1411) запрещает рекламу по агрегированному
  `status.connected`; остальной код функции уже строит accept-list из полного
  списка bonds и сохраняет fallback на открытую рекламу при превышении лимита.
  Логику accept-list/лимит менять не требуется.
- При втором одновременном подключении сохранённого owner к уже занятому slot 0
  выбрано поведение: разрывать новый handle и сохранять старую owner-сессию. Это
  исключает неоднозначный admin/RSSI контекст без затрагивания первой связи.

## Агрегация сигналов `lock_control`

Сейчас `rssi_task` вызывает `lock_control_report_rssi(sufficient)` один раз на
единственную зашифрованную/bonded связь после медианы RSSI (около 1290–1327).
На любой `BLE_GAP_EVENT_DISCONNECT` и на очистку устаревшего handle вызывается
`lock_control_report_disconnected()` (1063, 1244).

`lock_control` — общий автомат: `RSSI_HIGH` обновляет общий момент присутствия и
может открыть/удержать один замок; `RSSI_LOW` меняет общий reopen-blocked/timer B;
`DISCONNECTED` сбрасывает `open_armed` и считает соединение отсутствующим
(`lock_control.c`, обработка событий 205–267). Поэтому будущая реализация должна:

1. Обрабатывать все занятые слоты одним `rssi_task`; после цикла формировать одно
   агрегированное событие RSSI, а не отправлять конфликтующие HIGH/LOW подряд.
   HIGH выдавать, если хотя бы один encrypted+bonded слот имеет валидную медиану
   выше эффективного порога; LOW — если валидные медианы есть и ни один такой слот
   не проходит порог. Сравнение использует текущую общую политику порогов, включая
   hold threshold для уже открытой/заблокированной двери.
2. Вызывать `lock_control_report_disconnected()` только при переходе агрегированного
   множества пригодных secured-связей из непустого состояния в пустое, а не при
   отключении произвольного гостя. Иначе уход одного телефона сбросит armed/presence
   другого.
3. Не менять `lock_control.c` и ULP. `lock_control_is_open()` — глобальный факт
   физического состояния, а не атрибуция открывшего телефона; при admission-policy
   это может консервативно защищать все гостевые слоты, пока замок открыт.

## Важные детали реализации после аудита

- Предложенной структуры слота недостаточно для изоляции существующих grace-таймеров:
  добавить в slot per-connection поля для слабого BLE RSSI grace, probe-failure grace
  и повторной попытки terminate, сохранив исходные 6000 мс и остальные значения.
- Слот 0 никогда не назначать гостю. Bonded owner классифицировать по
  `peer_id_addr`, owner при одновременной конкуренции за slot 0 отклонять новым
  подключением; все пять гостевых слотов искать отдельно в индексах 1–5.
- Первое pairing до назначения owner должно после успешного сохранения owner
  повысить guest slot этого же handle до owner slot 0.
- Гостевое выселение по порогу открытия применять только к индексам 1–5, с grace
  1500 мс, и не применять, когда общий замок уже открыт. Существующий disconnect
  threshold/grace остаётся отдельным правилом.
- Изменения Android, GATT UUID/формата, pairing/security, `lock_control.c`, ULP,
  Web UI/API и accept-list лимита не требуются.

## Этапы 3–4 — owner reservation и реклама при свободном слоте

Слот 0 выделяется только bonded owner, определяемому по `peer_id_addr`;
дубликат owner handle отклоняется с сохранением уже активной сессии. Гости ищут
свободные слоты только 1–5. При первом pairing владельца текущая сессия переносится
из guest slot в слот 0. `ble_phone_get_status()` предпочитает owner-слот, иначе
показывает первый занятый guest. Реклама поддерживается, пока свободен любой слот,
и останавливается через NimBLE host event при заполнении всех шести слотов.
Успешное подключение явно ставит host work item на возобновление рекламы.
Этап 3: build/OTA PASS `10.0.195→10.0.196`; этап 4: build/OTA PASS
`10.0.196→10.0.197`. После этапа 4 устройство вернулось; один connected,
encrypted, bonded телефон, `OPEN_HOLD`, `fault_flags=0`. Многотелефонный сценарий
пока не запускался.

## Этап 5 — освобождение слабого гостевого слота

Добавлена отдельная per-slot шкала `weak_signal_since_ms` для secured guest
слотов. Она начинает отсчёт только после появления валидной медианы из трёх RSSI
значений; если RSSI достигает `phone_rssi_threshold` или дверь в открытом/
hold-open состоянии, отсчёт сбрасывается. Через 1500 мс непрерывного валидного
RSSI ниже порога соединение завершается. Slot 0 всегда исключён. Старые 6000 мс
для `ble_disconnect_rssi_threshold` сохранены отдельно в `weak_ble_rssi_since_ms`.
Build/OTA PASS `10.0.197→10.0.198`; устройство вернулось, текущая bonded/encrypted
сессия, `OPEN_HOLD`, `fault_flags=0`. Выселение на телефонах с искусственно
ослабленным сигналом аппаратно не проверено.

## Этап 6 — диагностика

В `rssi_task` раз в 10 секунд печатаются индекс, owner flag, handle, last RSSI,
валидность RSSI и время старта слабого admission RSSI через `ESP_LOGI`; новая
FreeRTOS-задача не добавлялась. Финальный build/OTA PASS `10.0.198→10.0.199`;
Agent API подтвердил тот же device id с новым boot id. На устройстве остался один
connected/encrypted/bonded клиент; журнал содержит штатный `BLE admin: чтение
состояния`, `BLE OPEN принят`, состояние `OPEN_HOLD`, fault_flags=0. Через Agent
monitor подтверждён периодический вывод всех шести слотов: slot 0 показывает
`owner=1 handle=1`, guest slots пусты. Сценарии с 5 гостями + владельцем физически
не проверялись. После проверки формата ESP_LOGI аргументов выполнен финальный
повторный build/OTA `10.0.199→10.0.200`; устройство снова вернулось на Agent API.

## Непроверенные аппаратные критерии и ограничения

- В окружении обнаружен только один Android endpoint (ADB не перечислил устройства),
  поэтому не были созданы пять гостевых bonds, не проверены шестой гость и owner при
  полностью заполненных guest slots.
- Не выполнялся RF-тест длительного слабого RSSI, чтобы искусственно не менять
  окружение/положение замка; отсчёт реализован по валидной медиане 3 измерений.
- Общий lock state не сообщает, какой именно телефон открыл дверь. Поэтому новый
  guest eviction при глобально открытой/hold-open двери консервативно откладывается
  для всех гостей; это предотвращает отключение человека, удерживающего дверь.
- RSSI-task stack high-water значение менялось между запросами Agent API
  (1248–2576 отображаемых байт на коротких smoke-снимках). Это не worst-case
  измерение шести подключений и требует нагрузочной проверки при аппаратной приёмке.
