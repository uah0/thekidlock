# Аудит Android-приложения TheKidLock

## Немедленное закрытие при выходе из Always Open — 28.09.2026

- Android посылал `MODE_AUTO` при снятии Always Open. В `lock_control.c` эта
  команда снимала hold, но намеренно сохраняла физический запрос OPEN и вызывала
  `apply_state(true)`, поэтому статус возвращался обычный `OPEN`, а замок не
  закрывался.
- Для возврата из Always Open приложение теперь выбирает существующий
  `AUTO_OFF_CLOSE`, который очищает hold и ставит физический запрос закрытия.
  Другие переходы на `MODE_AUTO` оставлены без изменения.
- Повторное нажатие самой кнопки Always Open также выключает и сохраняет
  выключенное автооткрытие, чтобы близкий телефон не отменил закрытие. Переход
  через кнопку AUTO закрывает замок, затем возобновляет автооткрытие после
  подтверждения статуса замка.
- Проверка на устройстве выявила оставшийся native presence latch после явного
  `AUTO_OFF_CLOSE`. При подтверждённом `LOCKED` после сброса Always Open сервис
  теперь очищает этот latch, чтобы последующее включение AUTO могло снова
  отправить OPEN при близком телефоне.
- На build 107 завершён полный прогон AUTO (`OPEN`) → Always Open (`OPEN_HOLD`)
  → сброс (`LOCKED`) → AUTO (`OPEN`) → AUTO off (`LOCKED`). После выключения
  автооткрытия замок остался `LOCKED`, `hold_open=false` при RSSI `-38 dBm`.

## Диагностика автооткрытия — 28.09.2026

- На Xiaomi `2510DRA23E` BLE GATT и encrypted/bonded соединение успешны; ESP
  отвечает на `LOCK_STATUS`. Порог телефона — `-62 dBm`, RSSI соединения в
  наблюдаемом интервале был примерно `-59…-52 dBm`.
- После перезапуска сервиса приложение зарегистрировало
  `AUTO_OPEN_RSSI_THRESHOLD_REACHED` при `-59 dBm`, отправило `OPEN`; ESP
  записала `BLE OPEN принят`, ULP подтвердил OPEN, а read-only status показал
  `open=true`, `locked=false`. Радио, bonding и передача команды работают.
- Дальше сервис регулярно фиксировал `AUTO_OPEN_SUPPRESSED` при RSSI выше
  порога с причиной `nativeOpenSent=true`. Это ограничение «один OPEN за
  присутствие»: после одной отправки native auto-connect не посылает повторный
  OPEN, пока его логика не подтвердит departure/re-arm. Поэтому при текущем
  присутствии замок остаётся без новой команды открытия.
- Логи ESP дополнительно зафиксировали `AUTO_OFF_CLOSE`, после которого замок
  стал `LOCKED`. Кнопка AUTO — переключатель режима: повторное нажатие активной
  AUTO вызывает `setAutomaticMode(false)` и отправляет `AUTO_OFF_CLOSE`; это не
  кнопка разового открытия.
- Для наблюдения за причиной добавлен редкий (не чаще раза в 5 секунд) лог
  `AUTO_OPEN_SUPPRESSED` с конкретным блокирующим флагом. Финальная диагностика
  не меняла BLE/lock алгоритм. `gradlew test` и `build-android.ps1` прошли;
  диагностическая сборка 101 установлена, ориентация экрана восстановлена `0/0`.
- Исправление: сервис помечает присутствие обработанным только при успешной
  записи конкретной команды `OPEN`; успешные GATT writes режимных команд и
  `AUTO_OFF_CLOSE` больше не устанавливают этот флаг. Повторный цикл разрешается
  после реальной последовательности `LOCK_STATUS=OPEN`, затем `LOCKED`; один
  старый `LOCKED` не сбрасывает guard. При подтверждённом цикле сбрасывается
  также native auto-connect latch репозитория. Добавлены unit tests gate-а.
  Проверки `gradlew test` (debug/release) и `build-android.ps1` успешны; сборка
  103 установлена на Xiaomi, настройки ориентации восстановлены `0/0`. Live
  logcat после установки подтвердил `AUTO_OPEN_REARMED`, затем новый
  `AUTO_OPEN_RSSI_THRESHOLD_REACHED`; read-only status в коротком окне оставался
  `OPEN`, ошибок AndroidRuntime не обнаружено.

## Подтверждённое состояние двух mode-кнопок — 28.09.2026

- Baseline `build-android.ps1` до изменения прошёл (`assembleDebug`). До
  переработки `MainActivity` параллельно reducer-у хранила шесть mutable-флагов;
  `onLockData()` завершал любой pending по любому известному статусу, click
  handler менял локальный state AUTO, а GATT write переводил repository в
  `OPEN_SENT` до последующего чтения `LOCK_STATUS`.
- Теперь единственный state кнопок — `WorkingModeState` в reducer-е:
  `confirmedLockMode` меняется только по `LOCK_STATUS` (`OPEN_HOLD` →
  `ALWAYS_OPEN`; `OPEN`/`LOCKED` → `AUTO`), состояние автоматического сервиса
  отдельно подтверждается binder snapshot или `ACTION_AUTOMATIC_MODE`, а
  пользовательский запрос хранится как `transition`.
- `AUTO` selected вычисляется из подтверждённых `AUTO` + service active;
  `Always Open` selected — только из подтверждённого `OPEN_HOLD`. Pending не
  скрывает последнее подтверждённое выделение и блокирует повторные клики.
  GATT success и `OPEN_SENT` сами по себе reducer-у подтверждение не дают.
- Переход в Always Open завершается только `OPEN_HOLD`; переход в AUTO — только
  `OPEN`/`LOCKED`, затем при необходимости ожидается фактический запуск сервиса.
  Неподходящий или неизвестный статус не завершает переход. Timeout очищает
  только pending и запрашивает status; disconnect очищает pending и переводит
  режим замка в `UNKNOWN`. Ошибка записи сохраняет последнюю подтверждённую
  индикацию.
- Bind синхронизирует состояние из `LocalBinder.automaticModeActive`; кэш
  статуса замка выдаётся Activity только при активном `READY` GATT-соединении.
- Добавлены reducer-тесты для unknown/READY, обеих последовательностей
  переключения, отключения AUTO, отказа записи, timeout, disconnect,
  несовместимых stale status, повторных событий и позднего timeout.
- Проверки после изменения: `gradlew test` — PASS; `build-android.ps1`
  (`assembleDebug`) — PASS. Debug APK установлен на Xiaomi 2510DRA23E;
  `accelerometer_rotation` и `user_rotation` до/после установки — `0/0`.

## Непрерывный активный scan до обнаружения замка — 28.09.2026

- Baseline `build-android.ps1` до изменения прошёл (`assembleDebug`).
- Свежий logcat Xiaomi при включённом экране показывает callback-результаты от
  замка; слабый тон ограничен debounce 1,5 с. Поэтому редкие звуки не означают,
  что callback-события тоже редкие.
- До изменения `findAndConnect()` останавливал `LOW_LATENCY` scan через 15 с,
  переводил репозиторий в ERROR, после чего сервис запускал новый scan с
  экспоненциальным backoff до 30 с. Эти интервалы создавали программные слепые
  окна.
- Удалён только timeout обычного discovery scan: он остаётся `LOW_LATENCY` и
  с Service UUID filter до объявления замка или ошибки Android BLE API. После
  принятого результата scan по-прежнему останавливается перед GATT. Departure
  scan и GATT error recovery не менялись.
- Android/MIUI по-прежнему могут приостанавливать callbacks; приложение не может
  гарантировать радиорезультаты поверх системных ограничений Doze.

## Настраиваемая пауза восстановления BLE security — 27.09.2026

- До изменения `BleRepository` использовал фиксированные 700 мс в двух точках:
  после обнаружения GATT-сервисов и после MTU callback перед первым защищённым
  запросом. В AUTO control-only сценарии применима первая точка; вторая относится
  к MTU negotiation flow. Обе точки читают общее значение настройки.
- ESP Web UI не может напрямую менять локальную задержку Android. По решению
  пользователя настройка добавляется рядом с RSSI-порогом в Android UI и
  сохраняется локально через `LockSettings`; BLE/GATT протокол не меняется.
- Диапазон 0…2000 мс, шаг ползунка 50 мс, значение по умолчанию 700 мс.
  Репозиторий читает значение при планировании паузы; изменение применяется к
  последующим этапам подключения и новым подключениям без перезапуска сервиса.

## Архитектура фонового BLE-обнаружения — 26.09.2026

- В текущем рабочем дереве уже существует `PassiveBleScan`: UUID-filtered
  PendingIntent scan настроен на `SCAN_MODE_LOW_POWER`, а UUID прошивки
  `6f4f0001-9a7b-4c21-8d32-5e6f708192a3` действительно присутствует в BLE
  advertising (`main/ble_phone.c`). `BleScanReceiver` извлекает и проверяет
  свежий `ScanResult`; gate не пропускает параллельные события; сервис вызывает
  прямой `connectDetectedDevice()` и сохраняет существующую GATT/auth/open логику.
- AUTO при отсутствии замка уже переведён на регистрацию PendingIntent scan.
  Остались callback LOW_LATENCY scan и timeout 15 секунд только в обычном
  `BleRepository.findAndConnect()` (ADMIN/UI discovery); экспоненциальный
  reconnect в `BleLockService.scheduleReconnect()` вызывается при ADMIN recovery.
  В обычной ветви AUTO `scheduleReconnect()` повторно регистрирует passive scan.
- `waitForDeparture()` — отдельная UUID-filtered BALANCED callback scan фаза
  после OPEN. Она сбрасывает `openSentForPresence` после 20 секунд без рекламы
  и позволяет прежнему циклу защиты от повторного OPEN сохраниться.
- Убран 30-секундный `departureRecovery`, который мог запускать старый
  `findAndConnect()` без нового рекламного события. При возвращении замка
  подключение во время departure-фазы происходит по полученной рекламе; обычное
  ожидание снова использует PendingIntent.
- Receiver сейчас делает короткую передачу обнаруженного `BluetoothDevice`
  работающему `BleLockService` через `startService()`. Если Android завершил
  service/process до события, поведение этого вызова необходимо проверить на
  реальном API 31+ устройстве: PendingIntent способен разбудить процесс, но
  background FGS start ограничен. Целевой SDK проекта — 36; service объявлен
  `connectedDevice`. Boot/package-replaced receivers восстанавливают AUTO при
  выданных разрешениях. Force Stop и OEM ограничения остаются системными.
- Добавлены unit tests для auto-open/permissions/Bluetooth policy, UUID/возраста
  результата и idempotency gate. Baseline `build-android.ps1` без изменений:
  PASS. После изменений: `testDebugUnitTest` — PASS, `build-android.ps1` — PASS.

## 3. Проверенный GATT-контракт

- Advertising name: `BLE Lock`.
- Service UUID: `6f4f0001-9a7b-4c21-8d32-5e6f708192a3`.
- INFO UUID: `6f4f0002-9a7b-4c21-8d32-5e6f708192a3`, READ + READ_ENC.
- COMMAND UUID: `6f4f0003-9a7b-4c21-8d32-5e6f708192a3`, WRITE + WRITE_ENC.
- STATUS UUID: `6f4f0004-9a7b-4c21-8d32-5e6f708192a3`, READ + READ_ENC.
- Команда: ровно четыре байта UTF-8/ASCII `OPEN`.
- INFO возвращает `BLE Lock <version>`; STATUS — `OPEN` либо `LOCKED`.
- ESP32 дополнительно проверяет `encrypted`, `bonded` и connection RSSI до
  помещения OPEN в очередь автомата.

Следствие: Android должен сначала подключиться и открыть service discovery.
Обращение к encrypted characteristic инициирует системный bonding при открытом
окне регистрации. Запись OPEN выполняется только после `BOND_BONDED`; окончательное
решение всё равно остаётся на ESP32.

## 5. Состояния автомата приложения

`STOPPED -> PERMISSION_REQUIRED -> SCANNING -> CONNECTING -> BONDING ->
DISCOVERING -> READY -> OPEN_SENT -> COOLDOWN/DISCONNECTED`.

- Scan фильтруется по service UUID и останавливается при нахождении.
- После ошибки применяется ограниченный backoff.
- В одном цикле соединения OPEN отправляется не более одного раза.
- Повторный цикл начинается после disconnect/ухода, а ограничения повторного
  физического открытия дополнительно обеспечивает ESP32.

## 7. Риски

1. Без локального Android/Kotlin Gradle plugin и без доступа к Maven/Google
   repository APK не соберётся, даже если исходники корректны.
2. Системный PATH выбирает Java 8; Gradle/AGP требуют JDK 17.
3. Android-производители ограничивают фоновые процессы; foreground service и
   исключение из battery optimization повышают надёжность, но не дают абсолютной
   гарантии на каждом телефоне.
4. Android 12+ и 13+ имеют разные runtime permissions; старые версии требуют
   location permission для scan.
5. Bonding — асинхронный системный процесс. Нельзя считать успешным только вызов
   `createBond()`; нужно ждать broadcast `BOND_BONDED`.
6. Encrypted characteristic может вернуть authentication error до завершения
   bonding; требуется корректное ожидание и повтор операции, не цикл запросов.
7. В ESP32 разрешено одно соединение. nRF Connect или другой телефон может
   занять его и помешать приложению.
8. RSSI в Android не является решающим: итоговый порог применяется ESP32.
9. Непрерывный low-latency scan расходует батарею; нужны окна scan и backoff.
10. Автозапуск foreground service после boot ограничивается версиями Android;
    manifest и поведение необходимо проверять на целевом телефоне.
11. Удаление bond только на одной стороне приводит к security failure; UI должен
    дать инструкцию удалить bond и в Web UI ESP32, и в Android.
12. До реального телефона нельзя подтвердить открытие из кармана, работу при
    погашенном экране и расход за 8 часов.

## Звуковые сигналы событий BLE — 28.09.2026

- Принятая реклама обрабатывается в `BleRepository.scanCallback.onScanResult`;
  сигнал обнаружения поставлен после RSSI-проверки, перед остановкой сканирования
  и запуском GATT. Слабые и отфильтрованные объявления не озвучиваются.
- Установление и разрыв GATT обрабатываются в
  `BleRepository.gattCallback.onConnectionStateChange`. Сигнал соединения звучит
  на `GATT_SUCCESS + STATE_CONNECTED`; сигнал разрыва — только если ранее уже
  было подтверждено соединение. Общий `closeGatt()` также обрабатывает локальное
  закрытие; флаг соединения предотвращает повторный сигнал. Ошибка первичной

- `BleEventTones` использует четыре разных системных коротких тона на notification
  stream и освобождает `ToneGenerator` после воспроизведения. Повторные принятые

  сигналом на 1,5 секунды, чтобы частая реклама не создавала непрерывный писк.

## Аудит прототипа bonded `connectGatt(autoConnect=true)` — 28.09.2026

- Перед изменением выполнен `build-android.ps1`: `assembleDebug` завершился
  успешно. Это архивная Android-ветка с callback-сканером, а не предыдущая
  схема PendingIntent scan.
- Сейчас `BleRepository.findAndConnect()` запускает LOW_LATENCY scan по
  Service UUID; принятая реклама после проверки `rssiThreshold` останавливает
  scan и вызывает `pairOrConnect()`. Для bonded-замка `connect()` всегда
  использует `connectGatt(autoConnect=false)`, а восьмисекундный watchdog
  закрывает GATT без callback.
- `BleLockService` сохраняет защиту от повторного OPEN через
  `openSentForPresence`; после чистого отключения ожидает departure отдельным
  scan, затем планирует новый цикл. Ошибки идут через существующий reconnect

  нельзя применять восьмисекундный connect watchdog: отсутствие callback,
  пока замок вне зоны, является штатным ожиданием Android auto-connect.
- Не bonded-устройство и административный режим сохраняют текущий путь.
  Все auth/GATT операции после callback подключения остаются прежними.
- Это тестовый прототип, не подтверждённая замена штатной архитектуры;
  проверка требует физического телефона и замка после установки APK.
- Последующий аудит фактических логов выявил причину редких реальных попыток:

  зарегистрированный native auto-connect, а сервис назначал новые вызовы через
  3/6/12/24/30-секундный backoff. Android API документирует автоматические
  повторы `autoConnect=true` после разрыва/выхода устройства из зоны.
- Следующая итерация прототипа сохраняет GATT-объект после разрыва, оставляет

- При первом тесте сохранённого GATT обнаружена гонка: уже поставленные в main
  handler callbacks от прежней сессии могли после разрыва вернуть READY и вызвать
  лишнюю OPEN. Добавлен признак фактической link-сессии; GATT callbacks и
  отложенные handshake-действия игнорируются, пока Android не сообщит новое
  состояние CONNECTED.
- Повторная установка показала ещё одно окно гонки: callback READY уже мог быть

  `lockService`. Добавляется проверка актуальности state callback в сервисе и

  link ещё не восстановлен.
- Следующий аппаратный запуск подтвердил автоматические GATT reconnect с
